# 接口测试培训

> 基于 TOS 存储管理接口测试实战方法论，覆盖从概念到交付的完整闭环。
> 项目当前进度：4 个模块已完成（概要/卷/存储池/热备盘），45 个接口，1223 条用例。

---

## 一、接口测试是什么？为什么重要？

### 1.1 用生活比喻理解接口

你去餐厅吃饭：
1. **看菜单** → 菜单告诉你有什么菜、怎么点（接口文档）
2. **跟服务员说**「我要一份红烧肉」→ 你把需求告诉服务员，不需要关心后厨怎么炒（接口调用）
3. **服务员端菜上来** → 你拿到结果（响应数据）

接口就是两个系统之间传话的通道。打开 TOS 桌面看到的存储池列表，不是凭空出现的——是页面在背后调了 `GET /v2/storage/overview` 接口，向 NAS 后端要来的数据。

**验证方法**：打开 TOS 桌面 → 按 F12 → Network 标签 → 刷新页面，每一个网络请求就是一个接口调用，肉眼可见。

### 1.2 接口测试到底测什么？

功能测试 = 检查端上来的菜好不好看；接口测试 = 检查后厨炒菜的火候、调料、食材。

| 检查维度 | 问的是什么 | 举例 |
|---------|-----------|------|
| 状态码 | 服务端收到请求了吗？正常处理了吗？ | 200 正常 / 403 没权限 / 500 崩溃 |
| 响应结构 | 返回的数据格式对吗？ | 约定 JSON，不能返回 HTML |
| 字段值 | 数据内容对吗？ | state 应为 "healthy" 不是 null |
| 权限 | 该拦的拦住了吗？ | 普通用户不能删别人的存储池 |
| 参数校验 | 传错了能正确报错吗？ | 非法参数应返回明确错误，非 500 崩溃 |
| 边界 | 极限情况扛得住吗？ | 空字符串/超长字符串能正确处理 |

### 1.3 三个真实反例：为什么不能只测界面？

**例子一：后端 500 错误被前端吃掉**
后端崩溃返回 HTTP 500，但前端 try-catch 弹出「加载失败」提示。功能测试人员可能以为偶发网络问题，点掉就过了。接口测试直接看到 500 和错误堆栈 → 立刻定位后端 Bug。

**例子二：后端正则允许空字符串创建存储池**
校验规则有误，允许空字符串作为存储池名称创建。前端页面做了非空校验，功能测试发现不了。接口测试直接发空字符串 → 暴露后端校验漏洞。

**例子三：curl 绕过界面权限限制**
前端判断「你是普通用户，不显示删除按钮」。但如果接口不校验权限，用 curl 发 DELETE 请求 → 存储池没了。

**核心结论**：这三个例子的共同点——都是「界面看不出来，只有直接调接口才能暴露」的问题。**前端校验不可信**，后端必须独立校验。

### 1.4 不测接口会怎样？

- **删了别人的存储池**：前端只显示自己的存储池，接口没做归属校验 → 改 UUID 就能删别人的
- **权限只在界面做**：curl 绕过去就能执行越权操作

## 三、从 API 文档到测试用例：8 维度系统化分析法

面对一个新接口时，按以下流程展开测试点：

### 第一步：读取接口定义
1. 用 Apifox MCP `read_project_oas` 读取整体 OAS，定位接口路径和 HTTP 方法
2. 用 `read_project_oas_ref_resources` 读取接口详细定义（请求参数 Schema、响应 Schema、必填性、枚举值）
3. 用 SearchMemory 检索已有业务规则记忆（如字段约束、参数组合规则）

### 第二步：按 8 大维度展开测试点

| 维度 | 说明 | 展开方法 |
|------|------|----------|
| **1. 正常场景** | 每种合法的参数组合 | 枚举所有合法值组合（如创建卷：4 种文件系统 × 2 种 mode） |
| **2. 边界场景** | 每个字段的边界值 | 最小/最大值、刚好通过、刚好不通过、0、负数 |
| **3. 参数校验异常** | 每个必填/可选字段的非法值 | 必填字段缺失、类型错误、枚举值外、格式错误、空值 |
| **4. 业务逻辑异常** | 参数组合约束、状态约束 | 如「第一个卷不能是 HyperLock」、状态不满足时的操作 |
| **5. 认证/权限异常** | Token、CSRF、登录态、权限 | 未登录、Token 失效、CSRF 不一致、无权限（普通用户） |
| **6. URL/方法异常** | 请求方法、URL 格式、版本号 | GET 替代 POST、畸形 URL（多斜杠）、版本号错误（v2→v3） |
| **7. 超时场景** | 接口响应超时 | 设置超时环境 |
| **8. Header 异常** | 缺失或错误的请求头 | 缺少 Content-Type、Content-Type 类型错误 |

### 第三步：构造请求参数（Col 8）

**核心原则**：请求参数必须写完整 JSON 结构，包含所有字段（即使是空值/默认值），不可简化。

### 第四步：按模板组装各字段

| 字段 | 模板 | 说明 |
|------|------|------|
| Col 9 用例标题 | `{场景描述}（{关键参数}）` | 如「正常在现有存储池创建 ext4 卷」 |
| Col 10 前置条件 | 三条式 / 一条式 | 正常→三条式；认证异常→一条式 |
| Col 11 操作步骤 | 4 步 / 5 步（超时） | 第 3 步原样嵌入 Col 8 |
| Col 13 预期结果 | 模板 A / B / C | 正常→A（逐字段校验）；参数异常→B；认证/URL 异常→C |

## 四、接口场景矩阵：GET / POST / DELETE 全覆盖模式

从卷 Sheet 15 个接口 340+ 用例归纳出的通用模式，生成新接口用例时可直接套用。

### 4.1 GET 接口：分层组合模式

GET 接口 = **基础层 8 条（固定）** + **参数层 6 条（有参数时追加）**

#### 基础层（所有 GET 接口必须有，共 8 条）

| # | 场景维度 | 用例标题模板 | 前置条件 | Col 8 |
|---|---------|------------|---------|-------|
| 1 | 正常 | 正常获取{资源}信息 | 三条式（登录+权限+参数选择） | 有参则写参数，无参写`无` |
| 2 | 认证-未登录 | 未登录访问获取{资源}信息接口 | `1. 用户未登录` | `无` |
| 3 | 认证-Token失效 | Token失效访问获取{资源}信息 | `1. 用户登录的Token失效` | `无` |
| 4 | 认证-CSRF不一致 | CSRF不一致访问获取{资源}信息 | `1. 手动构造不同的X-Csrf-Token值` | `无` |
| 5 | 认证-无权限 | 无权限用户访问获取{资源}信息 | `1. 用户已登录但无存储管理权限` | `无` |
| 6 | 超时 | 接口响应时间超时 | 三条式 | 同正常 |
| 7 | URL-畸形 | 畸形 URL 获取{资源}信息接口 | 二条(登录+权限) | 同正常 |
| 8 | 方法错误 | 使用错误的请求类型 | 二条(登录+权限) | `无` |

> 无参数 GET 接口最少只需这 8 条。`{资源}` 替换为模块名（如「存储池列表」「磁盘信息」）。

#### 参数层（有 query/path 参数时追加，共 6 条）

| # | 场景维度 | 用例标题模板 | 适用参数类型 |
|---|---------|------------|------------|
| 9 | 参数为空 | 必填参数为空 / {参数名}参数为空 | query + path |
| 10 | 参数值非法 | {参数名}参数值非法 | query + path |
| 11 | 参数大写 | 参数名大写{参数名} | **仅 path** |
| 12 | 添加非法参数 | 添加任意非法参数 | query + path |
| 13 | 缺少参数 | 缺少{参数名}参数 | query + path |
| 14 | 参数错误 | {参数名}参数错误（值在系统中不存在） | query + path |

**速算**：无参数 GET = 8 条 | query 参数 GET = 13 条 | path 参数 GET = 14 条

### 4.2 POST 接口：按参数类型分层

| 类型 | 覆盖 | 最少条数 |
|------|------|:--:|
| **无参数 POST** | 同 GET 基础层 8 条 | 8 |
| **纯 body POST** | 基础8 + body字段 + body整体3条 + 大写 | 17+ |
| **path + body POST** | 基础8 + path6 + body字段 + body整体3条 + 大写 | 25+ |

**Body 整体维度（有请求体的 POST 固定追加 3 条）**：

- B1：请求体为空对象 `{}`
- B2：请求体不是 JSON（传字符串/非法格式）
- B3：请求体中添加任意非法参数字段

**字段分级覆盖**：

| 级别 | 条件 | 覆盖条数 |
|------|------|:--:|
| 🔴 核心 | 必填+有枚举/范围约束 | 8 条全量 |
| 🟡 重要 | 必填但无约束 | 4 条 |
| 🟢 一般 | 可选/有默认值 | 2 条 |
| ⚪ 标志 | boolean/0/1 | 1 条 |

### 4.3 DELETE 接口：两层叠加

DELETE = GET 基础层（8 条）+ DELETE 扩展层（正常+参数+状态+并发/幂等，≥12 条）

**最少覆盖**：8(GET 基础) + 1(正常) + 3(参数) + 5(状态) + 3(并发/幂等) = **20 条**

### 4.4 状态异常场景速查表

以下状态维度适用于所有对「资源」执行操作的接口：

| 状态 | 场景标题模板 | 适用接口 |
|------|------------|---------|
| 正常运行 | 正常{操作}{资源} | 全部 |
| 损坏 | {资源}损坏时执行{操作} | POST/PUT/DELETE |
| 同步中 | 同步中的{资源}执行{操作} | POST/PUT/DELETE |
| 删除中 | 对删除中的{资源}执行{操作} | POST/PUT |
| 创建中 | 创建中的{资源}执行{操作} | POST/PUT |
| 格式化中 | 格式化中的{资源}执行{操作} | POST |
| 挂载中 | 挂载中的{资源}执行{操作} | POST/PUT |
| 已删除（幂等） | 对已被删除的{资源}执行{操作} | DELETE |
| 并发-连续操作 | 连续执行{操作} | POST/PUT |
| 并发-进程冲突 | 已有{其他操作}的进程执行{操作} | POST/DELETE |

## 五、三列联动编写规律（Col 8 / Col 10 / Col 11）

### 5.1 Col 8「请求参数」写法

**核心**：写接口实际发出的参数原始形态，不写描述性文字。

| 参数类型 | 写法 | 示例 |
|---------|------|------|
| 无参数 | `无` | — |
| Query 键值 | `键：值`（中文全角冒号） | `type：detail` |
| 参数为空 | `键:`（值留空） | `uuid:` |
| 参数非法 | `键：非法值` | `type：哈哈哈哈` |
| Path 分组 | `path参数`+换行+`键:值` | `path参数`\n`uuid:{{lv0_uuid}}` |
| 请求体分组 | `请求体`+换行+`{JSON}` | `请求体`\n`{ "device": "volume" }` |
| Path + 请求体 | 两个分组并列 | `path参数`\n`uuid:xxx`\n`请求体`\n`{...}` |

### 5.2 Col 10「前置条件」写法（三种模板）

**模板 A：正常/边界/参数异常场景（三条式）**
```
1. 用户已登录并获取有效Token
2. 用户具有存储管理权限
3. {业务前提，如「参数选用type：detail」/「系统中存在卷」/「无参数选择」}
```

**模板 B：认证/权限异常场景（一条式）**

| 场景 | 前置条件 |
|------|---------|
| Token 失效 | `1. 用户登录的Token失效` |
| 未登录 | `1. 用户未登录` |
| 无权限 / 普通用户 | `1. 用户已登录但无存储管理权限` |
| CSRF 不一致 | `1. 手动构造不同的X-Csrf-Token值` |
| X-CurPass-Token 错误 | `1. 手动构造错误的X-CurPass-Token` |
| X-CurPass-Token 为空 | `1. 手动构造为空的X-CurPass-Token` |

**模板 C：留空** — 同一接口下多条用例前提相同，只在首行写，其他行留空。

### 5.3 三列联动速查表

| 用例场景 | Col 8 | Col 10 | Col 11 特点 |
|---------|-------|--------|-------------|
| 正常场景 | 具体参数值 | 三条(登录+权限+参数选择) | 第2步「有效」，第3步嵌入参数 |
| 参数为空 | `无` / `键:` | 三条(第3条「无参数选择」/「参数为空」) | 第3步嵌入空或省略 |
| 参数非法 | `键：非法值` | 三条(第3条「参数选择非法…」) | 第2步「有效」，第3步嵌入非法值 |
| Token失效 | 通常 `无` | 一条(Token失效) | 第2步「无效」 |
| CSRF不一致 | 通常 `无` | 一条(手动构造) | 第2步「对应的」 |
| 无权限 | 通常 `无` | 一条(登录但无权限) | 第2步「有效」 |
| 畸形URL | 正常 | 二条(登录+权限) | 第1步URL变形 |

## 六、操作步骤编写规范

### 6.1 标准四步结构

每步内容必须根据接口实际情况动态生成，不可套用固定模板。

| 步骤 | 内容 | 规则 |
|------|------|------|
| 第 1 步 | 使用 {HTTP方法} 请求访问 {接口完整路径} | 方法从 Col 6 读取并转大写；路径从 Col 3 读取 |
| 第 2 步 | 携带 {认证凭证} | 根据 Col 7「请求头」实际内容动态生成 |
| 第 3 步 | 携带{Col 8 原样嵌入} | Col 8 为空/「无」/「-」时省略此步（变 3 步） |
| 第 4 步 | 查看接口响应 | 固定写法 |

### 6.2 第 3 步 Col 8 原样嵌入规范（核心规则）

**总原则**：Col 8「请求参数」内容必须原样嵌入到第 3 步，禁止简化描述、抽象改写。

**分组标签白名单**（去尾冒号后作为携带对象）：`path参数 / 请求体 / 参数 / query参数 / 请求参数 / 请求头 / header参数`

**规则**：
1. 若 Col 8 首行是白名单标签（如 `path参数`、`请求体`），首行去尾冒号后拼成 `3. 携带{标签}`，后续行原样保留
2. 若 Col 8 首行不是白名单（如 `uuid:`、`type：detail`），冒号必须保留，整个 Col 8 原样跟在 `3. 携带` 后

**示例对照**：

| Col 8 内容 | 生成的第 3 步 |
|-----------|--------------|
| `path参数`<br>`uuid:{{lv0_uuid}}` | `3. 携带path参数`<br>`uuid:{{lv0_uuid}}` |
| `请求体`<br>`{`<br>`  "device": "volume"`<br>`}` | `3. 携带请求体`<br>`{`<br>`  "device": "volume"`<br>`}` |
| `uuid:` | `3. 携带uuid:` |
| `type：detail` | `3. 携带type：detail` |

**禁止的反例**：
- 抽象描述：「携带请求体某一参数为空」→ 应直接贴完整 JSON
- 误去冒号：`Col 8=uuid:` 写成 `3. 携带uuid` → 冒号必须保留（非白名单）
- 简写路径参数：`3. 携带参数uuid为空` → 应写 `3. 携带path参数\nuuid:`

### 6.3 超时场景五步结构

「接口响应时间超时」场景为 5 步，在标准 4 步前插入「设置超时环境」：

```
1. 设置接口超时环境
2. 携带有效 Cookie 和 X-Csrf-Token
3. 使用 GET 请求访问 /v2/storage/overview
4. 查看接口响应
```

### 6.4 凭证动态提取规则

第 2 步根据 Col 7 请求头实际 Header 名拼接，禁止硬编码：

| Col 7 含有的 Header | 第 2 步 |
|---------------------|---------|
| Cookie + X-Csrf-Token | `携带有效 Cookie 和 X-Csrf-Token` |
| Cookie + X-Csrf-Token + X-CurPass-Token | `携带有效 Cookie、X-Csrf-Token 和 X-CurPass-Token` |
| 仅 Content-Type（未登录场景） | 不携带认证信息（整步省略或写无） |

## 七、预期结果编写规范（三类模板）

### 模板 A：正常场景（有数据返回）

不贴完整 JSON，用逐字段校验列表 + 业务逻辑校验放最后，≤10 行。

```
1.HTTP Status Code = 200 OK。
2.Content-Type = application/json。
3.响应 Body：
- is_login = true
- code = true
- code_num = 0
- data 为 Array/Object 类型。
- data 数组长度 > 0。
- 每个对象包含 health、level、uuid、show_name、total 等字段（对照 Apifox Schema）。
- time > 0。
- code_msg 为空。
4.返回的存储池/卷信息与页面显示一致。
```

### 模板 B：边界/空数据场景

先贴精简 JSON，再分项字段校验，最后兜底。

```
1.HTTP Status Code = 200 OK。
2.Content-Type = application/json。
3.响应 Body：
{ "is_login": true, "code": true, "code_num": 0, "data": [], "time": 0.034, "code_msg": "" }
4.字段校验：
- is_login = true
- code = true
- code_num = 0
- data 数组长度 = 0。
- time > 0。
- code_msg 为空。
5.接口正常返回，不报错、不返回 500、不返回异常信息。
```

### 模板 C：纯异常场景（403/404）

极简，只写状态码：

```
1.HTTP Status Code = 403 。
```

### 预期结果的得出过程（三源推导）

1. 先看**实际结果**：拿到接口真实返回的 JSON
2. 对照 **Apifox 文档**：确认字段枚举值、类型、必填性
3. 参考 **YApi api.json**：补充字段业务描述
4. 综合三者，按模板 A/B/C 写出预期结果

> **所有字段校验必须严格对照 Apifox 文档 Schema**，不能凭空编造。

## 八、认证场景与凭证变量规范

TNAS 鉴权机制：Cookie（会话）+ X-Csrf-Token（防跨站，服务端比对请求头 X-Csrf-Token 与 Cookie 内绑定值）。

### 8.1 四类鉴权失败场景

| 场景 | Cookie | X-Csrf-Token | 失败原因 |
|------|--------|-------------|---------|
| 未登录 | 移除（不发）| 移除（不发）| 没有任何凭证 |
| Token 失效 | `{{expired_Cookie}}` | `{{expired_X-Csrf-Token}}` | 会话已过期 |
| CSRF 不一致 | `{{Cookie}}`（**必须有效**）| `{{wrong_X-Csrf-Token}}` | Cookie 有效但 Token 不一致 |
| 无权限/普通用户 | `{{NormalUserCookie}}` | `{{NormalUserCsrfToken}}` | 凭证有效但无存储管理权限 |

### 8.2 Col 7 请求头格式（凭证变量参照）

```
Content-Type: application/json
Cookie: {{Cookie}}
X-Csrf-Token: {{X-Csrf-Token}}
```

认证场景按上表替换为对应的失效/错误/普通用户凭证变量后写入 Col 7。例如 CSRF 不一致场景：

```
Content-Type: application/json
Cookie: {{Cookie}}
X-Csrf-Token: {{wrong_X-Csrf-Token}}
```

> **Col 7 是请求头的唯一真源**。生成 Apifox 用例时，headers 必须解析 Col 7 每行（`Header名: 值`），不可硬编码固定值。

### 8.3 需在 Apifox 环境变量预置的凭证

- 正常有效：`Cookie` / `X-Csrf-Token` / `X-CurPass-Token`
- 失效会话：`expired_Cookie` / `expired_X-Csrf-Token`
- CSRF 不一致：`wrong_X-Csrf-Token`（与 Cookie 不一致的值）
- 普通用户：`NormalUserCookie` / `NormalUserCsrfToken` / `NormalUser_X-Curpass-Token`

## 九、六维质量审查规范

| 维度 | 检查内容 | 常见错误 |
|------|----------|----------|
| 1. 标题与关联功能一致性 | 标题中不得出现其他接口名称 | 「存储概览信息」出现在非 overview 接口中 |
| 2. 前置条件准确性 | 术语统一（「磁盘」≠「存储池」≠「卷」） | 「存在存储池」应为「存在磁盘」 |
| 3. 操作步骤聚焦性 | 方法错误测试不应混入「普通用户」描述 | POST 接口步骤写 GET |
| 4. 预期结果与 Schema 一致性 | 字段名、类型、枚举值对照 Apifox | 畸形 URL 预期 403 应为 404 |
| 5. 畸形 URL 路径匹配性 | 路径指向对应接口真实地址 | `/v2/storage/overview` 写成 `/v2/disk/GetOverview` |
| 6. 实际结果与预期结果自洽 | 逻辑不矛盾 | 预期 200 但实际返回 404 |

### 复制粘贴错误的识别与修正

| 错误类型 | 修正方式 |
|----------|----------|
| 标题含其他接口名 | 替换为当前「关联功能」列的值 |
| 接口地址版本号错误（v2→v3/v4） | 统一回 v2 |
| 操作步骤路径残留上一个接口 | 替换为当前接口地址 |
| 操作步骤方法错误（POST 写 GET） | 改为与「接口请求类型」一致 |
| 前置条件术语错误 | 根据接口类型替换 |
| 前置条件不完整（Token 失效缺「已登录」） | 补充「用户已登录但 Token 已失效」 |
| 预期结果 403→404 | 畸形 URL 实际返回 404，改为 404 |

## 十二、常见陷阱

| 陷阱 | 表现 | 处理 |
|------|------|------|
| Excel 进程残留 | 脚本报「OK」但 Save 静默失败 | 执行前 Kill 所有 EXCEL 进程 |
| 列号误判 | 「接口地址空」「请求方法无法继承」 | 先用 `dump_cols.ps1` 确认列号 |
| UTF-8 BOM 缺失 | 脚本中文变乱码 | `[byte[]](0xEF,0xBB,0xBF) + $bytes` 写回 |
| Cookie 过期 | 所有接口 403 | 重新登录刷新凭证 |
| 实际结果只写描述 | 写「正常返回」四个字 | 必须贴完整 JSON 响应体 |
| 变量引用不生效 | `{{Cookie}}` 未被替换 | 检查 Apifox 环境选择器和变量名拼写 |
| GET 接口请求头漏写 | 批量生成时 Col 7 为空 | 所有用例行必须写入 Col 7 请求头 |
| 预期结果提前填模板 | Col 13 写了占位符 | 未获取实际返回值前 Col 13 必须留空 |
| 403 响应当成 JSON | 403 返回 HTML | 实际结果必须保留原始 HTML 内容 |
| Col 7 认证场景凭证用错 | 认证用例全用了正常凭证 → 触发不了鉴权失败 | 按场景替换为对应的失效/错误/普通用户凭证变量 |
| 认证行请求参数与正常不一致 | 认证行清了参数 → 无法验证鉴权是否真生效 | 认证/超时/畸形/方法行请求参数必须与正常场景一致 |

## 十三、实战案例：编辑卷接口完整测试点设计

### 13.13 设计总结

编辑卷接口共设计 **44 条用例**（path+body POST，基础8 + path参数6 + body字段14 + body整体3 + 业务逻辑8 + 状态2 + 并发1 + 超时1 + Header1）。

**关键经验**：

1. **编辑类接口的字段极易与创建类混淆**——编辑卷的 body 字段是 description/capacity/hyper_lock_day/quota_flag，创建卷是 name/raid/desc/spare_disks/force，两者完全不同，必须以 Apifox Schema 为准
2. **卷类型决定字段的合法域**——ext4/Btrfs/WORM 三种卷类型对 quota_flag、hyper_lock_day 的约束不同，每种类型都要覆盖
3. **容量相关有两个「不校验」的边界**——容量小于当前（不拒绝缩容）、容量超过池可用（不校验上限），这两条虽然表面像 Bug 但实际是设计如此，需在备注中说明
4. **code_num 错误是高频 Bug 类型**——13 个 Bug 中有 6 个与 code_num 相关，说明错误码规范是薄弱环节
5. **普通用户越权是严重问题**——B13 属于权限校验缺失，应在回归中优先修复

| 等级 | 判定规则 | 适用场景 |
|------|---------|---------|
| P0 | 核心正常场景 | 接口正常调用 |

> 优先级分类器 P2 须先于 P1 判定：如「CurPass 为空」属认证 P2 而非参数 P1。

## 十六、总结

1. **接口测试不是玄学**——每一步都是可验证、可复现、有据可查的
2. **前端校验不可信**——后端必须独立校验参数和权限
3. **实际结果 ≠ 描述**——必须贴完整响应体，拒绝「正常」两个字
4. **预期结果 ≤10 行**——只点关键字段、类型、核心约束
5. **场景设计靠 AI 辅助 + 人工审查**——正向/反向/边界/权限全覆盖
6. **认证场景请求头才是触发鉴权失败的关键**——按场景换对应的失效/错误凭证变量
7. **Excel 是唯一真源**——Apifox 用例从 Excel 生成，Col 7 是请求头的唯一真源
