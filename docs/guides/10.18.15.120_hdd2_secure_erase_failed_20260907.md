# 10.18.15.120 HDD2 安全擦除失败分析

> 记录日期：2026-09-07  
> 目标设备：`10.18.15.120`，hostname `F6-32`  
> TOS 运行版本：`TOS_X642.0_7.0.1140`（以 `/usr/lib/version` 为准）  
> StorageManager 版本：`1.1.007`  
> 内核版本：`6.12.63+`  
> 本次性质：只读排查，未执行数据格式化、重新擦除、停止服务或修改 TOS 配置

## 1. 结论

HDD2 不是典型物理坏盘。SMART 总体健康状态为 `PASSED`，重分配扇区、当前待映射扇区和离线不可校正扇区均为 `0`。

当前“点击就数据获取失败”的直接原因，是 TOS StorageManager 在安全擦除结束后，未能把设备路径从 `/dev/shm/erasesdc` 恢复为 `/dev/sdc`。而更底层的故障链是：安全擦除期间触发了 `udev` 事件，TOS 的 udev 规则对 `/dev/sdc` 写入块设备队列参数，worker 卡在 `blk_mq_freeze_queue_wait`，最终导致 StorageManager 超时并杀掉 udev worker。

因此，本问题应定位为 **StorageManager、udev 与块设备队列之间的锁等待/超时竞争**，不是磁盘本身在安全擦除后突然损坏。

## 4. 根因分析

### 4.1 直接失败点

StorageManager 的失败日志位于 `/tmp/log/StorageManager/access.20260907.log`：

```text
2026-09-07 14:30:13.321 [ERRO] failed to restore erase device path
from /dev/shm/erasesdc to /dev/sdc err context deadline exceeded
```

对应的 StorageManager 调用栈指向：

```text
secerase.(*SecErase).EraseSyncContext
DiskTaskCommands.executeDiskEraseContext
DiskOperationImpl.SecErase
```

### 4.2 底层阻塞点

内核日志显示：

```text
task:systemd-udevd
state:D
blk_mq_freeze_queue_wait+0x96/0xd0
queue_attr_store+0x60/0xc0
```

这说明 `udev` worker 在往某个块设备队列属性写入时，等待请求队列解冻，但队列一直没有解冻。

### 4.3 TOS 的 udev 规则

目标机器上的 `/etc/udev/rules.d/00-default.rules`：

```text
# modify block read_ahead_kb
ACTION=="add|change",KERNEL=="sd[a-z]",
ATTR{queue/read_ahead_kb}="4096",
ATTR{queue/nr_requests}="128"
```

该规则会在每个 `sd[a-z]` 的 `add/change` 事件中写入 `queue/read_ahead_kb` 和 `queue/nr_requests`。写入 `nr_requests` 等队列属性时，内核会尝试冻结请求队列；如果队列已被安全擦除或设备管理流程冻结，就会一直等待。

### 4.4 完整根因链

1. 安全擦除开始时，HDD2 被从系统 RAID 成员中移除。
2. StorageManager 把 `/dev/sdc` 移为 `/dev/shm/erasesdc`。
3. 期间 `/dev/sdc` 触发块设备 `add/change` 事件。
4. TOS 的 udev 规则尝试写入 `/sys/block/sdc/queue/nr_requests`。
5. 块设备队列处于冻结或等待状态，`udev` worker 卡住。
6. StorageManager 等待路径恢复，但 context 超时先到期。
7. StorageManager 杀掉 udev worker，并报告安全擦除失败。
8. `/dev/sdc` 节点没有被恢复，UI 后续一直按旧路径查询，显示“设备不存在”。

这个链条的证据完整度较高，但尚未在其他隔离设备上做对照复现，因此建议将其表述为“高置信度根因判断”，而不是已完成的回归测试结论。

## 6. 当前状态

当前设备状态：

```text
sda   disk 931.5G WDC WD10EJRX-89N74Y0  WD-WCC4J2YZDVJX  sata  running
sde   disk 931.5G TOSHIBA DT01ABA100V    91LU8ZLES         sata  running
```

`/dev/sda` 与原始 `/dev/sdc` 是同一块 WDC 盘：

- `/dev/sda` 存在，SMART 为 `PASSED`。
- `/dev/sdc` 不存在。
- `/dev/shm/erasesdc` 仍是旧的临时设备节点，已不是当前有效路径。
- 故障期间 StorageManager 日志按 `/dev/sdc` 查询并返回 `device not found`；截至本次采集，未再看到新的同类错误。
- 系统中未发现新的安全擦除进程；存储管理服务仍为 `active`。

日志中最后一次 `/dev/sdc` 的 `device not found` 是 `15:00:52`；此后未再看到新的 `/dev/sdc` 错误，说明旧路径轮询至少已经停止。这可能是页面刷新、TOS 重新扫描，或 udev 重新枚举后前端状态被更新。

### 6.1 为什么现在看起来正常

“看起来正常”并不等于磁盘修复了，也不代表数据回来了。更准确的说法是：底层硬盘本来就没有出现物理坏盘特征，之前失败的是 TOS 管理层的路径恢复流程。

关键变化：

1. `15:00:46` 日志显示 SCST 解绑，`/dev/sdc` 被停止。
2. `15:01:20` SATA 链路重新上线。
3. 同一块 WDC 盘以 `/dev/sda` 重新出现，序列号仍为 `WD-WCC4J2YZDVJX`。
4. `/dev/sda` 有完整的 `by-id`、`by-path` udev 符号链接。
5. 当前 SMART 为 `PASSED`。

因此，如果 UI 现在显示 HDD2 正常，通常是“内核与 udev 重新拿到了有效设备路径”后的结果。磁盘本身仍是已安全擦除、无分区表的状态；如果要重新使用，仍需要后续初始化。

本次排查未执行数据写入、格式化、重新擦除或 NAS 配置修改。排查中运行过 `udevadm test` 调试模式，该工具不会执行 `RUN` 程序；之后日志出现 `sdc -> sda` 重新枚举，这个变化可能是 TOS/SCST/udev 清理触发，不能排除调试检查促使了重新枚举，但未发生数据写入操作。

## 7. 后续建议

1. **不要立即重复安全擦除。** 当前磁盘本身可以通过 SMART，重复擦除可能再次触发相同的 udev/队列竞争。
2. **优先让 TOS 重新扫描磁盘表。** 可考虑刷新页面、重新登录 TOS，或由授权人员执行 `udevadm trigger`、`udevadm settle`、重启 StorageManager 等恢复路径；执行前先确认没有正在运行的坏块扫描、擦除或卷任务。
3. **避免手工创建 `/dev/sdc` 后直接使用。** 先确认 StorageManager 是否会把新设备识别为同一序列号；否则可能造成前端和内核路径不一致。
4. **反馈给 TerraMaster 或内部研发时，应附上：**
   - TOS `7.0.1140`；
   - StorageManager `1.1.007`；
   - `/etc/udev/rules.d/00-default.rules:4`；
   - `14:30:13` 的 `failed to restore erase device path`；
   - 内核 `blk_mq_freeze_queue_wait + queue_attr_store`；
   - HDD2 在擦除后由 `/dev/sdc` 变更为 `/dev/sda` 的设备名变化；
   - WDC 盘 SMART 当前 `PASSED`。
5. **HDD3 按坏盘处理。** 建议在更换或停用前不要依赖其读写；当前后台坏块扫描未完成，后续再做该盘动作前应先确认其状态。

## 10. 复现方案

### 10.1 复现环境

建议在隔离的测试 NAS 上复现，不要在生产机器上直接执行：

| 条件 | 要求 |
| --- | --- |
| TOS 版本 | `TOS_X642.0_7.0.1140`（以 `/usr/lib/version` 为准） |
| StorageManager | `1.1.007` |
| 内核 | `6.12.63+` |
| udev 规则 | 必须保留 `/etc/udev/rules.d/00-default.rules` 的第 4 行 |
| 目标盘 | 一块可牺牲的 SATA HDD，TOS 识别为 HDD2，支持安全擦除 |
| 目标盘状态 | 不影响系统盘、当前 `md` 阵列、LVM/Btrfs 卷或唯一数据副本 |
| 测试数据 | 不需要；复现前确认盘上没有需要保留的数据 |

如果无法使用隔离设备，当前 `10.18.15.120` 的 HDD2 `/dev/sda` 可以作为候选，但必须先确认没有其他正在运行的磁盘任务，且用户明确授权执行破坏性测试。

### 10.2 前置校验

```bash
hostname
cat /usr/lib/version
dpkg -s storagemanager | grep -E "^(Status|Version):"

lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,TRAN,STATE,MOUNTPOINTS
cat /proc/mdstat
findmnt -rno TARGET,SOURCE,FSTYPE

smartctl -d sat,auto -H /dev/sda
smartctl -d sat,auto -g security /dev/sda
cat /etc/udev/rules.d/00-default.rules
```

通过 TOS UI 或 Postman 请求：

```text
GET /v2/disk/GetDiskOption
GET /v2/disk/GetDiskListData
GET /v2/disk/GetDiskCapabilities?device=/dev/sda
```

前置通过标准：

- TOS 能看到 HDD2，设备路径为 `/dev/sda`；
- 目标盘不是当前系统盘、不在 `md1`/`md8`/`md9` 中；
- 目标盘无挂载点；
- `secure_erase_info.is_support = true`；
- ATA Security 为 `Disabled, NOT FROZEN`；
- 没有正在运行的格式化、擦除、坏块扫描或性能测试任务。

### 10.3 最小复现步骤

1. 登录 TOS 网页。
2. 打开存储管理的磁盘页面，选中 HDD2。
3. 点击“安全擦除”，按页面提示输入密码并确认。
4. 立即在 NAS SSH 会话中开启实时监控：

   ```bash
   journalctl -u StorageManager.service -f
   dmesg -wT
   ```

   另开一个会话每秒采集设备状态：

   ```bash
   while true; do
     date '+%F %T'
     ls -l /dev/sda /dev/shm/erasesda /sys/block/sda 2>&1
     ps -ef | grep -E "systemd-udevd|badblocks|smartctl|storagemanager" | grep -v grep
     sleep 5
   done
   ```

5. 观察 5 到 10 分钟，重点记录：

   - StorageManager 是否出现 `failed to restore erase device path`；
   - `/dev/sda` 或临时路径是否消失；
   - `systemd-udevd` worker 是否进入 `D` 状态；
   - `dmesg` 是否出现 `queue_attr_store -> blk_mq_freeze_queue_wait`；
   - UI 是否出现“设备不存在”或 `GetDiskCapabilities` 返回 `device is not found`。

6. 如第一次未复现，重复执行至少 3 到 5 次。该问题可能依赖事件触发时机。

### 10.4 增强复现条件

现场原始的 HDD2 安全擦除与另一块 SATA 盘的坏块扫描同时运行。如果最小复现不稳定，可以增加并发负载：

1. 使用另一块可牺牲的 SATA 盘；
2. 先启动该盘的坏块扫描：

   ```text
   POST /v2/disk/DiskScan
   device=/dev/sdX
   status=1
   ```

3. 在坏块扫描仍处于运行状态时，再启动 HDD2 安全擦除。

HDD3 的健康状态不作为本次复现的结论依据；它只作为并发负载因素，用于逼近原始触发条件。

### 10.5 复现判定

判定为复现成功，必须同时满足：

1. `StorageManager` 日志记录 `disk erase command failed` 或 `failed to restore erase device path ... context deadline exceeded`；
2. 内核日志出现 `blk_mq_freeze_queue_wait`；
3. `/dev/sda` 或 `/dev/sdc` 设备路径在擦除期间消失；
4. UI 或 `GetDiskCapabilities` 出现设备不存在；
5. 后续通过 udev/SCSI 重新枚举后，同一序列号磁盘恢复。

如果安全擦除正常返回成功、设备路径始终存在、无 `restore erase device path` 错误，则本次未复现。

### 10.6 复现后处置

- 先保存完整日志，不要立即格式化或重复擦除。
- 等待设备重新枚举；如未恢复，经用户确认后再执行 `udevadm trigger` 或重启 StorageManager。
- 若需要交给研发，保留 `/tmp/log/StorageManager/access.20260907.log`、`storage_device_tool.log`、`syslog` 和 `dmesg -T` 的对应片段。
- 不要在未确认目标盘身份和授权的情况下执行 `/dev/sda` 上的写入、分区、格式化或擦除。

在 TOS 存储管理中对 HDD2 执行“安全擦除”后，StorageManager 没有成功把 `/dev/shm/erasesdc` 恢复为 `/dev/sdc`。前端随后调用 `GetDiskCapabilities` 和 `GetDiskDetailData` 时返回 `device is not found` / `device invalid`，用户侧显示“数据获取失败”。

该盘底层 SMART 当前为 `PASSED`，未出现重分配扇区或当前待映射坏扇区；ATA Security 为 `Disabled, NOT FROZEN`。现场最终通过 SATA/SCSI 重新枚举恢复为 `/dev/sda`，说明问题更可能是 StorageManager 与 udev/块设备队列的竞态，而不是磁盘本体损坏。

### 11.5 复现环境

1. TOS `7.0.1140`，StorageManager `1.1.007`。
2. `/etc/udev/rules.d/00-default.rules` 第 4 行存在：

   ```text
   ACTION=="add|change",KERNEL=="sd[a-z]",
   ATTR{queue/read_ahead_kb}="4096",
   ATTR{queue/nr_requests}="128"
   ```

3. HDD2 为可安全擦除的 SATA 盘，未挂载、不在当前活动 md/LVM 阵列中。
4. 磁盘无需要保留的数据。

### 11.7 期望行为

- 安全擦除任务按状态机正常执行。
- 擦除结束后，临时设备路径恢复为原设备路径。

### 11.8 实际行为

- `12:06:45` 安全擦除开始，预计 148 分钟。
- 随后 udev worker 卡在 `queue_attr_store -> blk_mq_freeze_queue_wait`。
- `14:30:13` StorageManager 报 `disk erase command failed device=/dev/sdc err="context deadline exceeded"`。
- `14:30:13` 报 `failed to restore erase device path from /dev/shm/erasesdc to /dev/sdc`。
- TOS 通知 HDD2 安全擦除失败。
- 前端反复请求 `/disk/GetDiskCapabilities?device=/dev/sdc`，返回 `device is not found`。
- 最终 `15:00:46` 后设备重新枚举为 `/dev/sda`，底层 SMART 为 `PASSED`。

### 11.9 根因初步判断

StorageManager 在安全擦除期间将块设备路径移到临时节点；期间设备触发 `add/change` 事件，TOS 的 udev 规则尝试写 `queue/nr_requests` 等属性。块设备队列被安全擦除/设备管理流程保持冻结，udev worker 在 `blk_mq_freeze_queue_wait` 中等待，StorageManager 的路径恢复最终超时。

因此问题属于：

> StorageManager 安全擦除、udev 队列属性写入、块设备冻结状态之间的锁等待竞态。

### 11.11 给研发的建议

1. 确认 `00-default.rules` 是否应在安全擦除、设备管理或临时 `erasesd*` 路径场景跳过队列属性写入。
2. 检查 `queue/nr_requests` 和 `queue/read_ahead_kb` 的写入是否会触发队列冻结，以及为何等待不会及时返回。
3. 安全擦除后的路径恢复应支持超时重试，或改用不会与 udev 事件冲突的方式恢复设备节点。
4. StorageManager 应允许设备名变化，按序列号或 `by-id` 等稳定身份重新建立映射，而不是固定依赖旧 `/dev/sdX`。
5. 安全擦除失败通知应区分“底层擦除失败”和“管理流程/设备路径恢复失败”，避免用户误以为磁盘损坏。
