# 项目目录重建方案（2026-08-04）

> 当前阶段：目录迁移、正式工具提炼、文档修正和 Git 提交均已完成；`win` 与 `main` 以本次同步后的同一提交为准。所有移出根目录的资产均为可恢复移动，未批量删除。
>
> 核心目标：让根目录只呈现当前业务、正式工具、文档和明确的归档入口；存储管理应用重构测试是当前业务中心。

## 一、整理前的混乱来源（历史记录）

1. 旧版自动化目录从根目录迁入 `test_automation/` 后，Git 仍显示旧目录大量删除、新目录整体未跟踪。
2. Git 暂存区已有 36 个 `tos_api_cli_tester` 文件，与目录重建不是同一主题。
3. `temp_scripts/` 包含约 5115 个文件，混合正式检查器、一次性修复脚本、生成数据、日志、缓存和 `node_modules`。
4. 根目录存在明确重复或孤立资产：
   - `api_testing/` 只剩一个与核心目录完全相同的 `pre_usb_mount_encrypt.js`。
   - 文档存在多组内容完全相同的副本。
5. `itachi-v2-run/` 和 `itachi-validate.json` 是宠物生成资产，不属于本工程。
6. `miaoqi/` 是个人素材目录，按现有约束不移动、不修改。
7. `README.md` 和部分编号文档仍描述整理前结构。

## 二、重建原则

- **先保路径稳定**：暂不重命名 `接口测试用例/`、`temp_scripts/`、`storagemanager/`。
- **正式与临时分离**：可复用工具进入 `tools/`；`temp_scripts/` 只作为忽略的历史工作台。
- **活跃与归档分离**：历史脚本、记忆导出、参考项目统一进入 `archives/` 的明确子目录。
- **业务与个人分离**：个人素材和宠物产物不进入工程提交。
- **先清理 Git 再提交**：拆分已有暂存内容，避免把独立工具发布与目录重建混为一个提交。
- **所有迁移可回滚**：移动前生成清单，移动后检查文件数、哈希、引用路径和 Git diff。

## 六、推荐迁移阶段

### 阶段 0：保护现场

### 阶段 1：低风险根目录清理

1. 更新 `.gitignore`：`.obsidian/`、宠物产物、个人目录及本地凭据。
2. 合并并移除重复的根 `api_testing/` 壳目录。
3. 清理完全重复的文档副本，并修复所有引用。
4. 更新根 `README.md` 和权威目录索引。

### 阶段 2：归档历史资产

1. 将 `scripts_legacy/` 移到 `archives/scripts_legacy/`。
2. 将 `qoder_memory_export/` 移到 `archives/qoder_memory_export/`。
3. 将 `test-case_project/` 移到 `archives/test_case_reference/`。
4. 每次只移动一个目录，随后执行引用搜索和 Git diff 检查。

1. 在 `tools/api_case_pipeline/` 建立独立 README。

4. 为体检与对账增加结构化输出、退出码和最小测试。
