## 二、预期结果的得出方式

预期结果不是凭空写的，而是**综合三个来源**得出的：

| 来源 | 提供什么信息 | 用途 |
|------|-------------|------|
| **实际结果** | 接口真实返回的 JSON 数据 | 确定字段的实际值、数据类型、嵌套结构 |
| **Apifox 文档预览** | 接口定义的 Schema（字段名、类型、枚举值、必填性） | 确定字段校验规则、合法取值范围 |
| **YApi 导出的 api.json** | 完整的接口定义（请求头、请求体、响应体、描述） | 补充 Apifox 可能缺失的字段说明、业务逻辑描述 |

**得出过程：**
1. 先看**实际结果**：拿到接口真实返回的 JSON，知道 `data` 是 Array 还是 Object、包含哪些字段
2. 再对照 **Apifox 文档预览**：确认字段的枚举值（如 `health: [0,1,2,3,4,7,9,999]`）、类型、必填性
3. 参考 **YApi api.json**：补充字段的业务描述（如"health: 0=损坏, 7=正常"）
4. 综合以上三者，按模板 A/B/C 写出预期结果

**关键原则**：预期结果中的每个字段校验都必须有依据（来自 Schema 或实际结果），不能凭空编造。

## 三、操作步骤规范（四步结构）

每步内容必须根据接口实际情况**动态生成**，不可套用固定模板。

| 步骤 | 内容 | 是否固定 |
|------|------|----------|
| **第 1 步** | 使用 {HTTP方法} 请求访问 {接口完整路径} | 方法从"接口请求类型"列读取；路径从"接口地址"列读取（有的接口没有 v2 前缀，必须如实写）；查询参数写在路径后（如 `?type=detail`） |
| **第 2 步** | 携带 {请求头中定义的认证参数} | **根据"请求头"列实际内容写**，不是固定写法。常见：`携带有效 Cookie 和 X-Csrf-Token`；特殊接口含 X-CurPass-Token 时：`携带有效 Cookie、X-Csrf-Token 和 X-CurPass-Token` |
| **第 3 步** | 携带参数值{请求参数/路径参数/请求体} | 根据"请求参数"列决定。参数为"无"时**省略此步**，总共 3 步。有参数时写明内容（如 `uuid:lv0_uuid`、请求体 JSON 等） |
| **第 4 步** | 查看接口响应 | 固定写法 |

**无参数示例（3 步）：**
```
1. 使用 Get 请求访问 /v2/storage/status
2. 携带有效 Cookie 和 X-Csrf-Token
3. 查看接口响应
```

**有参数示例（4 步）：**
```
1. 使用 Put 请求访问对应接口
2. 携带有效 Cookie 和 X-Csrf-Token
3. 携带path参数 uuid:lv0_uuid 请求体 { "description": "执行编辑卷", "capacity": 10.55, "quota_flag": 1 }
4. 查看接口响应
```

## 四、预期结果规范（三类模板）

### 模板 A：正常场景（有数据返回）

```
1.HTTP Status Code = 200 OK。
2.Content-Type = application/json。
3.响应 Body：
- is_login = true
- code = true
- code_num = 0
- data 为 Array/Object 类型。
- data 数组长度 > 0。
- 每个对象包含 xx、yy、zz 等字段（对照 Apifox Schema）。
- time > 0。
- code_msg 为空。
4.返回的 xx 信息与页面显示一致。
```

**特点**：不贴完整 JSON，用逐字段校验列表 + 业务逻辑校验放最后。

### 模板 B：边界/空数据场景

```
1.HTTP Status Code = 200 OK。
2.Content-Type = application/json。
3.响应 Body：
{ 贴完整小 JSON }
4.字段校验：
- is_login = true
- code = true
- code_num = 0
- data 数组长度 = 0。
- time > 0。
- code_msg 为空。
5.接口正常返回，不报错、不返回 500、不返回异常信息。
```

**特点**：数据量小先贴 JSON，再逐项校验，最后兜底。

### 模板 C：纯异常场景（403/404）

```
1.HTTP Status Code = 403 。
```

**特点**：极简，只写状态码。

**所有字段校验必须严格对照 Apifox 文档 Schema**（类型、枚举值、必填性）。

## 五、六维质量审查规范

| 维度 | 检查内容 | 常见错误 |
|------|----------|----------|
| **1. 标题与关联功能一致性** | 标题中不得出现其他接口名称 | "存储概览信息"出现在非 overview 接口中 |
| **2. 前置条件准确性** | 术语统一（"磁盘"≠"存储池"≠"卷"），Token 失效类必含"已登录"前提 | "存在存储池"应为"存在磁盘"；缺少"已登录" |
| **3. 操作步骤聚焦性** | 方法错误测试不应混入"普通用户"描述 | POST 接口步骤写 GET；权限测试写"普通用户" |
| **4. 预期结果与 Schema 一致性** | 字段名、类型、枚举值对照 Apifox | 畸形 URL 预期 403 应为 404 |
| **5. 畸形 URL 路径匹配性** | 路径指向对应接口真实地址 | `/v2/storage/overview` 写成 `/v2/disk/GetOverview` |
| **6. 实际结果与预期结果自洽** | 逻辑不矛盾 | 预期 200 但实际返回 404 |

## 六、复制粘贴错误的识别与修正规则

| 错误类型 | 识别方法 | 修正方式 |
|----------|----------|----------|
| 标题含其他接口名 | 标题含"存储概览"/"获取卷列表接口"但接口地址不匹配 | 替换为当前"关联功能"列的值 |
| 接口地址版本号错误 | 下拉填充导致 v2→v3/v4 | 统一回 v2 |
| 操作步骤路径错误 | 残留上一个接口路径（如 `/v2/storage/info`） | 替换为当前接口地址 |
| 操作步骤方法错误 | Post 接口步骤写 GET | 改为与"接口请求类型"一致 |
| 前置条件术语错误 | "存储池"应为"磁盘"/"卷" | 根据接口类型替换 |
| 前置条件不完整 | Token 失效类缺少"已登录"前提 | 补充"用户已登录但 Token 已失效" |
| 缺失字段 | 所属模块/接口地址/请求类型/请求头为空 | 从上方最近的行复制 |
| 预期结果 403→404 | 畸形 URL 实际返回 404 但预期写 403 | 改为 404 |
