# 10.18.15.136 系统盘迁移失败复现指南

- 版本：2026-09-07
- 目标：复现“迁移到 HDD1 后提示系统盘迁移失败，但界面同时显示两块系统盘”
- 适用环境：优先使用专用测试 NAS 或专用测试盘
- 安全要求：不要让当前已经部分迁移的 HDD1 被再次当作干净测试盘使用

## 1. 为什么不能直接在当前机器上重复

当前 `10.18.15.136` 已经处于失败后的部分状态：

```text
md9: active raid1 sdc2[1] sdza2[0]
```

也就是说，HDD1 的 `sdc2` 已经加入了根系统 RAID，`sdc3` 仍没有加入交换 RAID。如果直接再次执行，当前状态不是“干净迁移前状态”，无法准确复现，也可能进一步改动系统 RAID。

复现必须在以下条件下进行：

```text
源系统盘：只有原 NVMe 系统盘成员
目标盘：一块准备好、无数据、未被占用的 128 GB SATA SSD
环境：专用测试 NAS，或可以整体停机恢复的测试机
```

## 2. 复现前确认环境

登录并确认设备身份和版本：

```bash
ssh -i "$HOME/.ssh/id_ed25519_codex" -p 9222 test@10.18.15.136
hostname
cat /usr/lib/version
```

确认源系统盘和 RAID 基线：

```bash
lsblk -b -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS
cat /proc/mdstat
mdadm --detail /dev/md9
mdadm --detail /dev/md8
parted -s /dev/sdza unit B print
```

基线应类似：

```text
md9: active raid1 sdza2[0]
md8: active raid1 sdza3[0]
```

目标测试盘 `/dev/sdc` 不应已有 `sdc2`、`sdc3` 的系统 RAID 签名。

## 3. 准备目标测试盘

目标盘必须是没有数据、没有 RAID 成员、没有被挂载的 SATA SSD。推荐使用和现场相同的 128 GB 型号，因为本次差异与分区对齐后的实际字节数有关。

仅对专用测试盘执行以下确认：

```bash
lsblk -b -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS /dev/sdc
blkid /dev/sdc*
```

确认输出中没有：

```text
linux_raid_member
UTOSCORE
UTOSSWAP
```

如果需要排除旧签名，仅在专用测试盘上使用：

```bash
wipefs -a /dev/sdc
parted -s /dev/sdc mklabel gpt
```

不要在当前测试 NAS 的生产系统盘上执行上述命令。

## 4. 打开正确的系统盘迁移界面

进入：

```text
存储管理
→ 磁盘
→ 系统盘
→ 迁移系统盘
```

界面中有两个选择区域：

```text
迁出表：当前已经是系统盘的磁盘
迁入表：可以作为目标系统盘的磁盘
```

操作：

1. 在迁出表中选择全部当前系统盘。
   - 示例：`NVMe Disk1`
   - 如果界面提示“系统盘仅允许设置在同一类型的磁盘上”，仍按界面要求先勾选当前所有系统盘。
2. 在迁入表中选择目标 HDD1。
3. 确认后等待迁移过程结束。

前端实际请求是：

```text
POST /v2/disk/MigrateSysDisk
```

请求体格式：

```json
{
  "src_sys_disks": ["/dev/sdza"],
  "dest_disk": "/dev/sdc"
}
```

## 5. 抓取接口证据

推荐使用浏览器开发者工具：

```text
浏览器 DevTools
→ Network
→ 过滤 MigrateSysDisk
→ 查看 Headers、Payload、Response、Status
```

需要记录：

```text
Request URL
Request Method
Request Payload
Response Status
Response Body
```

如果使用 CLI 抓包，也可以监听本机 `8181` 端口或记录浏览器 HAR 文件。

## 6. 观察 StorageManager 日志

开始迁移前开启日志监听：

```bash
journalctl -u StorageManager.service -f
```

同时持续查看：

```bash
tail -f /tmp/log/StorageManager/access.20260907.log
```

预期会看到以下顺序：

```text
mdadm --zero-superblock /dev/sdc2
mdadm --zero-superblock /dev/sdc3
parted -s /dev/sdc mkpart primary ext4 0% 300
[MigrateSysDisk]-System Migrate called
[MigrateSysDisk]-disk /dev/sdc version mismatch, rebuilding with version 32768
mdadm --manage /dev/md9 --add /dev/sdc2 --force
mdadm --manage /dev/md8 --add /dev/sdc3 --force
[MigrateSysDisk]-addSysDisk /dev/sdc faied,Err: mdadm: /dev/sdc3 not large enough to join array
[MigrateSysDisk]-MigrateSysDisk /dev/sdc faied,Err: mdadm: /dev/sdc3 not large enough to join array
systemdisk_migration_failed
```

注意：`md9` 的 `sdc2` 同步可能需要约 2 到 3 分钟，完整日志中可能会先看到 `md9 recover` 结束，再看到 `md8` 失败。

## 7. 复现后的记录模板

失败发生后，执行：

```bash
lsblk -b -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS /dev/sdza /dev/sdc /dev/md8 /dev/md9
parted -s /dev/sdza unit B print
parted -s /dev/sdc unit B print
mdadm --detail /dev/md8
mdadm --detail /dev/md9
blkid /dev/sdza1 /dev/sdza2 /dev/sdza3 /dev/sdza4 /dev/sdc1 /dev/sdc2 /dev/sdc3 /dev/md8 /dev/md9
cat /proc/mdstat
```

重点核对：

```text
旧源盘 sdza3 = 2,048,000,000 B
目标盘 sdc3  = 2,047,868,928 B
md8 要求    = 2,045,902,848 B
```

差异是：

```text
131,072 B
```

这就是 `mdadm: /dev/sdc3 not large enough to join array` 的触发条件。

## 8. 识别正确复现成功的特征

出现以下结果即可判定复现成功：

1. 系统盘通知显示 `系统盘迁移失败`。
2. 系统盘页面同时显示 `NVMe Disk1` 和 `HDD1`。
3. `/dev/md9` 的成员是 `sdza2` 和 `sdc2`。
4. `/dev/md8` 的成员仍然只有 `sdza3`。
5. `/dev/sdc3` 没有 `linux_raid_member` 文件系统类型。
6. StorageManager 日志出现 `not large enough to join array`。

## 9. 不建议的复现方式

以下方式不建议使用：

```text
在当前部分迁移的 NAS 上直接再次执行迁移
直接删除 sdza2 再执行
直接手动 mdadm --fail / --remove
在未备份的情况下重新格式化当前 HDD1
```

当前机器必须先完成明确的恢复方案后，才能作为下一次测试环境。

## 10. 后续建议

复现报告建议添加：

```text
测试设备型号、磁盘型号和序列号
TOS 版本
源系统盘分区表（前）
目标盘分区表（前）
请求接口、请求体、响应
迁移期间 mdadm/StorageManager 日志
失败后分区表、RAID 状态
是否触发同类型提示
是否符合本次缺陷特征
```

如果要用现场这台机器复现，需要先恢复 `/dev/sdc2` 的当前成员关系，并重新建立干净的基线；这属于系统盘恢复操作，应该在备份和明确授权后再执行。
