# 接口测试用例编写与执行工作流程

---

## 阶段一：API 数据导入与整理

### 1.1 从 Yapi 导出接口定义
1. 登录 Yapi 平台，进入目标项目
2. 选择「导出」→ 导出格式选择 **JSON**
3. 导出得到 `api.json` 文件，保存到本地工作目录

### 1.2 导入 Apifox
1. 打开 Apifox → 进入目标项目
2. 点击「数据导入」→ 选择数据格式 **Yapi**
3. 上传 `api.json` 文件
4. 导入目标选择 **默认模块** 下
5. 确认导入，检查接口列表是否完整

### 1.3 接口分模块整理
导入后所有接口平铺在默认模块根目录下，需按业务功能归类到文件夹：

1. **梳理接口归属**：根据接口 URL 路径和业务含义，识别所属模块
   - 如 `/api/storage/*` → 存储管理模块
   - 如 `/api/user/*` → 用户管理模块
   - 如 `/api/system/*` → 系统设置模块
2. **创建模块文件夹**：在 Apifox 中按业务功能创建目录树
3. **拖拽归类**：将接口逐一拖入对应模块文件夹
4. **标注优先级**：默认优先查看 **存储管理** 相关接口

整理后的目录结构示例：
```
默认模块
├── 登录认证
│   ├── POST /api/login（超级管理员）
│   └── POST /api/login（普通用户）
├── 存储管理
│   ├── 存储池
│   │   ├── GET    /api/storage/pools（查询列表）
│   │   ├── POST   /api/storage/pools（创建）
│   │   └── DELETE /api/storage/pools/{id}（删除）
│   ├── 卷管理
│   │   ├── GET    /api/storage/volumes（查询列表）
│   │   ├── POST   /api/storage/volumes（创建卷）
│   │   ├── PUT    /api/storage/volumes/{id}（编辑卷）
│   │   └── DELETE /api/storage/volumes/{id}（删除卷）
│   └── 共享管理
│       └── ...
├── 用户管理
│   └── ...
└── 系统设置
    └── ...
```

## 阶段二：登录认证与变量配置

### 2.1 调用登录接口
在 Apifox 中依次调试以下登录接口：

| 序号 | 操作 | 说明 |
|------|------|------|
| 1 | 超级管理员登录 | 获取管理员权限的 Cookie 和 Token |
| 2 | 普通用户登录 | 获取普通用户权限的 Cookie 和 Token |

### 2.2 提取并设置模块变量
从登录接口的响应中提取以下字段，设置为 **模块级变量**：

- `Cookie` — 会话凭证
- `X-Csrf-Token` — CSRF 防护令牌

> **注意**：不同角色（超级管理员 / 普通用户）的变量需分别保存，便于后续按角色切换测试。

## 阶段三：逐接口 AI 分析与用例设计

### 3.1 逐接口场景分析
对模块中的 **每一个接口**，使用 ChatGPT / Qoder 等 AI 工具进行分析：

**输入给 AI 的信息：**
- 接口 URL、Method、请求参数、响应结构
- 业务背景（存储管理具体功能）
- 前端校验规则（如有）
- 关联接口信息（前置/后置依赖）

**要求 AI 输出并列举以下场景：**
- 正向场景（正常参数、边界值、特殊字符等）
- 反向场景（缺参、类型错误、越权、超长度等）
- 边界场景（空值、最大值、并发、重复提交等）
- 业务逻辑场景（状态依赖、前后校验一致性等）

将 AI 输出的场景逐一整理，作为 **用例标题**。

### 3.2 关联接口与参数传递
1. **识别前置接口**：当前接口依赖哪些接口的输出
2. **提取关联参数**：从前置接口的响应中提取所需参数
   - 例：创建卷之前需先获取存储池 ID → 从「查询存储池」接口提取 `pool_id`
3. **建立参数传递链**：记录参数来源，形成接口调用链路

### 3.3 前端校验一致性检查
根据存储管理应用的功能要求（主要功能、前端校验规则等），保证前后端校验一致：

- [ ] 前端必填字段 ↔ 后端必填校验一致
- [ ] 前端输入限制（长度、范围、格式） ↔ 后端校验一致
- [ ] 前端错误提示 ↔ 后端返回错误码对应
- [ ] 前端禁用/置灰条件 ↔ 后端权限校验一致

### 3.4 重点场景专项设计

#### 高风险接口（删除卷等不可逆操作）
| 测试维度 | 用例示例 |
|----------|----------|
| 正常删除 | 删除存在的卷，验证返回成功 |
| 重复删除 | 删除已删除的卷，验证返回合理错误 |
| 依赖检查 | 删除被使用的卷，验证拒绝并提示 |
| 权限校验 | 普通用户删除卷，验证权限不足 |
| 关联影响 | 删除卷后查询列表，确认数据已清除 |
| 并发删除 | 同时发起多个删除请求，验证数据一致性 |

#### 状态依赖与顺序逻辑（如关闭后才能打开）
| 测试维度 | 用例示例 |
|----------|----------|
| 正向流程 | 关闭服务 → 再打开，验证状态切换成功 |
| 逆序操作 | 未关闭直接打开，验证拒绝并提示 |
| 重复操作 | 已关闭状态再次关闭，验证幂等或合理报错 |
| 并发切换 | 同时发送开启和关闭请求，验证最终状态一致 |
| 中间状态 | 快速连续切换，验证状态机不出现异常 |

#### 并发与竞态
- 同一资源并发修改（如同时修改卷大小）
- 同一资源并发删除
- 读写并发（查询进行中 + 删除操作）

## 阶段四：生成 Excel 测试用例文件

### 4.1 用例字段结构（15字段标准格式）
每条用例包含以下字段：

| 序号 | 字段 | 说明 |
|------|------|------|
| 1 | 用例ID | 模块缩写_功能_序号，如 `TC_STORAGE_OVERVIEW_001` |
| 2 | 所属模块 | 接口归属的业务模块/子模块，如 `概要` |
| 3 | 接口地址 | 完整的接口 URL 路径，如 `/v2/storage/overview` |
| 4 | 关联功能 | 该接口对应的业务功能描述，如 `存储概览信息获取` |
| 5 | 优先级 | P0（核心）/ P1（重要）/ P2（一般）/ P3（低频） |
| 6 | 接口请求类型 | GET / POST / PUT / DELETE |
| 7 | 请求头 | Content-Type、Cookie、X-Csrf-Token 等（引用模块变量） |
| 8 | 请求参数 | Body / Query 参数，无参数填「无」 |
| 9 | 用例标题 | 对应 AI 分析的场景描述 |
| 10 | 前置条件 | 登录状态、权限、数据依赖等 |
| 11 | 操作步骤 | 具体的请求执行步骤（编号列出） |
| 12 | 实际结果 | 执行后填入实际响应（JSON），未执行时留空 |
| 13 | 预期结果 | HTTP 状态码 + 响应结构 + 字段校验 + 业务逻辑验证 |
| 14 | 备注 | 补充说明（如特殊校验规则、已知差异等） |
| 15 | cURL | 完整的 cURL 命令（执行后填入） |

### 4.2 生成规则
1. **按模块分 Sheet**：每个模块文件夹对应一个 Sheet 页
   - Sheet 命名：`存储管理-卷管理`、`存储管理-存储池` 等
2. **逐接口填充**：将每个接口的 AI 分析场景逐条填入 Excel 行
3. **标注属性**：补充优先级、前置条件、预期结果等字段
4. **实际结果与 cURL**：执行后回填
5. **文件命名**：`接口测试用例_<模块名>_<日期>.xlsx`
   - 示例：`接口测试用例_存储管理_20260714.xlsx`

## 阶段五：浏览器录制生成测试计划文档

### 5.1 安装浏览器录制插件
在 Chrome / Edge 浏览器中安装操作录制插件（如 Selenium IDE、Katalon Recorder 等）。

### 5.2 录制全部接口操作
按模块对 **全部接口** 逐一进行浏览器端操作录制：

1. **启动录制** → 打开浏览器开始录制
2. **执行登录** → 输入账号密码 → 登录系统
3. **逐接口操作** → 按模块顺序依次执行每个接口的调用
   - 在浏览器中触发接口请求（页面操作或直接调用）
   - 观察并记录响应结果
   - 截图记录关键响应
4. **停止录制** → 导出操作记录

> 录制范围覆盖 **所有模块的全部接口**，确保测试计划文档完整。

### 5.3 生成 Word 测试计划文档
基于录制内容和 Excel 用例清单，生成正式测试计划文档：

**文档结构：**
```
测试计划文档
├── 1. 测试概述
│   ├── 测试目标
│   ├── 测试范围（本次覆盖的模块/接口）
│   └── 测试环境（NAS 型号、固件版本、浏览器版本）
├── 2. 测试策略
│   ├── 测试类型（功能、边界、权限、并发）
│   └── 工具说明（Apifox、浏览器录制插件、AI 辅助）
├── 3. 接口清单
│   └── 本次测试涉及的接口列表（按模块分组）
├── 4. 测试用例
│   └── 按模块列出所有用例（用例ID、所属模块、接口地址、关联功能、优先级、接口请求类型、请求头、请求参数、用例标题、前置条件、操作步骤、预期结果、备注）
├── 5. 重点场景说明
│   ├── 高风险操作（删除卷等）的专项策略
│   ├── 状态依赖逻辑的验证方法
│   └── 并发测试方案
├── 6. 进度安排
│   └── 各模块测试时间节点
└── 7. 风险与依赖
    └── 前置条件、环境问题、已知限制
```

**文件命名**：`测试计划_<模块名>_<版本号>_<日期>.docx`
- 示例：`测试计划_存储管理_v1.0_20260714.docx`

### 5.4 提交测试计划
1. 将 Word 测试计划文档提交至项目管理平台（禅道 / Jira / 共享文档）
2. 通知相关人员评审
3. 评审通过后进入执行阶段

## 阶段六：按计划执行测试

### 6.1 执行前准备
1. 打开已提交的 Word 测试计划文档
2. 确认测试环境就绪（NAS 固件版本、网络、账号）
3. 在 Apifox 中确认模块变量（Cookie、X-Csrf-Token）有效
4. 打开对应模块的 Excel 用例文件

### 6.2 执行顺序
```
登录（获取凭证）
  → 前置接口调用（提取依赖参数）
    → 按测试计划中的用例逐条执行
      → 后置验证（查询确认变更生效）
```

### 6.3 执行方式
1. **Apifox 手动调试**：按用例逐条执行，观察响应
2. **Apifox 自动化测试**：编排测试流程，批量执行
3. **自动化脚本**（可选）：导出为 Python/pytest 脚本持续运行

### 6.4 结果记录
在 Excel 用例文件中增加「执行结果」列：

| 状态 | 标记 | 说明 |
|------|------|------|
| 通过 | ✅ PASS | 实际结果与预期一致 |
| 失败 | ❌ FAIL | 实际结果与预期不符，提交 Bug 单 |
| 阻塞 | ⏸ BLOCKED | 前置接口/环境问题导致无法执行 |
| 跳过 | ⏭ SKIP | 需求变更或本轮不测 |

同时在 Word 测试计划文档中同步更新执行进度。

---

## 阶段七：生成测试报告与提交 Bug

### 7.1 生成测试报告
测试执行完成后，根据 Excel 用例文件和执行结果，生成正式测试报告：

**报告内容结构：**
```
测试报告
├── 1. 测试概况
│   ├── 测试模块 / 接口范围
│   ├── 测试环境（NAS 型号、固件版本）
│   ├── 测试时间
│   └── 测试工具（Apifox、浏览器录制插件、AI 辅助）
├── 2. 执行统计
│   ├── 用例总数 / 通过数 / 失败数 / 阻塞数 / 跳过数
│   ├── 通过率统计
│   └── 按模块/接口维度汇总
├── 3. 缺陷汇总
│   ├── Bug 总数（按严重程度分布）
│   ├── 致命 / 严重 / 一般 / 建议 各数量
│   └── 高频缺陷模块分析
├── 4. 失败用例明细
│   ├── 每条失败用例的实际结果 vs 预期结果
│   ├── 关联 Bug 单号
│   └── 失败原因分类（接口缺陷 / 环境问题 / 用例问题）
├── 5. 风险评估
│   └── 未覆盖场景、已知限制、遗留风险
└── 6. 结论与建议
    ├── 测试结论（通过 / 有条件通过 / 不通过）
    └── 后续建议
```

**文件命名**：`测试报告_<模块名>_<版本号>_<日期>.docx`
- 示例：`测试报告_存储管理_v1.0_20260714.docx`

### 7.2 提交 Bug
根据测试报告中的失败用例，逐一提交 Bug 单：

1. **Bug 描述规范**：
   - 标题：`[模块名][接口] 简要描述`，如 `[存储管理][删除卷] 删除使用中的卷未返回错误提示`
   - 关联用例编号
   - 接口 URL + 请求方法
   - 请求参数（完整 Body）
   - 实际响应（状态码 + Response Body）
   - 预期结果
   - 复现步骤
2. **严重程度分级**：

   | 等级 | 说明 | 示例 |
   |------|------|------|
   | 致命 | 系统崩溃、数据丢失 | 删除卷导致系统无法启动 |
   | 严重 | 核心功能不可用 | 创建卷接口返回 500 |
   | 一般 | 功能异常但有绕过方案 | 编辑卷名称不生效 |
   | 建议 | 体验优化 | 错误提示信息不够明确 |

3. **提交至项目管理平台**（禅道 / Jira），指派对应开发

---

## 阶段八：回归测试与收尾

### 8.1 回归执行
1. 开发修复后 → 按 Bug 单逐一回归执行失败用例
2. 同时执行相关影响用例，确认修复未引入新问题
3. 在 Excel 中更新执行结果：
   - 回归通过 → 标记 ✅ PASS
   - 回归未通过 → 重新打开 Bug 单，补充失败信息

### 8.2 循环回归
- 每轮修复后重复执行：回归失败用例 → 记录结果 → 更新 Bug 状态
- 直到所有用例全部通过或达成发布标准

### 8.3 测试收尾
1. 全部用例执行通过 → 更新 Word 测试计划文档的执行总结
2. 更新测试报告，补充最终通过率和缺陷闭环情况
3. 归档全部交付物：
   - Excel 测试用例文件（含执行结果）
   - Word 测试计划文档
   - Word 测试报告
   - Bug 单清单

> **持续迭代**：如后续版本有新接口或功能变更，重复阶段三至阶段八的流程。
