## 一、问题结论摘要

### 1.1 一句话结论

当前 HDD1 `/dev/sda` 的 `sda4` 仍残留并自动激活了 RAID1 阵列 `md0`，`md0` 上又保留着 LVM 卷组 `vg0`；但上层存储池配置中已无对应存储池可见记录，因此形成“前端无存储池、底层仍有 md/VG、磁盘被占用”的孤儿存储栈状态。

删除流程随后尝试停止 `md0`，但因 `Device or resource busy` 失败，`vg0` 和 `md0` 继续存在。相同问题还出现在 HDD11 `/dev/sdj` 的 `md1/vg1`。

### 1.2 已由现场命令确认

1. `/etc/installed_disk.json` 明确映射 `HDD1 -> /dev/sda`，磁盘序列号为 `1A128GE314Q00247`。
2. `/dev/sda4` 是 `linux_raid_member`，被自动组装为 `md0`。
3. `md0` 为单盘 RAID1，状态 `clean`，当前唯一成员为 `/dev/sda4`。
4. `/dev/md0` 被识别为 LVM PV，并关联到卷组 `vg0`。
5. `vg0` 中存在两个 LV：`lv0` 20 GiB、`lv1` 约 66.44 GiB，二者当前均为未激活状态。
6. `/etc/volume/volume.conf` 为 0 字节，`/etc/volume/storage.conf` 不存在。
7. `md0`、`md1` 均未挂载到 `/Volume*`，也没有显示 device-mapper holder；但 StorageManager 执行 `mdadm --stop` 时仍收到 `Device or resource busy`。
8. StorageManager 日志明确显示 HDD1 因被占用而触发可用 Pool 删除逻辑，同时提示 `vg0`、`vg1` 已存在，序号 1/2 不可用。
9. `md0/vg0` 与日志中的 Pool 标签吻合；`md1/vg1` 与另一条 Pool 日志吻合。

### 1.3 用户现场界面观察

用户反馈：开机后插入带有存储池信息的磁盘，HDD1 在前端没有被展示为存储池，但磁盘一直处于占用状态。HDD1 无法用于：

- 向其他存储池添加磁盘
- 阵列修复
- 阵列迁移
- 更换磁盘
- 创建存储池
- 创建热备盘

该项属于现场界面观察；本次 SSH 只读检查未操作前端页面，但底层空配置与残留 md/VG 的证据与该现象一致。

### 1.4 尚待确认

1. 当前日志没有直接记录“上一次创建/删除/挂载操作在哪一步被中断”，因此中断操作是已确认现象还是导致本次状态的原因，仍需按阶段复现。
2. `mdadm --stop` 返回 `Device or resource busy` 的具体占用者尚未完全定位。普通 `lsof/fuser` 未显示引用，`dmsetup` 在当前受限权限下无法取得完整结果，因此不能把某个具体进程写成已证实原因。
3. `vg0` 中 `lv1` 的标签是 Pool 2，而 `vg0` 自身标签是 Pool 1。该跨 Pool 标签是否属于正常设计或中断残留，需要 StorageManager 研发确认。

## 五、问题形成链路与影响

### 5.1 当前可确认的链路

```text
磁盘上保留 md RAID 元数据
  -> 启动或插盘后 StorageManager 自动组装 md0/md1
  -> md0/md1 上保留 LVM PV/VG 元数据
  -> pvscan 自动识别 vg0/vg1
  -> 上层已没有可在前端展示的正常存储池配置
  -> 磁盘仍被判定为 occupied
  -> 删除流程尝试停止 md
  -> mdadm --stop 返回 Device or resource busy
  -> md/VG 残留继续存在，磁盘无法释放
```

### 5.2 对业务操作的影响

HDD1 当前不可作为普通可用磁盘参与：

- 添加磁盘到其他存储池
- 阵列修复
- 阵列迁移
- 更换磁盘
- 创建存储池
- 创建热备盘

风险包括：

1. 用户无法从界面识别底层为什么被占用。
2. 创建、删除或挂载被中断后，状态无法自动收敛。
3. 如果后续操作绕过前端直接清理，可能误删仍有恢复价值的池数据。
4. 同一问题的 `md1/vg1` 也占据序号 2，扩大可用资源阻塞范围。

## 六、初步分析

### 6.1 高置信度判断

1. HDD1 被占用的直接底层对象是 `sda4 -> md0 -> vg0`。
2. 前端无池展示与 `/etc/volume/volume.conf` 为空、`storage.conf` 不存在同时出现，说明上层池记录和底层存储栈不一致。
3. 删除流程当前的实际失败点是 `mdadm --stop` 返回 busy；日志没有记录后续成功执行 VG/PV 清理。
4. `vg0` 和 `vg1` 存在会直接导致 StorageManager 报告序号 1、2 不可用。
5. `vg1` 没有任何 LV，却仍作为完整 VG 存在，具有明显的残余元数据特征。

### 6.2 需要研发确认的判断

1. `mdadm --stop` 的具体 busy 持有者。当前普通用户检查没有看到 open reference，但没有取得完整特权级 LVM/device-mapper 信息。
2. 删除顺序是否应为“卸载卷 -> 停 LV -> 停 VG -> 移除 PV/VG -> 停 md -> 清元数据”，以及当前实现是否跳过了其中一步。
3. `vg0/lv1` 使用 Pool 2 标签是否说明跨 Pool 残留，或这是产品允许的中间状态。
4. 自动导入/自动组装的边界：何时应恢复为可见存储池，何时应进入“异常残留”清理流程。

### 6.3 因果表述边界

“创建、删除或挂载操作中断导致该状态”目前是现场背景说明和合理假设，不是本次日志已经完整证明的唯一根因。要形成确定性结论，需要在每个事务阶段主动中断并保留当时的上层配置、md 元数据、VG 元数据和 StorageManager 日志。

## 八、建议修复方向

### 8.1 状态一致性与自动恢复

1. 启动和热插拔扫描时，同时检查：
   - md 阵列和成员元数据
   - LVM PV/VG/LV 标签
   - 上层存储池配置和数据库记录
   - 实际挂载点
2. 如果发现“有 md/VG，但无上层池记录”：
   - 数据可能有效时，标记为“可导入/异常存储池”，允许用户恢复。
   - 数据明确不需要时，提供显式、可审计的残留清理入口。
   - 不应静默占用磁盘，也不应只在设备页面显示“已占用”。

### 8.2 删除操作事务化与幂等

建议明确删除顺序和可恢复点：

```text
停止上层服务使用
  -> 卸载卷
  -> 停用 LV
  -> 停用 VG
  -> 删除 LV/VG/PV
  -> 停止 md
  -> 清理 md/LVM/签名元数据
  -> 刷新 udev 和存储缓存
  -> 确认磁盘重新可用于创建/修复/迁移/热备
```

每次中断后再次启动或再次删除，应能从上一步继续，而不是留下 `md0/vg0` 或 `md1/vg1`。

### 8.3 UI 和错误提示

建议至少展示：

- 磁盘被哪个 md 阵列占用
- 阵列是否关联已识别的 VG
- 是否存在上层存储池记录
- 当前删除/清理停在哪一步
- 用户可选“导入存储池”或“清理残留元数据”

### 8.4 复现与验收建议

复现矩阵至少覆盖：

1. 创建存储池过程在分区、md 创建、VG 创建、LV 创建、池配置落盘各阶段中断。
2. 删除存储池过程在卸载、LV/VG 删除、md 停止、元数据清理各阶段中断。
3. 挂载存储池过程中断后重启。
4. 中断后再次插盘、重启 StorageManager、重启 NAS。
5. 两个池同时存在时，一池残留标签出现在另一池的 VG 中。

验收标准：

1. 重启或插盘后，底层 md/LVM 与前端池状态一致。
2. 有可用数据的孤儿存储栈可被识别和导入。
3. 明确删除后不存在残留 md、VG、PV 或池标签。
4. 中断删除可幂等续跑，不出现 `Device or resource busy` 后直接终止。
5. HDD1 可重新用于添加磁盘、阵列修复、阵列迁移、更换磁盘、创建存储池和热备盘。

## 九、可直接提交的问题描述

### 9.1 建议标题

`[StorageManager][P1] 创建或删除存储池中断后 HDD1 残留 md0+vg0 元数据，前端不展示存储池且磁盘持续被占用`

### 9.2 前置条件

- TOS `TOS_X642.0_7.0.023`
- StorageManager `1.0.071`
- 系统盘中有历史池信息或数据盘的池创建/删除过程曾被中断
- HDD1 插入后底层存在 `linux_raid_member` 和 LVM PV/VG 元数据

### 9.3 实际结果

- 前端不显示对应存储池。
- `md0` 被自动组装，`vg0` 被自动识别。
- HDD1 被判定 occupied。
- `mdadm --stop /dev/md0` 返回 `Device or resource busy`。
- `vg0` 继续存在，序号 1 不可用。
- `md1/vg1` 也保留，序号 2 不可用。
- HDD1 无法用于添加磁盘、修复、迁移、换盘、创建池和热备盘。

### 9.4 期望结果

- 要么恢复并展示可导入的存储池。
- 要么在用户确认后完整清理孤儿 md/VG 元数据。
- 删除过程中断后能够自动恢复或幂等续跑。
- 磁盘状态应与前端展示一致，并在清理后恢复可用。

## 十、当前现场处置建议

1. 在研发确认前保留当前 `md0/md1`、`vg0/vg1` 现场，不建议直接删除元数据。
2. 如果盘内数据需要保留，应按“存储池导入/恢复”处理，不能按普通空闲盘格式化。
3. 如果确认数据不需要保留，应由研发在维护窗口设计完整的栈级清理流程，并验证不会误伤 `md8/md9` 系统阵列。
4. 下一次复现时同步保存：
   - 前端操作截图和请求时间
   - `/var/log/StorageManager/access.log`
   - `journalctl -u StorageManager.service -b`
   - `cat /proc/mdstat`
   - `mdadm --detail` 和 `mdadm --examine`
   - `pvs/vgs/lvs`
   - `lsblk`、`blkid`
   - `/etc/lvm/backup/vg0`、`vg1`
   - `/etc/volume/volume.conf`
