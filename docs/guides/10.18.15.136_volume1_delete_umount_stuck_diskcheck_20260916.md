- 记录日期：2026-09-16
- 记录时间：09:02-09:11 CST
- 设备：`10.18.15.136`，主机名 `TNAS`
- SSH：`test@10.18.15.136:9222`
- 内核：`6.12.63+`
- 目标卷：`Volume1`
- 卷标识：`00000001-2609-1412-0049-6cbfb5045c76`
- 存储链路：`vg0/lv0 -> /dev/mapper/vg0-lv0 -> /Volume1`
- 授权范围：只处理 `Volume1` 的卸载前置占用；卷本身由用户在前端重新执行删除

## 一、问题结论

这不是正常推进中的删除，而是删除流程卡在“卷仍被占用，无法卸载”的重复重试状态。

StorageManager 进程没有崩溃，任务线程仍活着，但业务状态不再前进。`09:03:37` 之后，系统持续每 5 秒执行一次：

```text
fuser -km /Volume1
umount /Volume1
fuser -km /Volume1
umount -f /Volume1
```

每次结果均为：

```text
umount: /Volume1: target is busy.
```

截至 `09:07:32`，相同日志仍在重复。因此应描述为“删除任务进入无限重试”，而不是立即断言为线程死锁。

## 二、时间线

| 时间 | 现象 |
| --- | --- |
| 2026-09-16 09:02:19 | StorageManager HTTP 日志记录 `Volume deleted successfully!` |
| 2026-09-16 09:02:20 | 开始执行 `stopFS: /dev/mapper/vg0-lv0` |

| 2026-09-16 09:03:37 | 首次出现 `/Volume1: target is busy`，开始每 5 秒重试 |

`09:02:19` 的 `Volume deleted successfully!` 只证明接口阶段返回了成功，不能证明底层卷已完成删除。后续日志和底层对象状态均表明删除尚未完成。

## 四、本次处理边界

计划执行：

1. 停止 `diskcheck-helper.service`。
2. 停止 `diskcheck-mail-helper.service`。
3. 确认上述进程退出。
4. 执行 `umount /Volume1`。
5. 验证 `/Volume1` 已不再挂载。

明确不执行：

- 不执行 `lvremove`、`vgremove` 或薄池删除。
- 不修改 RAID、分区、磁盘签名或 `/etc/volume/volume.conf`。
- 不替用户在前端执行卷删除。

### 5.4 结论

手动卸载 `/Volume1` 成功后，之前已经发起的删除任务在 StorageManager 恢复时被重新接管并最终完成。因此前端无需再对 `Volume1` 执行一次新的删除；卷已经不存在，应该显示为已删除或列表中不再出现。

两个 DiskCheck 服务当前为 `failed`，原因是其可执行文件原本位于已删除的 `/Volume1/@apps/diskcheck` 下。若后续重新创建 `Volume1`，应确认这两个服务是否需要重新安装或恢复应用数据。

本次人工操作未直接执行 `lvremove`、`vgremove`、RAID 停止、分区修改或磁盘签名清理。
