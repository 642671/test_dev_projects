# TOS 登录链路接口清单及各接口作用

> 文档说明：本文档整理 TOS 平台登录流程所涉及的全部接口及其在登录链路中的作用，包括初始化、凭证获取、核心登录、状态判断、敏感操作验证与登出全流程。
> 适用环境：Apifox 接口测试（测试环境 http://192.168.64.8:8181）

---

## 一、登录链路总览

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段 0：初始化准备（登录前）                                      │
│  GET /v2/Initialise/IsInitialise  →  全量变量清理（重置现场）      │
│  GET /tos/                        →  获取 X-Csrf-Token（模块变量） │
│  GET /v2/welcome                  →  提取 X-Rsa-Token → RSA_PUBLIC_KEY │
├─────────────────────────────────────────────────────────────────┤
│  阶段 1：核心登录认证                                            │
│  POST /v2/login（超管登录 / 普通用户登录）                        │
│    ├─ 前置：外部程序 RSA 加密密码                                 │
│    └─ 后置：拼接 Cookie、保存凭证变量（超管/普通用户分套隔离）      │
│  GET /v2/login/state → 判断已登录/未登录                          │
├─────────────────────────────────────────────────────────────────┤
│  阶段 2：敏感操作密码验证（登录会话内）                            │
│  POST /v2/otp/verify_pwd → 生成 X-Curpass-Token（环境变量）       │
├─────────────────────────────────────────────────────────────────┤
│  阶段 3：登出                                                   │
│  PUT /v2/logout → 备份 expired_Cookie / expired_X-Csrf-Token，   │
│                   清除 X-Csrf-Token（下次 /tos/ 重新生成）        │
└─────────────────────────────────────────────────────────────────┘
```

## 二、接口明细

### 阶段 0：初始化准备（登录前）

| # | 接口 | 方法 | 作用 |
|---|------|------|------|
| 1 | `/v2/Initialise/IsInitialise` | GET | **环境初始化/变量清理**。判断系统是否已初始化；其**前置脚本**执行全量变量清理（清空白名单之外的所有环境变量 + 全部模块变量 + 临时变量 + 集合变量），确保每次登录从干净状态开始，避免上一轮残留凭证干扰 |
| 2 | `/tos/` | GET | **获取 X-Csrf-Token**。登录页加载时调用，服务端下发 CSRF 令牌，脚本提取后**设置为模块变量**，供登录及后续请求作为 Header 携带；登出后该令牌被清除，下次进入登录页重新调用生成 |
| 3 | `/v2/welcome` | GET | **获取登录标题样式**（登录欢迎页配置）。核心用途：从**响应头 `X-Rsa-Token`** 提取 RSA 公钥，存入环境变量 `RSA_PUBLIC_KEY`，供登录密码加密使用 |

### 阶段 1：核心登录认证

| # | 接口 | 方法 | 作用 |
|---|------|------|------|
| 4a | `/v2/login`（**超管登录**） | POST | **核心用户登录接口（超管）**。前置脚本调用外部加密程序（`encoderLoginPassword.go`）对明文密码做 RSA 加密（公钥取自 `RSA_PUBLIC_KEY`），携带 `X-Csrf-Token` 头提交。后置脚本 `01_auth_login.js` 执行：① 获取登录返回的 Cookie（`TMSESSNAME`）；② 获取 `X-Csrf-Token`；③ 获取当前用户名（`tos_current_username`）；④ 自动拼接完整 Cookie（`X-Csrf-Token` + `TMSESSNAME` + `tos_current_username` + `userName` + `loginStatus=true`）；⑤ 保存到环境变量。另附带：**登出会话复用检测**（对比 `expired_Cookie`，若相同则逐段拆解定位未变成分，验证会话是否轮换）与**生成 `wrong_X-Csrf-Token`**（改第 10/30/50 位 hex 字符，供"token 不一致"负向用例） |
| 4b | `/v2/login`（**普通用户登录**） | POST | **核心用户登录接口（普通用户）**。前置脚本同上（RSA 加密）。后置脚本 `01_auth_login_normal.js`：① 获取 `NormalUser_TMSESSNAME`、`NormalUser_tos_current_username`、`X-Csrf-Token`；② 拼接完整 Cookie 存为 **`NormalUserCookie`**；③ `X-Csrf-Token` 存为 **`NormalUserCsrfToken`**（普通用户专用变量，与超管凭证隔离存放）；**无**会话复用检测与 wrong token 生成逻辑 |
| 5 | `/v2/login/state` | GET | **获取登录状态**。判断当前会话是**已登录**还是**未登录**，供前端路由守卫（未登录跳转登录页）与测试前置断言使用 |

### 阶段 2：敏感操作密码验证（登录会话内）

| # | 接口 | 方法 | 作用 |
|---|------|------|------|
| 6 | `/v2/otp/verify_pwd` | POST | **验证用户密码**。密码校验通过后生成 **`X-Curpass-Token` 变量并保存到环境变量**，供敏感操作（删除存储池/卷、磁盘安全擦除、格式化等）前的身份确认使用 |

### 阶段 3：登出

| # | 接口 | 方法 | 作用 |
|---|------|------|------|
| 7 | `/v2/logout` | PUT | **退出登录**。后置脚本 `19_logout_capture_expired.js` 执行：① 把登出前 `Cookie` 备份为 **`expired_Cookie`**（登出后会话已轮换，该凭证自然失效）；② 把登出前 `X-Csrf-Token` 备份为 **`expired_X-Csrf-Token`**（原始值备份）；③ **清除环境变量 `X-Csrf-Token`**，使下次 `/tos/` 重新生成。产出变量专供"过期凭证"负向用例使用（服务端已修复登出后 session 轮换问题，expired_* 是真正失效的凭证） |

## 三、凭证变量流转图

```
/tos/ ──────────→ X-Csrf-Token（模块变量，CSRF 令牌）
/v2/welcome ─────→ X-Rsa-Token → RSA_PUBLIC_KEY（RSA 加密公钥）
/v2/login（超管） ─→ TMSESSNAME + tos_current_username + X-Csrf-Token
                     │
                     ├─ 拼接 → Cookie（几乎所有业务接口 Header 依赖）
                     ├─ 篡改 → wrong_X-Csrf-Token（负向用例）
                     └─ 登出备份 → expired_Cookie / expired_X-Csrf-Token
/v2/login（普通用户）→ NormalUser_TMSESSNAME + NormalUser_tos_current_username
                     └─ 拼接 → NormalUserCookie + NormalUserCsrfToken（隔离存放）
/v2/otp/verify_pwd → X-Curpass-Token（敏感操作鉴权）
/v2/logout ────────→ expired_Cookie / expired_X-Csrf-Token（过期凭证备份）
                     + 清除 X-Csrf-Token（下次 /tos/ 重新生成）
```

## 四、关键凭证变量汇总

| 变量名 | 生成接口 | 提取来源 | 作用域 | 含义 | 使用方 |
|--------|----------|----------|--------|------|--------|
| `RSA_PUBLIC_KEY` | `GET /v2/welcome` | 响应头 `X-Rsa-Token` | environment | RSA 公钥，用于密码加密 | `POST /v2/login` 前置脚本 |
| `X-Csrf-Token` | `GET /tos/`（模块变量）、`POST /v2/login`（环境变量） | 服务端下发/登录后置脚本 | moduleVariables / environment | CSRF 防护令牌（登出后被清除，下次 /tos/ 重新生成） | 几乎所有需要认证的接口 Header |
| `Cookie` | `POST /v2/login`（超管） | 后置脚本拼接 | environment | 完整 Cookie 会话凭证 | 几乎所有需要认证的接口 Header |
| `NormalUserCookie` | `POST /v2/login`（普通用户） | 后置脚本拼接 | environment | 普通用户完整 Cookie 会话凭证（隔离存放） | 普通用户权限测试用例 Header |
| `NormalUserCsrfToken` | `POST /v2/login`（普通用户） | 后置脚本 | environment | 普通用户 CSRF 令牌（隔离存放） | 普通用户权限测试用例 Header |
| `wrong_X-Csrf-Token` | `POST /v2/login` | 后置脚本：改第 10/30/50 位 hex | environment | 用于"token 不一致"场景 | 负向测试用例 Header |
| `expired_Cookie` | `PUT /v2/logout` | 后置脚本：登出前 Cookie 快照 | environment | 已失效的完整 Cookie | "过期凭证"负向用例 Header |
| `expired_X-Csrf-Token` | `PUT /v2/logout` | 后置脚本：登出前 X-Csrf-Token 快照 | environment | 已失效的 CSRF 令牌原始备份 | "过期凭证"负向用例 Header |
| `X-Curpass-Token` | `POST /v2/otp/verify_pwd` | 加密脚本处理后生成 | environment | 密码验证令牌，敏感操作前身份确认 | 删除存储池/卷、安全擦除、格式化等敏感接口 |

## 五、前置脚本与后置脚本使用说明

> Apifox 中每个接口都可以挂载**前置脚本（Pre-request Script）**与**后置脚本（Post-request Script / Tests）**，分别于请求发送前、响应返回后执行。以下结合登录链路中的真实案例说明使用时机。

### 5.1 什么时候用前置脚本

前置脚本在**请求发出之前**执行，用于"准备好这次请求要发出去的东西"。适用场景：

| 场景 | 说明 | 登录链路中的案例 |
|------|------|------------------|
| 请求数据需要预处理 | 请求体/参数需要经过计算、加密、签名后才能发送 | `POST /v2/login`：前置调用外部加密程序 `encoderLoginPassword.go`，用 `RSA_PUBLIC_KEY` 对明文密码做 RSA 加密后再放入请求体 |
| 需要重置/清理状态 | 请求前把环境恢复到干净状态，避免残留数据干扰 | `GET /v2/Initialise/IsInitialise`：前置执行全量变量清理（清空环境/模块/临时/集合变量），保证每次登录从"零残留"开始 |
| 需要校验前置依赖 | 请求前检查所需凭证/数据是否已就绪，未就绪则先补齐 | 凭证类接口的前置脚本检查 `TMSESSNAME`/`X-Csrf-Token` 是否有效，缺失或为空则先触发登录获取后再继续（见 `tools/captcha_solver/apifox_pre_script.js`） |
| 需要动态生成请求头/参数 | 时间戳、随机数、非对称加密值等每次请求都不同的内容 | 携带 `X-Csrf-Token` 头的接口在请求前动态读取/组装令牌 |

**判断口诀**：请求还没发，但请求要带的东西还没准备好 → 用前置脚本。

### 5.2 什么时候用后置脚本

后置脚本在**响应返回之后**执行，用于"处理这次请求带回来的东西"。适用场景：

| 场景 | 说明 | 登录链路中的案例 |
|------|------|------------------|
| 提取响应数据存变量 | 把响应体/响应头中的关键值保存为变量，供后续接口使用 | `GET /v2/welcome`：从响应头 `X-Rsa-Token` 提取 RSA 公钥存为 `RSA_PUBLIC_KEY`；`POST /v2/login`：提取 `TMSESSNAME`、`X-Csrf-Token`、`tos_current_username` |
| 加工响应数据后再保存 | 响应数据需要拼接、转换、组合后才是有用的变量 | `POST /v2/login`：把多个凭证片段拼接成完整 `Cookie`（`X-Csrf-Token` + `TMSESSNAME` + `tos_current_username` + `userName` + `loginStatus=true`）再存入环境变量 |
| 生成派生变量 | 基于本次响应构造新的测试数据（如篡改值），供负向用例使用 | `POST /v2/login`：改第 10/30/50 位 hex 生成 `wrong_X-Csrf-Token`；`PUT /v2/logout`：登出前快照备份 `expired_Cookie`/`expired_X-Csrf-Token` |
| 清理/收尾变量 | 某个阶段结束后移除不再有效的变量，防止残留干扰 | `PUT /v2/logout`：执行 `pm.environment.unset("X-Csrf-Token")`，使下次 `/tos/` 重新生成 |
| 校验响应正确性 | 断言状态码、响应字段是否符合预期（测试通过/失败判定） | 登录成功后断言返回的会话凭证非空、登录状态接口断言 code 等 |

**判断口诀**：请求已经发完，但响应的东西还没处理（提取/保存/清理/断言）→ 用后置脚本。

### 5.3 后置脚本的变量是怎么被其他接口调用的

后置脚本产出的变量**必须写入到合适的"作用域"**，其他接口才能引用。本项目统一约定：凭证类变量写入**环境变量（environment）**，仅单次请求内使用的临时值写入模块变量。

```
① 写入：后置脚本执行 pm.environment.set("Cookie", fullCookie)
                │
                ▼
        ┌───────────────────┐
        │ 环境变量（environment） │  ← 跨接口、跨用例共享
        └───────────────────┘
                │
        ┌───────┼───────────────────┐
        ▼       ▼                   ▼
  ② 接口直接引用      ③ 前置脚本读取      ④ 其他脚本读取
  {{Cookie}}         pm.variables.get    pm.environment.get
  {{X-Csrf-Token}}   ("RSA_PUBLIC_KEY")  ("expired_Cookie")
  （URL / Header / Body 中自动替换）
```

具体调用方式：

1. **接口字段直接引用（最常用）**：在目标接口的 URL、Header、Body 中写 `{{变量名}}`，Apifox 发送请求时自动用环境变量的值替换。
   - 正常业务接口：Header 填 `Cookie: {{Cookie}}`、`X-Csrf-Token: {{X-Csrf-Token}}`，即引用了登录后置脚本拼好的凭证；
   - 普通用户权限用例：Header 填 `Cookie: {{NormalUserCookie}}`；
   - 负向用例："token 不一致"场景 Header 填 `{{wrong_X-Csrf-Token}}`，"过期凭证"场景填 `{{expired_Cookie}}` + `{{expired_X-Csrf-Token}}`；
   - 敏感操作接口：Header 填 `{{X-Curpass-Token}}`（由 `/v2/otp/verify_pwd` 后置产出）。
2. **前置脚本读取**：某接口的前置脚本中通过 `pm.variables.get("RSA_PUBLIC_KEY")` 读取 welcome 后置脚本写入的公钥，用于加密。
3. **后置脚本读取**：后置脚本之间也可互相消费，如 `19_logout_capture_expired.js` 读取 `pm.environment.get("Cookie")`（登录后置写入）做快照备份；`01_auth_login.js` 读取 `expired_Cookie` 做会话复用检测。

**关键约束**：后置脚本必须用 `pm.environment.set(...)`（环境变量）写入，`pm.variables.set(...)` 只对**当前请求**有效、其他接口读不到；用 `pm.moduleVariables.set(...)` 则只在当前模块（执行批/场景）内有效。本项目凭证统一走环境变量，正因如此登录产生的 `Cookie` 才能被成百上千个业务接口的 Header 直接 `{{Cookie}}` 引用。

## 六、注意事项

1. **登录接口双套凭证隔离**：超管登录产出 `Cookie`/`X-Csrf-Token`，普通用户登录产出 `NormalUserCookie`/`NormalUserCsrfToken`，两者互不覆盖，便于权限类用例分别引用。
2. **`PUT /v2/logout` 方法确认**：接口定义为 PUT（脚本注释中历史写法为 POST，以 Apifox 接口定义为准）。
3. **`X-Csrf-Token` 的作用域差异**：`GET /tos/` 写入的是**模块变量**；`POST /v2/login` 后置脚本写入的是**环境变量**。
4. **会话轮换已修复**：登出后 session 会轮换（TMSESSNAME 变化），`expired_Cookie` 为真正失效凭证；登录后置脚本中保留了会话复用检测逻辑，用于回归验证该修复。
5. **RSA 公钥来源**：Apifox 变量追踪中 `RSA_PUBLIC_KEY` 由 `GET /v2/welcome` 响应头 `X-Rsa-Token` 生成；部分实践（PowerShell 登录流程）中亦从 `GET /v2/Initialise/IsInitialise` 响应头提取，落地时以 Apifox 实际配置为准。
