# 架构与关键文件

## 请求链路

```text
Codex Desktop / CLI
  -> CCSwitchMulti 本地代理  http://127.0.0.1:15721/v1   (wire_api = responses)
     -> codexRouting 按模型名选择路由
        -> router-codex-official                          -> OpenAI 官方
        -> router-273341fc...(deepseek-v4-pro)            -> DeepSeek
        -> router-9c0521b9...(zai-org/GLM-5.2)            -> SiliconFlow
        -> router-28edab80...(glm-5.2/glm-5.3)            -> Zhipu GLM
        -> router-universal-codex-405dafb7...(9007)       -> 公司网关 10.18.10.140:9007 -> deepseek-v4-flash
        -> router-universal-codex-950cc769...(newapi)     -> 公司网关 10.18.2.100 -> deepseek-v4-flash
```

两个关键结论：

1. CCSwitchMulti 必须保持运行；关闭它，本地代理 `15721` 消失，Codex 所有模型（包括 GPT）都无法访问。
2. 模型选择器里显示的名字只是显示名，真正发给上游的模型名由 `upstreamModel` 或路由的 `modelMap` 决定；把带前缀的显示名直接发给远端会失败。

## 分层与配置归属

| 层 | 归属 | 关键配置 |
| --- | --- | --- |
| Codex 客户端 | 读 `config.toml`，把请求指向本地代理 | `config.toml` 的 `model_provider` / `model` / `base_url` |
| 本地代理与路由 | CCSwitchMulti 监听 `15721`，按 `codexRouting` 转发 | `cc-switch.db` 中 `codex-multirouter` 的 `settings_config.codexRouting` |
| 上游 Provider | OpenAI / DeepSeek / SiliconFlow / Zhipu GLM / Noontec 9007 / Noontec NewAPI（日志中为 `Noontec_9007` / `Noontec_NewAPI`） | `cc-switch.db` 的 `providers` 表（含认证与 Base URL） |
| 模型目录 | 同步到 Codex 侧 | `C:\Users\twm\.codex\cc-switch-model-catalog.json` |
| 网络分流 | Clash Verge 规则 | Clash Verge 的 Merge.yaml（内网直连、OpenAI 走代理） |

## 数据存放要点

- 路由与 Provider：`cc-switch.db` 中 `codex-multirouter` 的 `settings_config.codexRouting`，包含 `enabled`、`routes`、`defaultRouteId`。
- 左侧历史列表：由 `codex-dev.db` 的 `local_thread_catalog` 驱动；`state_5.sqlite` 有会话记录不代表左侧一定显示。
- 路由日志可确认事实：以 `model=... provider=... upstream_url=... status=...` 的形式逐条记录每次请求。
