# PRD 测试用例生成

工作区：`D:\test_dev_projects\office`。生成前必须完整读取 `references/tos-testcase-spec.md`，严格按用户规范执行，不得擅自改用其他模板。

## 工作流

1. 读取 `00-输入需求/{项目名}/` 下指定的 PRD 或全部 PRD。
2. 需求建模：生成 `01-需求分析/{项目名}/需求模型.json`。
3. 测试规划：生成 `01-需求分析/{项目名}/测试范围.md`。
4. 生成用例：为每个 PRD 生成 `02-测试用例/{项目名}/_cases/{序号}_{模块}.json`，字段必须符合固定 11 列格式。
5. 导出 Excel：先校验 `_cases/` 下用例 JSON 的固定 11 列契约（字段顺序、编号格式、优先级、输入/预期条数一致、验证结果默认“未执行”、bug 列默认留空），通过后再运行 `scripts/build_excel.py` 生成单模块 xlsx 和合并后的 `测试用例.xlsx`。
6. 评审：生成 `02-测试用例/{项目名}/评审/评审记录.md`，输出场景覆盖矩阵。
7. 汇报：给出输出文件路径、用例总数，并用 `open_in_codex` 打开 Excel 成品。

## 路径规则

| 内容 | 路径 |
| --- | --- |
| PRD 输入 | `00-输入需求/{项目名}/NN_模块_PRD.md` |
| 需求模型 | `01-需求分析/{项目名}/需求模型.json` |
| 测试计划 | `01-需求分析/{项目名}/测试范围.md` |
| 用例 JSON | `02-测试用例/{项目名}/_cases/NN_模块.json` |
| 单模块 Excel | `02-测试用例/{项目名}/NN_模块.xlsx` |
| 合并 Excel | `02-测试用例/{项目名}/测试用例.xlsx` |
| 评审记录 | `02-测试用例/{项目名}/评审/评审记录.md` |

除非用户明确要求，不要修改 `00-输入需求/` 下的原文件。

## 固定测试用例格式

字段名称和顺序固定为 11 列，不得修改：

```text
编号	模块	用例名称	优先级	前置条件	操作步骤	输入数据	预期结果	验证结果	备注	bug
```

- `验证结果` 生成阶段默认填 `未执行`，不得自行填 `通过`。
- `备注` 无额外说明时填 `-`。
- `bug` 列生成阶段留空，由测试人员手工填写；更新或重排已有用例时，该列已有内容必须保留，不得清空。
- `编号` 使用 `模块缩写-子模块缩写-三位序号`，例如 `STO-DISK-001`。
- `模块` 使用 `一级模块-二级模块`，例如 `存储管理-磁盘`，同一批用例粒度一致。
- `优先级` 只允许 `P0`、`P1`、`P2`。
- `用例名称` 必须体现“测试对象 + 测试功能 + 测试场景”，推荐 `功能-场景`，例如 `磁盘管理-插入磁盘正常识别`。
- `前置条件` 只保留当前用例真正依赖的状态，尽量精简为 1-3 条；登录、设备正常、页面可打开等通用项合并为一条，不重复堆叠。
- `操作步骤` 只写测试人员实际执行的动作，不包含预期结果和判断语句。
- `操作步骤` 不要单独写“打开存储管理”这类已由前置条件隐含的导航步骤；进入具体页面合并为一步，例如“进入存储管理-磁盘页面”。
- `预期结果` 必须明确、可观察、可验证，禁止只写“正常”“成功”“符合预期”。
- `输入数据` 必须可复现，禁止使用“测试磁盘”“测试数据”“正常参数”这类模糊描述；需求未定义时使用具体示例值，并在备注注明“示例值，执行时可根据实际测试环境替换”，不得只写“以实际测试环境为准”。
- `输入数据` 只写与场景直接相关的数据；插拔类场景填写“测试磁盘：1块”即可，不需要型号、接口、容量，也不写“支持热插拔”，除非这些参数影响测试结果。
- `输入数据` 与 `预期结果` 必须一一对应：每条输入数据都有同一条编号对应的预期结果，禁止输入只有 1 条、预期结果却有 4-5 条。

## 多行字段换行规则

`前置条件`、`操作步骤`、`输入数据`、`预期结果` 中的每个编号项必须独立成行，使用换行符分隔。

- JSON 中使用字符串数组，例如 `["1. 打开存储管理；", "2. 进入磁盘页面；"]`。
- JSON 也可以使用含 `\n` 的字符串，但禁止用 `；` 把所有编号挤在同一行。
- Excel 单元格必须启用自动换行，保证每条编号显示在独立行。
- 生成文本预览时，字段之间使用 Tab 分隔，多行字段内部使用换行。

## Excel 样式规范

导出脚本 `scripts/build_excel.py` 统一应用以下样式，生成后不得再手工改动样式：

- 表头行（第一行）：行高固定 30；加粗、字号 12（正文为 11）；灰色填充（Excel 内置“白色，背景1，深色15%”，theme=0 / tint=-0.15，约 `#D9D9D9`）；水平居中、垂直居中。
- 数据行：行高不固定，打开后按内容自动适配；自动换行、垂直居中；`优先级`、`验证结果` 列水平居中，其余列水平左对齐。
- 框线：整个表格（表头 + 数据）所有单元格加细框线，包括留空的 bug 列。
- 列宽：脚本按单元格实际内容自动计算（中文按 2 个字符宽度计），并对每列设置上限，保证长文本合理换行、表格不过宽。
- `验证结果` 列（I 列）带下拉选项：`通过` / `失败` / `阻塞` / `未执行`，执行时点选填写；按取值自动着色（字体颜色，条件格式）：`通过` 绿色、`失败` 红色、`阻塞` 黄色（琥珀色保证白底可读）、`未执行` 灰色。
- 冻结首行（`A2`），滚动查看时表头始终可见。

样式规则以 `build_excel.py` 的实现为唯一权威来源，修改样式必须同步修改脚本。

## 用例 JSON 格式

`_cases/` 下每个 JSON 文件都是一个数组，元素字段与 Excel 列完全一致：

`编号`、`模块`、`用例名称`、`优先级`、`前置条件`、`操作步骤`、`输入数据`、`预期结果`、`验证结果`、`备注`、`bug`

示例：

```json
[
  {
    "编号": "STO-DISK-001",
    "模块": "存储管理-磁盘",
    "用例名称": "磁盘管理-插入磁盘正常识别",
    "优先级": "P0",
    "前置条件": [
      "1. 已使用管理员账号登录TOS，存储管理可正常打开；",
      "2. 已准备1块测试磁盘。"
    ],
    "操作步骤": [
      "1. 进入存储管理-磁盘页面；",
      "2. 插入磁盘；",
      "3. 刷新磁盘列表。"
    ],
    "输入数据": [
      "1. 测试磁盘：1块。",
      "2. 操作：插入磁盘。",
      "3. 页面：磁盘列表、存储池、卷。"
    ],
    "预期结果": [
      "1. 磁盘列表显示新增的1块磁盘。",
      "2. 插入后磁盘接口正常返回，页面不长期Loading。",
      "3. 存储池和卷页面均可正常打开。"
    ],
    "验证结果": "未执行",
    "备注": "-",
    "bug": ""
  }
]
```

## 场景与质量

生成前按 `references/tos-testcase-spec.md` 的 11 个功能测试场景维度分析：

1. 主流程
2. 默认状态
3. UI场景
4. 输入校验
5. 异常场景
6. 权限场景
7. 重复操作
8. 中断恢复
9. 状态场景
10. 数据持久化
11. 功能联动

存储管理类需求必须考虑 UI、API、Linux 后台、数据一致性四层验证。需求未明确的信息写“以需求/技术方案为准”或“需要产品确认”，不得编造。评审记录必须输出“功能点 x 场景”覆盖矩阵。

## 导出脚本

从工作区根目录 `D:\test_dev_projects` 运行：

```powershell
py -3 .agents\skills\generate-prd-testcases\scripts\build_excel.py `
  --project 存储管理 `
  --cases-dir office\02-测试用例\存储管理\_cases `
  --output-dir office\02-测试用例\存储管理
```

脚本会为每个 JSON 生成同名 xlsx，并合并生成 `测试用例.xlsx`。

操作注意事项（本机实测）：

- 本机 `python` 是 Microsoft Store 占位符，必须使用 `py -3` 运行脚本。
- 中文输出乱码时，先执行 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` 并设置 `$env:PYTHONIOENCODING='utf-8'`。
- 导出前先校验 `_cases/` 下 JSON 的固定 11 列契约（bug 列可缺省，导出时留空），通过后再导出。
- 数据行不要手工设置固定行高，打开后由 Excel/WPS 按换行内容自动适配；只有表头行高固定 30。
