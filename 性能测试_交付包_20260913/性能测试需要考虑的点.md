# 性能测试需要考虑的点

> 本文档是 `性能测试` skill 的配套说明，供测试工程师在写 **TOS 系统功能**和**应用**的性能测试时对照使用。
> 内容来源两部分：**两份性能测试入门材料**（指标口径与方法论）+ **本次实测**（真实踩过的坑）。
> 不是理论罗列，每条都能直接照做。

---

## 〇、一句话总纲

**性能测试 = 提出问题（设定目标）→ 施加压力（执行测试）→ 分析证据（监控指标）→ 定位真相（找到瓶颈）。**

四个环节缺一不可，是一个**闭环**。
**最常见的失败不是测不出来，而是测出来了但解读错了** —— 所以第四章「口径与陷阱」比前三章更重要。

---

## 〇·三、🚩 评审红线（**硬性规则，先看这条**）

> **与参考阈值性质不同**：红线是**硬性**的，超了就要讨论评估；
> 参考阈值是**业界参考**，各项目组结合自身业务**具体讨论定夺**。

| 红线 | 判定口径 | 超了怎么办 |
|---|---|---|
| **单个进程的内存峰值 > 1 GB** | **`private_Dirty`（真实匿名内存）** | **需团队讨论评估** —— 不是「达标/不达标」的二元判定，而是要坐下来评估合不合理 |

### ⚠️ 判定口径必须是 `private_Dirty`，不能用 RSS

| 实测案例 | RSS 峰值 | **private_Dirty 峰值** | 用 RSS 判 | 用 private_Dirty 判 |
|---|---|---|---|---|
| qBittorrent 做种 | **5918 MB** | **140 MB** | ❌ 误报「超 1GB」 | ✅ 正常 |
| Emby 4 路转码 | 612 MB | ~333 MB | ✅ | ✅ |
| MultimediaServer 空载 | 48 MB | 8.4 MB | ✅ | ✅ |

**RSS 含 `RssFile`（mmap 文件页缓存，内核随时可回收）** —— 用它判会把页缓存当成真实占用，**全线误报**。

### 报告里怎么体现

判为 **`! 待确认`**（不是 `✗ 不通过`）—— 语义是「**需要讨论**」而非「不合格」，会进报告的「待确认」清单。

## 一、先搞清楚：性能测试是什么、为什么要做

### 1.1 四个本质维度

| 维度 | 含义 | 我们怎么测 |
|---|---|---|
| **速度** | 系统处理请求和返回响应的**速率** | 响应时间、TPS/QPS、任务耗时 |
| **稳定性** | 系统在负载下**无崩溃、无异常运行**的能力 | 长稳（8~24h）、错误率、内存是否爬升 |
| **可扩展性** | 负载**平滑增加**时，处理能力能否随之线性或有效增长 | 阶梯并发，看拐点 |
| **响应能力** | 系统对用户指令或外部刺激的**反馈速度** | 响应时间、前端 FCP/LCP/FID |

### 1.2 它不是单一测试，而是一系列测试类型的总称

| 类型 | 做什么 | 用在什么时候 |
|---|---|---|
| **负载测试** | 逐步加压到预期负载，看系统是否达标 | 验证「能不能扛住预期用户量」 |
| **压力测试** | 加到**极限甚至超出**，看何时崩溃、如何降级 | 找崩溃极限与恢复能力 |
| **耐久性测试**（稳定性测试） | **标准压力长时间运行**（8~24 小时） | 查内存泄漏、性能衰减 |
| **容量测试 / 容量规划** | 确定满足指标下能承受的**最大用户数** | 服务器选型、资源配置 |
| **并发测试** | 多用户/多任务同时操作 | 验证并发场景下的正确性与性能 |

> **别把「负载测试」和「压力测试」搞混**：前者验证达标，后者找极限。报告里要写清做的是哪种。

### 1.3 为什么要做（说服人的五条）

1. **保障用户体验与声誉** —— 缓慢、卡顿、崩溃直接导致用户流失
2. **验证系统能力与规划容量** —— 回答「能否支撑预期用户量」「促销期间能否扛住洪峰」，
   为**服务器选型与资源配置**提供数据，避免过度配置浪费或配置不足中断
3. **识别瓶颈、驱动优化** —— 暴露代码效率、数据库查询、网络延迟、资源配置的潜在问题，
   给开发明确的优化方向
4. **确保业务连续性与可靠性** —— 极限负载或长时间运行后是否泄漏、是否性能衰减、故障能否恢复
5. **满足合规、降低风险** —— 上线前预测问题，降低性能故障导致的业务损失与修复成本

## 二、入门五步法（照这个顺序做）

| 步 | 做什么 | 关键要求 |
|---|---|---|
| **1. 学习使用工具** | 至少掌握一种主流工具（JMeter / LoadRunner / k6 / Locust；apifox、PTS 平台也可） | **先懂性能测试，再学工具** —— 会用 JMeter ≠ 会做性能测试 |
| **2. 明确测试场景** | 想清楚要测**什么功能**（如文件上传、媒体转码、用户登录） | 场景不清 = 测了个寂寞 |
| **3. 定义具体指标** | 为场景设定**明确的、可衡量的**目标 | ⭐ 见下方「可衡量目标长什么样」 |
| **4. 执行与监控** | 运行测试，**完整记录所有指标数据** | 数据要能复核：保留原始 CSV/JSON |
| **5. 撰写分析报告** | 测试概况 + 结果对比 + 瓶颈分析 + 优化建议 | 见第八章 |

### ⭐ 可衡量目标长什么样

| ❌ 不可衡量 | ✅ 可衡量 |
|---|---|
| 「系统要快」 | 「**100 用户并发时，登录请求的 95% 响应时间 < 1 秒，错误率 = 0%**」 |
| 「上传不能太慢」 | 「**单文件 2 GB 上传耗时 ≤ 60 秒，期间 CPU ≤ 70%**」 |
| 「支持多人播放」 | 「**50 路 1080p 并发播放，每路不卡顿（无缓冲中断），服务端 CPU ≤ 70%**」 |

**目标来源三条路**（没有业务需求时按这个找）：

1. **业务需求** —— PM/产品要求（如「核心页面响应时间不超过 2 秒」）
2. **行业参考** —— 如 Google 建议页面加载 ≤3 秒
3. **竞品分析** —— 了解对手表现，作为追赶目标

## 三、测试前：必须想清楚的 8 件事

| # | 要想清楚 | 具体问自己 |
|---|---|---|
| 1 | **测什么** | 是「系统功能」（如文件上传、备份、快照）还是「安装的应用」（如多媒体服务器、网盘）？<br>→ 决定了盯哪个进程，查 `references/tos-feature-process-map.md` |
| 2 | **做哪种测试** | 负载 / 压力 / 耐久 / 容量 / 并发？（见 1.2）**别把负载测试当压力测试写进报告** |
| 3 | **性能目标** | 从哪来？业务需求／行业参考／竞品分析。**没有目标就没有「通过」** |
| 4 | **关注哪些指标** | 功能类看 **CPU/内存/磁盘/响应时间**；应用类还要看 **进程树资源 + 空载基线 + 泄漏**；接口类才看 **TPS/P95/错误率** |
| 5 | **场景是什么** | 空载？单任务？多任务并发？长稳？**至少覆盖「空载 → 单任务 → 并发」三档** |
| 6 | **负载怎么造** | 谁来触发？触发多少次？**并发几路**？单路速率多少？ |
| 7 | **跑多久** | **5 分钟抓峰值型上限；30 分钟以上才暴露慢变量（内存增长）**。两者不可互替 |
| 8 | **和谁比** | 有没有基线？（未安装态 / 安装后空载 / 上一版本）**没有基线就没有「放大多少」** |
| 9 | **合不合格谁说了算** | 阈值从哪来？**默认参考值 ≠ 业务验收标准**，报告里必须写明来源 |

## 四、测试中：采集的 6 条铁律

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **必须按进程树统计**（父 + 全部子孙） | 转码在 `ffmpeg` 子进程里、fork-per-connection 服务的内存长在子进程上。**只盯主进程实测漏掉过 77% 的开销** |
| 2 | **内存判压力用 `private_Dirty` / `PSS`，不要用 `RSS`** | RSS 含 `RssFile`（页缓存，内核可回收）。实测某应用 RSS 5918 MB 里 **97.6% 是页缓存**，真实匿名仅 140 MB |
| 3 | **网络是整机口径** | Linux 没有逐进程网络计数（`/proc/<pid>/net/dev` 属于整个 netns）。**不可归因单应用**，报告里必须声明 |
| 4 | **CPU 声明单核口径** | 100% = 1 个核，4 核跑满 = 400%。不声明则跨报告不可比 |
| 5 | **峰值必须带发生时刻** | 否则会把一次性尖峰（如转码收尾落盘 543 MB/s）误读成持续压力 |
| 6 | **采不到的指标不许填 0** | 采不到 ≠ 达标。要标 `❌未采集` / `⚠️口径降级` 并写清原因，报告固定带「采集覆盖度」章节 |

## 五、高频陷阱（实测踩过的，逐条都是真事）

### 5.1 监控对象类

| 坑 | 现象 | 对策 |
|---|---|---|
| **后台任务跑在独立服务里** | 测「多媒体服务器媒体索引」，只盯 `MultimediaServer` → **索引负载全程漏采** | 真正干活的是 `mediaindex`（独立 systemd 服务，PPID=1）。**测前先 diff 进程清单**：<br>`ps -eo comm \| sort -u > a`；触发任务后 `> b`；`comm -13 a b` 看新增了谁 |
| **`comm` 被截断到 15 字符** | `ResourceCollection` 显示为 `ResourceCollect`，按全名匹配不到 | 用 `--app` 正则 + 让脚本递归收子孙；别用 `--pid` 指主进程 |
| **worker 型进程漏采** | nginx 多 worker、postgres 每连接一个后端 | 同上，按进程树 + 名字正则 |
| **采集器匹配到自己** | `--app MultimediaServer` 把采集器自身也算进被测进程树（+1 进程、+12 MB） | 采集脚本要**排除自身**（本 skill 已修） |

### 5.2 数据解读类

| 坑 | 现象 | 对策 |
|---|---|---|
| **均值被窗口构成污染** | 5 分钟窗口空载占 6.6%、30 分钟只占 1.9%，假造出「+7.2% 长时退化」 | 比较不同时长前**先对齐负载占比**，或改用**稳态时段口径** |
| **页缓存虚高 RSS** | 见第四章铁律 2 | 拆 `RssAnon` / `RssFile` / `private_Dirty` 三件套 |
| **swap 换出 ≠ 内存压力** | 某应用 155 MB swap，但 PSS 仅 30 MB、CPU 0.01% | 那是「深度空闲」（页面长期未被访问），**不是压力** |
| **空闲期内存不归零是正常的** | 任务停了还留 62~335 MB | 判据不是「是否归零」，而是「**有无单调爬升**」 |
| **小文件全速拉取的合计速度虚高** | 客户端报「合计 555 MB/s」（≈4.4 Gbps），单条千兆不可能 | 那是**各路平均速度相加**且小文件瞬间读完。**并发吞吐必须以服务端实测为准** |

### 5.3 测试方法类

| 坑 | 现象 | 对策 |
|---|---|---|
| **重复测试命中缓存** | 第二次读同一批素材，读峰值从 184 降到 35.7 MB/s，看着像「性能提升」 | 那是 page cache 命中。**对比前先确认缓存状态一致** |
| **应用自身缓存跳过真实负载** | 转码应用缓存产物，相同请求直接命中缓存、**根本不起 ffmpeg** | 清应用缓存目录 + **保证每路请求参数唯一** |
| **并发台数 ≠ 容量指标** | 4 路全转码占 2.8 核，13 路混合只占 0.9 核 | 差异在**素材能否硬件解码**。报告要写清负载的编码格式 |
| **启动错峰导致并发数不足** | 逐条错峰 0.25s 启动 80 条，前面的读完后面的才起来 → 实际并发远低于 80 | 声称的并发数要用**服务端进程树**核对，别只信客户端数字 |
| **实时侦测脚本自身会瞎** | 盯的数据源被换了（采集器重启换了文件名）、判定字段方向搞反（推流看 rx 不看 tx） | **连续采集 + 事后按时间戳切分**，永远比实时侦测可靠 |
| **把带宽当容量上限** | 实测某应用「按带宽算能撑 79 路」，但真实上限是应用的并发连接数（约 50 路） | **容量要按实测的绑定约束算**，别只做一个维度的除法 |

## 六、不同测试对象的关注点

| 对象 | 必测场景 | 关键指标 | 特有坑 |
|---|---|---|---|
| **TOS 系统功能**<br>（上传下载、备份、快照、同步） | 空载 → 单任务 → 多任务并发 | 进程树 CPU / 内存 / 磁盘读写 / 网络；任务耗时 | 功能常由**独立服务**承载（不在主进程树）；大文件要防缓存命中 |
| **安装的应用**<br>（多媒体、网盘、虚拟机） | **未安装 → 安装 → 空载 → 负载 → 泄漏 → 卸载**六阶段 | 安装后**默认占用**、放大倍数、内存增长 | 安装/卸载**必须人工触发**；启动应用可能**重启关联服务**导致基线重置 |
| **接口 / 服务** | 单接口基线 → 阶梯并发 → 长稳 | TPS/QPS、P95/P99、错误率、服务端资源 | 拐点 = 最佳并发点；错误率任何非零都要查 |
| **Web 页面** | 首屏、交互、并发访问 | FCP/LCP/FID/CLS + 服务端资源 | 前端指标与后端资源要**关联看** |

## 七、结果怎么分析（四步 + 决策树）

### 7.1 标准四步

| 步 | 做什么 |
|---|---|
| **a. 对照阈值** | 实际指标 vs 参考阈值或项目预定目标，判断是否达标 |
| **b. 观察趋势与拐点** | 画「响应时间-并发」「吞吐量-并发」曲线，**关注拐点**（性能开始显著下降的点） |
| **c. 关联分析瓶颈** | 指标不达标时，结合**资源指标**（CPU/内存/IO/数据库）+ **中间件指标**（连接数/慢查询/GC）定位根因 |
| **d. 关注稳定性** | 长稳中看 TPS 曲线是否平稳、错误率是否可控、**内存是否有持续增长趋势** |

### 7.2 两条核心规律

- **吞吐量与响应时间的权衡**：资源未饱和前，吞吐量随并发上升、响应时间变化不大；
  **达到瓶颈后吞吐量趋平甚至下降，响应时间急剧上升** —— **这个拐点就是最佳并发点**
- **资源指标是瓶颈的指向标**：响应时间变长或吞吐量上不去时，看资源——
  **CPU 持续 >80% 且 `%iowait` 很低 → CPU 计算能力不足**；**`%iowait` 很高 → 磁盘 I/O 瓶颈**

### 7.3 排查决策树（像侦探一样按线索查）

**线索 A：响应时间变长，同时 TPS/QPS 上不去甚至下降** → 立即看服务端资源监控图：

| 观察到 | 结论 |
|---|---|
| CPU 使用率**持续高于 80%** | 服务器计算能力已达瓶颈 → 代码优化或加 CPU |
| 内存使用率**不断增长且不释放** | 可能存在内存泄漏 → 检查代码 |
| **磁盘 I/O 等待时间很长** | 数据库或文件读写瓶颈 → 优化查询或用更快存储 |
| 网络**贴住线速** | 网卡瓶颈 → 上万兆/链路聚合 |

**线索 B：响应时间变长，但 TPS/QPS 平稳，资源利用率也不高**
→ 瓶颈在**应用逻辑、数据库查询效率或外部服务依赖**：查慢 SQL、第三方接口响应慢

> 更完整的决策树见 `性能测试skill/references/analysis-playbook.md`

### 7.3 瓶颈分析流程图（**带具体阈值，照这个走**）

> 入口是「**先看响应时间是否超标**」，再用吞吐量分大类，最后匹配资源阈值。

```
开始分析测试结果
      │
      ▼
判断：响应时间是否超过阈值？
      │
      ├─ 否 ──► 响应时间达标 ──► 结合其他指标评估是否通过测试
      │
      └─ 是 ──► 判断：对应时间的系统吞吐量如何？
                    │
                    ├─ 分支 A：TPS / QPS 显著下降
                    │        └─► 资源利用率分析 ──► 哪个资源达到瓶颈？
                    │              ├─ CPU 使用率 > 75~80%       ──► CPU 瓶颈：计算能力不足
                    │              ├─ 内存异常高或持续增长      ──► 内存瓶颈：可能存在泄漏
                    │              ├─ 磁盘 I/O 繁忙率 > 70%     ──► 磁盘瓶颈：读写速度慢
                    │              └─ 网络吞吐接近带宽上限      ──► 网络瓶颈：带宽不足
                    │            ──► 制定优化方案 ──► 结合其他指标评估是否通过测试
                    │
                    └─ 分支 B：TPS / QPS 保持高位
                             └─► 可能为应用逻辑或数据库瓶颈
                                 ──► 制定优化方案 ──► 结合其他指标评估是否通过测试
```

**四个资源阈值（记下来，比笼统的「看资源」有用）**

| 资源 | 判定瓶颈的阈值 |
|---|---|
| **CPU** | 使用率 **> 75~80%** → 计算能力不足 |
| **内存** | 使用率**异常高或持续增长** → 可能存在泄漏 |
| **磁盘 I/O** | **繁忙率 > 70%** → 读写速度慢 |
| **网络** | 吞吐量**接近带宽上限** → 带宽不足 |

> ⚠️ **两套阈值不要混**：本表是**瓶颈判定**（磁盘 >70% 就该怀疑）；
> `references/metrics.md` 里的 `%util ≤80%` 是**达标线**。
> **70% 是预警线，80% 是不合格线** —— 报告里说「逼近瓶颈」用 70%，说「不达标」用 80%。

### 7.4 方法总结（一次完整性能测试做了什么）

1. **压力测试** —— 用 JMeter 对目标接口执行
   **3000 并发、持续 30 分钟**的压测，采集 QPS、响应时间、错误率、**分位响应时间**（P90/P95/P99）
2. **资源监控** —— 实时采集 **CPU、内存、网络、磁盘 IO**，观察资源水位与性能趋势
3. **瓶颈定位分析方法**：
   1. 先判断**响应时间是否超标**
   2. 结合 **吞吐量 TPS/QPS 分大类**：
      **吞吐量下降 → 优先查服务器硬件资源**；**吞吐量高但延迟高 → 优先查业务代码、数据库**
   3. **资源判断**：CPU / 内存 / 磁盘 IO / 网络，**匹配阈值**定位资源瓶颈类型
   4. 输出优化方案，**综合多指标**评估测试是否通过

### 7.5 核心性能指标速览（**表 1，原文**）

| 指标类别 | 关键指标 | 简要说明 |
|---|---|---|
| **用户感知指标** | **响应时间 (RT)** | 用户从发起请求到接收到**完整响应所花费的总时间**。通常关注**平均响应时间**、**P90/P95**（90%/95% 的请求**快于**该值） |
| | **错误率 (Error Rate)** | 失败请求数占**总请求数**的百分比。**理想情况下应接近 0%** |
| **系统处理能力指标** | **TPS**（每秒事务数） | 系统每秒成功处理的**完整业务流程（事务）数量** |
| | **QPS**（每秒查询数） | 系统每秒处理的请求或查询数量，**通常用于衡量接口类能力** |
| | **并发用户数** | 在同一时刻与系统进行交互的用户数量，**用于模拟真实负载** |
| **资源消耗指标** | **CPU 使用率** | 服务器 CPU 的繁忙程度。**业界警戒值通常为 75% ~ 80%** |
| | **内存使用率** | 系统内存的消耗情况，**需警惕持续增长**（可能存在内存泄漏） |
| | **磁盘 I/O** | 磁盘的读写速率和繁忙程度。**磁盘繁忙率通常建议低于 70%** |
| | **网络吞吐量** | 单位时间内网络传输的数据量，**需关注是否接近带宽上限** |

> ⚠️ **两套阈值口径别混用**：
> - **表 1（本表）给「警戒值」** —— CPU **75%~80%**、磁盘繁忙率 **<70%**、错误率 **趋近 0%**、网络**不接近带宽上限**
> - **表 2（`metrics.md` 的达标线）给「达标线」** —— CPU **≤70%**、`%util` **≤80%**、`%iowait` **≤20%-30%**、错误率 **≤0.2%**
>
> **说「逼近瓶颈」用表 1，说「不达标」用表 2。**

### 7.6 关键指标汇总表（**表 2，原文**）

| 指标类别 | 具体指标 | 含义与说明 | 参考阈值（良好 / 通过标准） |
|---|---|---|---|
| **系统处理能力** | 响应时间 (RT) | 从发起请求到接收完整响应经过的时间。关注平均与 **90% 响应时间** | 视业务而定。**核心操作 ≤200ms**；**普通页面加载 ≤3 秒**；**只读查询 ≤10ms** |
| | 吞吐量 | 单位时间处理的请求数量或数据量，用 TPS / QPS 衡量 | 无固定值。**目标并发下 TPS 曲线应保持平稳** |
| | 并发用户数 | 同时与系统交互的用户数量 | 需测试得出**最大并发数**；**在线用户数的 8%~12%** 可作估算 |
| **资源利用率** | CPU 使用率 | CPU 用于处理请求的时间占比 | 应用/DB **≤70%**；**70% 好 / 85% 坏 / 90%+ 很差**；`%us`、`%sy` 分别关注 |
| | 内存使用率 | 物理内存或 JVM 堆使用比例 | 系统 **≤70%** 且无页交换；**JVM 堆 ≤70%** |
| | 磁盘 I/O | `%util`、`await`、IOPS | `%util` **≤80%**（**<30% 为「好」**）；`%iowait` **≤20%-30%**，**>40% 可能成瓶颈** |
| | 网络带宽使用率 | 流量占可用带宽比例 | **≤30%**，且**无丢包、延迟和阻塞** |
| **中间件/数据库** | 数据库连接数 | 活跃连接占最大连接的比例 | **(当前/最大)×100% ≤ 85%** |
| | 慢查询 | 执行时间过长的 SQL | **不应出现** |
| | 死锁 | 线程/进程争抢资源互相等待 | **不应出现** |
| | GC 频率与时长 | 尤其 Full GC，频繁或耗时会暂停应用 | **不应过于频繁（如大于平均半小时 1 次）**；时长应足够短，**压测中不应因 FGC 导致响应时间急剧升高** |
| **稳定性与错误** | 错误率 | 失败请求占总请求的比例 | 压测失败率 **≤0.2%** |
| | 系统负载 Load Average | 运行+等待状态的进程平均数 | **≤ CPU核数 × 0.7**；更宽松 **< 核数 × 2** |
| | 稳定性时长 | 标准压力下能稳定运行的最短时间 | **8 小时系统 ≥8h**；**7×24 系统 ≥24h** |

## 九、稳定性的具体口径

PDF 里给了一个可操作的基准，值得直接采用：

> **标准压力 = 日常压力的 80%；长时间 = 8~24 小时。**

关注三件事：

| 关注点 | 判据 |
|---|---|
| **性能曲线** | TPS 和响应时间是否平稳，有无大幅波动 |
| **资源泄漏** | 内存是否持续缓慢增长（最终可能导致 `OutOfMemoryError`） |
| **错误率** | **任何非零错误率都要分析原因**：超时 / 连接拒绝 / 代码异常 |
