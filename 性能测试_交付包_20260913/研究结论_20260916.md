## 2. 这是什么

这是一个 2026-09-13 生成的性能测试参考交付包，包含：

- 一份性能测试方法论和实操清单；
- 一套“性能测试”技能目录，含 8 个子技能、7 个 Python 脚本、参考资料和报告模板；
- MultimediaServer 3.2.106 的示例性能测试报告；
- 对应的 CSV/JSON 原始数据和统计结果。

当前共 60 个文件，约 2.60 MB，包括 28 个 Markdown、6 个 HTML、7 个 Python、5 个 CSV 和 13 个 JSON 文件。

它的测试对象是 MultimediaServer，不是 StorageManager。其框架可以借鉴，但示例结论不能直接当作 StorageManager 的结论。

## 3. 值得复用的部分

1. 使用进程树而非单 PID，能够覆盖 worker、fork 子进程和独立任务进程。
2. 将 PSS、RSS、`private_Dirty`、RssAnon、RssFile 分开，避免把页缓存误判成泄漏。
3. 按“未安装、安装、空载、负载、泄漏、卸载”组织应用生命周期。
4. 保留 CSV/JSON 原始数据，报告给出峰值、均值、P95、P99、峰值时刻和覆盖度。
5. 明确区分参考阈值和业务验收标准，并记录未采集指标和口径降级。
6. 报告模板为 Markdown 和自包含 HTML，适合离线查看和缺陷附件。

## 4. 已复核的数据结论

对 `P4_app_fixed.csv` 的 2026-09-13 15:34:15～16:22:35 区间重新计算：

- 样本数：2875；
- 首四分之一 `private_Dirty` 均值：6.1855 MB；
- 末四分之一 `private_Dirty` 均值：3.9400 MB；
- 净变化：−2.2455 MB；
- 相邻样本递增比例：0.0177。

因此，“该约 48 分钟窗口未出现明显持续内存增长”有原始数据支持。但该结论只能覆盖这次 MultimediaServer 混合负载和小时级明显增长，不能证明：

- StorageManager 没有泄漏；
- goroutine、FD、Socket、SQLite、后台任务或子进程没有泄漏；
- 8～24 小时慢泄漏不存在；
- 停止负载或 GC 后一定回到稳定平台。

## 5. 发现的报告一致性问题

### 5.1 瓶颈结论前后矛盾

- `测试报告/README.md` 仍写“瓶颈是千兆网卡线速”，并推算建议不超过 55 路。
- 根 `README.md` 和最终汇总报告已经撤回该结论，改为“MiniDLNA 并发服务上限约 50 路”，建议不超过 35 路。

使用时应以最终汇总报告中的“已撤回结论”为准，并修正旧索引，避免读者拿到两个答案。

### 5.2 长稳窗口与 48 路并发描述不一致

- 最终汇总报告称 47.9 分钟长稳窗口“包含 48 路并发”。
- 实际 15:34:15～16:22:35 窗口内进程数最大为 11。
- 进程数达到 52 的 48 路附近负载出现在 16:28:53 以后，已超出该长稳窗口。

因此，长稳窗口可支持内存趋势结论，但不能声称它覆盖了 48 路并发。

### 5.3 阶段元数据容易误读

`phases.json` 中的阶段窗口是从持续采集 CSV 中切出的分析窗口，不是 CSV 文件完整起止时间。例如：

- `P0_pre_install_host.csv` 实际为 15:01:29～15:11:29、600 行；元数据只声明了其中约 233 个样本。
- `P1_install_host.csv` 实际为 15:04:34～15:44:34、2397 行；元数据中的安装阶段只到约 15:05:28。
- `P2_MultimediaServer.csv` 实际为 15:06:35～15:16:35、596 行；元数据只选取前 5 分钟。

后续报告应明确写“原始文件窗口”和“分析切片窗口”，避免把采集文件长度与阶段样本数混为一谈。

### 5.4 容量上限证据未完整随包交付

包内有服务端资源 CSV 和统计 JSON，但未看到 80 路客户端逐连接结果、完整 curl 日志或成功/失败清单。因此“前 50 路满速、第 51 路衰减、第 67 路无数据”无法仅依靠当前交付包独立复核。

该结论目前可视为测试记录中的结论，不应视为已经由随包原始证据完全闭环的结论。

## 6. 脚本安全与适配检查

### 6.1 与“只读”描述不完全一致

采集指标本身主要读取 `/proc`，但远程模式还会：

- 上传 `/tmp/perf_collect.py`；
- 在 `/tmp/perf_collect_out.csv` 写入采集结果；
- 完成后执行 `rm -f` 删除这两个远端文件。

因此准确说法应为“只读采集被测指标，但会在 `/tmp` 创建和删除临时文件”，不能表述为完全不写被测机。

### 6.2 存在自动安装行为

- `selftest.py` 和 `sshcommon.py` 在缺少 Paramiko 时会自动执行 `pip install paramiko`。
- `perf_run.py` 可能通过 winget 安装 k6/JMeter，或通过 pip 安装 Locust。
- 设置 `SKILL_NO_AUTO_INSTALL=1` 才会关闭自动安装。

在正式测试环境中应默认关闭自动安装，依赖安装单独评审。

### 6.3 SSH 实现不符合当前 NAS 安全约定

当前脚本：

- 使用 `AutoAddPolicy()` 自动接受未知主机指纹；
- `look_for_keys=False`、`allow_agent=False`，不会优先使用现有 SSH 密钥；
- 支持把 `TOS_PASS` 放入 `.env.local`；
- 没有通过 `C:\Users\twm\.ssh\config` 和 `known_hosts` 做动态 IP 身份核验。

这与当前要求的“动态 IP 先核对主机指纹和 hostname、优先 `id_ed25519_codex`、不保存密码”不一致，不能直接用于正式 NAS。

### 6.4 建议改造后再使用

1. 使用系统 OpenSSH 配置和 `known_hosts`，优先 `C:\Users\twm\.ssh\id_ed25519_codex`。
2. 禁止自动接受未知主机指纹；动态 IP 冲突时先备份并只替换精确 `[IP]:9222` 记录。
3. 默认设置 `SKILL_NO_AUTO_INSTALL=1`。
4. 不把真实密码写入 `.env.local`；必要时只做一次性掩码输入。
5. 远端临时文件使用唯一目录，停止/清理前验证路径和采集进程身份。
6. StorageManager 专项增加 PSS/RSS、Go heap/goroutine、FD、Socket、SQLite/WAL、任务数和 `mdadm`/`mkfs`/`lvm` 子进程残留。

## 7. 总体评价

| 维度 | 评价 |
|---|---|
| 方法论 | 较完整，适合作为性能测试框架参考 |
| 报告模板 | 可复用，覆盖统计、趋势、覆盖度和口径声明 |
| 原始数据 | 对 MultimediaServer 的部分结论可复算 |
| 报告一致性 | 存在旧结论未同步、窗口描述不准确的问题 |
| 容量证据 | 客户端原始证据不足，不能完全独立复核 |
| 直接用于当前 NAS | 不建议；需先改造 SSH、凭据、主机指纹和自动安装策略 |
| 用于 StorageManager | 可借鉴框架，但必须重新设计业务场景和泄漏指标 |

结论：保留该包作为“参考资料和脚本原型”是有价值的，但在当前 NAS 上执行前需要先完成安全适配与数据口径修订。
