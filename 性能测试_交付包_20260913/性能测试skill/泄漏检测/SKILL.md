# 泄漏检测

> 内存泄漏是性能测试里**最容易误报**的一项。本文件给两条路：
> **弱判据**（常规巡检，看趋势）与**强判据**（churn 专项，看单调性）。
> 判据一律看 **`private_Dirty`**，不看 RSS——RSS 会被页缓存撑大，拿它看趋势会得出假警报。

---

## 一、两条路，按场景选

| 路 | 何时用 | 做法 | 结论强度 |
|---|---|---|---|
| **弱判据** | 每次 P2 空载 / P3 负载 / 长稳窗口顺带做 | 看窗口内**水位趋势**与**能否回落** | 中，只够说「疑泄漏 / 无增长」 |
| **强判据** | 有泄漏嫌疑时、或验收明确要求 | **多轮 churn**，看**拆除后水位是否单调上升** | 高，可下「有 / 无泄漏」的定论 |

| 观察 | 判定 |
|---|---|
| 窗口内内存**单调增长** | **疑泄漏** |
| 峰值 / 均值波动小 | 无泄漏 |
| 空闲期能否**回落** | 能回落 = 无残留；不能回落 = 有残留 |

> ⚠️ 弱判据只够支持「疑似」，**下结论要上强判据**。反过来说，弱判据出「疑泄漏」也不必立刻报警，
> 先看是不是踩了下面第四节的四条反误判。

---

## 二、churn 轮次设计（强判据）

每轮四个动作，**共 5 轮**，每轮记**三个水位**：

```
第 i 轮：
  ① 建立 N 个会话 / 任务    → 记录【建立后水位】
  ② 保持 15 秒              → 记录【保持期水位】
  ③ 全部拆除                → （拆除动作）
  ④ 静置 20 秒              → 记录【拆除后水位】 ← 判定看这一列
```

| 参数 | 默认 | 调大意味着 |
|---|---|---|
| `--rounds` | `5` | 轮数越多结论越稳，耗时线性增加 |
| `--hold-s` | `15` | 保持期越长，越能暴露「用着不还」的部分 |
| `--rest-s` | `20` | 静置期越长，越能区分「暂时未回收」与「真不回收」 |

```bash
# 泄漏专项：8 轮、保持 60s、静置 30s
python scripts/perf_lifecycle.py --app Emby --phases P4 --rounds 8 --hold-s 60 --rest-s 30 \
    --out-dir ./perf-out
```

> ⚠️ **本脚本不驱动业务动作**（业务由人做），只做**轮次打点**——每到闸门打印指引、等人建/拆负载。
> 脚本在每个打点处采一次内存水位，写入 `P4_churn.json`
> （字段：`rounds` / `baseline_mb` / `drift_mb` / `verdict`）。

## 三、判定：看【拆除后水位】是否单调上升

| 模式 | 判定 |
|---|---|
| 拆除后水位**逐轮抬升、且单调** | **有泄漏**（每轮泄漏量 ≈ 平均抬升幅度） |
| 拆除后水位在一个区间内**波动、无单调性** | **无泄漏**（噪声级） |
| 拆除后水位**下降** | **无泄漏**（比无泄漏还干净） |

> **实测范例（PPT 服务端）**：5 轮拆除后水位
> **32.32 / 32.45 / 30.96 / 31.05 / 31.19 MB**，
> 末轮比首轮**反而略降 −1.12 MB（噪声级）→ 判定无泄漏**。

> ⚠️ 别只看首轮 vs 末轮的单点差——单点噪声极大。要看**整列的单调性**，
> 或用下面的 `growth` 自动判定（首尾四分位均值 + 单调性检验）。

## 四、四条反误判（写报告时必须做的事）

### 1. 空闲期内存不归零，属正常设计

> 实测：某备份应用任务停止后仍保留 **62~335 MB 常驻缓冲**。
> 判据**不是**「是否归零」，而是「**是否有单调爬升**」——无爬升即判无泄漏。

### 2. 页缓存（`RssFile`）不是泄漏

> `RssFile` 是 mmap 读入的文件页，**内核可随时回收**。
> 实测：某做种应用 RSS **5918 MB** 里 `RssFile` 占 **5778 MB（97.6%）**，真实匿名仅 140 MB。
> 拿 RSS 看趋势 = 拿页缓存看趋势 = **必然报假泄漏**。

### 3. swap 换出不是压力

> 实测：155 MB swap 配 PSS 仅 30 MB、CPU 0.01%、磁盘近零 —— 这些页**长期未被访问**，
> 是「深度空闲」的结果。代价只是**首次请求有一次换入延迟**，报告要写出来，别当故障。

### 4. 均值会被窗口构成污染，要用稳态时段口径

> 实测：5 分钟窗口里空载段占 6.6%、30 分钟窗口只占 1.9%，于是算出「+7.2% 长时退化」的假结论；
> 改用「只看稳态时段」重算，实际仅 **+1.9%**。
> → 比较不同时长的均值前**先对齐负载占比**，或直接改用稳态时段口径；
> 报告里同时给出「全程均值」与「稳态均值」，并注明稳态占比。

## 五、长稳测试（8h / 24h）

| 项 | 做法 |
|---|---|
| 时长 | 标准压力下持续 **8h**（8 小时系统）/ **24h**（24 小时系统） |
| 看什么 | ① TPS 曲线平稳度 ② 错误率 ③ 内存趋势（**`private_Dirty`**） |
| 采多密 | 长稳可放 `--interval 5` 省 IO，趋势不受影响 |
| 与短窗口的关系 | 5 分钟抓**峰值型**上限；长窗口才暴露**慢变量**——**两者不可互相替代** |

```bash
# 长稳：5 秒一采，跑 8 小时，进程树口径
python scripts/perf_collect.py --app Emby --interval 5 --duration 28800 --out Emby_long_8h.csv
```

| 观察点 | 判据 |
|---|---|
| TPS 曲线 | 平稳、无大幅波动（波动大 = 周期性阻塞或资源争抢） |
| 错误率 | 在可控范围内（参考 ≤0.2%） |
| 内存（`private_Dirty`） | **无持续增长趋势**；增长即疑泄漏 |

## 六、用 `perf_analyze.py` 自动判定

分析脚本内置 `growth()`，对 `private_Dirty占用(MB)` 列做自动判定：

```
取窗口【首尾各 1/4 样本】的均值相比  ← 用四分位均值而非首尾单点（单点噪声极大）
   + 单调性检验
        │
        ├─ 抬升且单调   → 「疑泄漏」
        ├─ 抬升但不单调 → 「有抬升但非单调,建议延长窗口复测」
        ├─ 无抬升       → 「无增长」
        └─ 样本不足     → 「样本不足」
```

```bash
python scripts/perf_analyze.py --in "perf-out/P2_Emby.csv" \
  --app Emby --tag P2 --out "perf-out/P2_stats.json"
# stats.json 里的 growth 字段 → 报告「内存回落与泄漏判定」章节
```

| 字段 | 含义 |
|---|---|
| `growth.verdict` | 四档结论之一 |
| `growth.first` / `growth.last` | 首尾四分位均值（MB） |
| `growth.delta` | 差值 |

> ⚠️ 结论是**四档不是两档**——「有抬升但非单调」既不能判泄漏也不能判干净，
> **必须延长窗口复测**，不要硬塞进「有/无」两选一。
