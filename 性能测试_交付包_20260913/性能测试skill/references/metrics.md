## 🚩 评审红线（**硬性规则，先看这条**）

> 与下面的「参考阈值」**性质不同**：红线是**硬性**的，超了就要讨论评估；
> 参考阈值是**业界参考**，各项目组结合自身业务**具体讨论定夺**。

| 红线 | 判定口径 | 超了怎么办 |
|---|---|---|
| **单个进程的内存峰值 > 1 GB** | **`private_Dirty`（真实匿名内存）** | **需团队讨论评估** —— 不是「达标/不达标」的二元判定，而是**要坐下来评估合不合理** |

### ⚠️ 为什么判定口径必须是 `private_Dirty`，不能用 RSS

| 实测案例 | RSS 峰值 | **private_Dirty 峰值** | 用 RSS 判 | 用 private_Dirty 判 |
|---|---|---|---|---|
| qBittorrent 做种 | **5918 MB** | **140 MB** | ❌ 误报「超 1GB 不合理」 | ✅ 正常 |
| Emby 4 路转码 | 612 MB | ~333 MB | ✅ 通过 | ✅ 通过 |
| MultimediaServer 空载 | 48 MB | 8.4 MB | ✅ 通过 | ✅ 通过 |

**RSS 含 `RssFile`（mmap 文件页缓存，内核可随时回收）** —— 用它判会把页缓存当成真实占用，
**全线误报**。这条与 `memory-accounting.md` 的红线 2 是同一个道理。

### 报告里怎么体现

判定为 **`! 待确认`**（不是 `✗ 不通过`）—— 语义是「**需要讨论**」而非「不合格」，
会进报告的「待确认」清单。默认阈值 `--thresholds '{"proc_mem_peak_mb": 1024}'` 可调。

## 表 1 · 核心性能指标速览（**完整版，原文**）

> 出自《测试入门·性能测试入门关注指标》。**这 9 项已核对为原文，可信使用。**

| 指标类别 | 关键指标 | 简要说明 |
|---|---|---|
| **用户感知指标** | **响应时间 (RT)** | 用户从发起请求到接收到**完整响应所花费的总时间**。通常需关注**平均响应时间**、**P90/P95**（90%/95% 的请求**快于**该值）等百分位数 |
| | **错误率 (Error Rate)** | 失败请求数占**总请求数**的百分比。**理想情况下应接近 0%**，过高通常意味着系统存在瓶颈或缺陷 |
| **系统处理能力指标** | **TPS**（每秒事务数） | 系统每秒成功处理的**完整业务流程（事务）数量**，直接反映系统的处理能力 |
| | **QPS**（每秒查询数） | 系统每秒处理的请求或查询数量，**通常用于衡量接口类能力** |
| | **并发用户数** | 在同一时刻与系统进行交互的用户数量，**用于模拟真实负载** |
| **资源消耗指标** | **CPU 使用率** | 服务器 CPU 的繁忙程度。**业界警戒值通常为 75% ~ 80%** |
| | **内存使用率** | 系统内存的消耗情况，**需警惕持续增长**（可能存在内存泄漏） |
| | **磁盘 I/O** | 磁盘的读写速率和繁忙程度。**磁盘繁忙率通常建议低于 70%** |
| | **网络吞吐量** | 单位时间内网络传输的数据量，**需关注是否接近带宽上限** |

**表 1 的四个阈值速记**：
- CPU 警戒 **75% ~ 80%**
- 磁盘繁忙率 **< 70%**
- 网络吞吐 **不接近带宽上限**
- 错误率 **趋近 0%**

> 这四个值与 `analysis-playbook.md` 的瓶颈流程图**完全一致**（CPU >75~80% / 磁盘 >70% / 网络接近上限），
> 两处互相印证。

## 一、用户感知指标（表 2 · 达标线口径）

| 指标 | 口径（是什么 / 怎么算） | 参考阈值 | 采集方式 | 超标排查 |
|---|---|---|---|---|
| **响应时间 RT** | 从用户发起请求到接收到**完整响应**所经过的时间。通常关注**平均响应时间**与 **90% 响应时间**（P90，即 90% 的请求在此时间内完成）；压测报告一般给到 **P95 / P99** | 视业务而定。一般建议：**核心操作 ≤ 200ms**；**普通页面加载 ≤ 3 秒**；**只读查询可要求 ≤ 10ms** | 压测工具（k6/JMeter）自动统计；前端用 Navigation Timing | 结合资源指标判断：CPU 高 → 计算瓶颈；`%iowait` 高 → 磁盘瓶颈；两者都不高 → 应用逻辑/慢 SQL/外部依赖 |
| **错误率 Error Rate** | 失败请求数 ÷ 总请求数 × 100% | 压测失败率建议 **≤0.2%**（即成功率 ≥99.5%）。理想情况为 0，非零常意味着系统存在瓶颈或缺陷 | 压测工具汇总 | 看错误码分布：超时 / 连接拒绝 / 5xx 代码异常，三者根因不同 |

## 二、系统处理能力指标

| 指标 | 口径 | 参考阈值 | 采集方式 | 超标排查 |
|---|---|---|---|---|
| **TPS**（每秒事务数） | 系统每秒**成功处理**的**完整业务流程**（事务）数 | 无固定值，取决于系统设计目标。期望**在目标并发下 TPS 曲线保持平稳** | 压测工具 | TPS 上不去且响应时间变长 → 系统已达瓶颈，查资源与中间件 |
| **QPS**（每秒查询数） | 系统每秒处理的请求或查询数量 | 同上 | 压测工具 | 同上 |
| **吞吐量** | 单位时间内系统处理的请求数量或数据量。常用 TPS / QPS 衡量 | 无固定值，取决于系统设计目标 | 压测工具；传输类应用可用网络字节数 | 见「拐点」判据 |
| **并发用户数** | 同一时刻与系统进行交互的用户数量。是设计测试场景、评估系统容量的核心依据 | 需通过测试得出系统能稳定支撑的**最大并发数**；**在线用户数的 8%~12%** 可作为并发用户数的估算参考 | 压测工具配置 | 并发上升而 TPS 不升反降 → 已过拐点 |
| **拐点（最佳并发点）** | 资源未饱和前，吞吐量随并发上升而响应时间变化不大；**到达瓶颈后吞吐量趋平甚至下降，而响应时间急剧上升** | 拐点即最佳并发点 | 画「响应时间-并发用户数」「吞吐量-并发用户数」曲线找 | — |

## 三、整机资源指标

| 指标 | 口径 | 参考阈值 | 采集方式 | 超标排查 |
|---|---|---|---|---|
| **CPU 使用率** | 服务器 CPU 用于处理请求的时间占比。是判断计算资源是否成为瓶颈的关键指标。**用户态 `%us` 与系统态 `%sy` 也需分别关注** | · 应用/数据库服务器：**≤ 70%**<br>· 通用标准：**≤70% 为「好」，85% 为「坏」，90% 以上「很差」**<br>（表 1 的警戒值口径为 **75%~80%**，取用时说明来源） | `/proc/stat` 两次采样差值；进程级用 `/proc/<pid>/stat` | `%us` 高 → 应用计算密集 / 死循环；`%sy` 高 → 系统调用或上下文切换过多；`%iowait` 高 → 磁盘瓶颈 |
| **内存使用率** | 系统物理内存或应用（如 JVM）堆内存的使用比例。**需警惕内存泄漏** | · 系统内存：**≤ 70%，无页交换为「好」**<br>· **JVM 内存：占用率 ≤ 70%** | `free` / `/proc/meminfo` | **警惕持续增长**（内存泄漏）。判压力以 `private_Dirty`/`PSS` 为准，**不要只看 RSS**——见 `memory-accounting.md` |
| **磁盘 I/O** | 磁盘的利用率 `%util`、等待时间 `await`、每秒读写次数 `IOPS`。反映磁盘的繁忙程度 | · 磁盘利用率 `%util`：**≤ 80%**，**< 30% 为「好」**<br>· I/O 等待 `%iowait`：**≤ 20%-30%**，**超过 40% 可能成为瓶颈**<br>（表 1 口径：磁盘繁忙率建议 **< 70%**） | `iostat -x`（需 sysstat）；无 sysstat 时用 `/proc/diskstats`；进程级用 `/proc/<pid>/io` | 写队列积压 / `await` 高 → 换更快存储、优化查询、减少落盘 |
| **网络带宽使用率** | 网络流量占可用带宽的比例 | **≤ 系统带宽的 30%**，且**无丢包、延迟和阻塞** | `/proc/net/dev`（**整机口径**，见下方声明） | 千兆网 ≈ **119 MB/s**；贴住线速说明瓶颈在网卡，不在 CPU/内存/磁盘 |
| **系统负载 Load Average** | 单位时间内系统处于运行和等待状态的进程平均数。反映系统整体繁忙程度 | `Load Average ≤ CPU核数 × 0.7`；**更宽松的标准是 `Load < CPU核数 × 2`** | `/proc/loadavg` | Load 高但 CPU 不高 → 大量进程在等 I/O |

> ⚠️ **网络是整机口径**：Linux **没有逐进程网络字节计数**（`/proc/<pid>/net/dev` 属于整个网络命名空间，
> 与整机数值相同）。所以每个进程的 CSV 里网络列**取自同一份整机数据、数值完全相同**，
> **不能归因给单个应用**。报告里必须显式声明这一点。

## 四、应用进程指标（应用侧核心）

> 这一节的口径来自目标机 12 份实测报告，是本技能与「接口压测」类技能的分水岭。

| 指标 | 口径 | 参考阈值 | 采集方式 |
|---|---|---|---|
| **PSS**（Proportional Set Size） | 私有内存 + 共享内存 ÷ 共享进程数。**推荐首选**的内存指标 | — | `/proc/<pid>/smaps_rollup` 的 `Pss:` |
| **private_Dirty** | 进程私有的、不可回收的脏页。**与 `RssAnon` 基本相等，判内存压力的第一口径** | — | `/proc/<pid>/smaps_rollup` 的 `Private_Dirty:` |
| **RSS**（Resident Set Size） | 私有 + 共享内存的完整大小。**会被页缓存严重放大，不能直接当占用** | — | `/proc/<pid>/status` 的 `VmRSS:` |
| **USS**（Unique Set Size） | 只算进程独占的内存，不含任何共享。进程退出能完全释放的部分 | — | `Private_Clean + Private_Dirty` |
| **RssAnon / RssFile** | `RssAnon` = 匿名内存；`RssFile` = 文件映射页（**页缓存，内核可随时回收**） | — | `/proc/<pid>/status` |
| **应用 CPU** | 单核口径：`100% = 1 个核`，4 核跑满 = 400%。**另给「折合核数」** = CPU% ÷ 100 | 与整机 CPU 阈值同口径 | `/proc/<pid>/stat` 的 `utime+stime` 差值 ÷ `CLK_TCK` × 100 |
| **磁盘读 / 写速度** | 进程级归属；写速度**必须扣除 `cancelled_write_bytes`**，否则虚高 | — | `/proc/<pid>/io` 的 `read_bytes` / `write_bytes` 差值 |
| **swap 占用** | 进程被换出的内存 | — | `/proc/<pid>/status` 的 `VmSwap:` |
| **进程树规模** | 父进程 + **全部子孙进程**的数量（均值 / 最大）。**独立指标，不要漏** | — | `ps -eo pid,ppid` 递归 / `/proc/<pid>/task/*/children` |
| **内存是否随窗口增长** | 是 / 否。空载基线与长稳测试**必答** | 否（增长即疑泄漏） | 窗口首尾水位对比 + 单调性检验 |
| **放大倍数** | `负载期均值 ÷ 空载期均值`，CPU 与内存各一份 | — | 两次采集的 `stats.json` 相除 |

### 使用 / 空闲判定（口径来自实测脚本）

```
活跃（使用中） = CPU > 2%  或  磁盘读写合计 > 0.5 MB/s  或  网络收发合计 > 0.5 MB/s
空闲           = 以上都不满足
```
传输类应用另有更窄的口径：**进程网络收发合计 > 0.5 MB/s = 使用**。

## 五、中间件 / 数据库指标

| 指标 | 口径 | 参考阈值 | 超标排查 |
|---|---|---|---|
| **数据库连接数** | 当前活跃连接数占最大连接数的比例 = `(当前 / 最大) × 100%` | **≤ 85%** | 连接池配置过小 / 连接未释放（泄漏） |
| **慢查询** | 执行时间过长的 SQL 语句 | **不应出现执行时间过长的 SQL** | 看执行计划、加索引 |
| **死锁** | 数据库或应用中的线程/进程因争夺资源而相互等待 | **不应出现 SQL 死锁或线程死锁** | 查加锁顺序、事务粒度 |
| **GC 频率与时长** | Java 虚拟机的垃圾回收情况，尤其是 **Full GC**。频繁或耗时的 GC 会导致应用暂停、影响响应时间 | · Full GC 频率：**不应过于频繁（如大于平均半小时 1 次）**<br>· Full GC 时长：**应足够短，且压测中不应因 FGC 导致响应时间急剧升高** | 调堆大小、查对象生命周期 |

## 六、稳定性与错误指标

| 指标 | 口径 | 参考阈值 |
|---|---|---|
| **错误率** | 同第一节 | ≤0.2% |
| **稳定性时长** | 系统在标准压力下能稳定运行的最短时间 | 对于 **8 小时系统**，至少稳定运行 **8 小时**；对于 **7×24 系统**，至少稳定运行 **24 小时** |
| **TPS 曲线平稳度** | 长稳期间 TPS 是否平稳、有无大幅波动 | 平稳；无大幅波动 |
| **资源泄漏** | 内存是否持续缓慢增长（最终可能导致 `OutOfMemoryError`） | 无持续增长 |

## 八、质量元指标（实测报告里都有，最容易漏）

| 指标 | 含义 | 为什么要记 |
|---|---|---|
| 采样点 | 实际采集到的样本数 | 判断样本量是否足够下结论 |
| 采样间隔 | 通常 1 秒 | 与其他数据对齐时的基准 |
| **坏行剔除** | 时间格式或数值列非法而被丢弃的行数（如粘连行） | 剔除量大会影响统计可信度 |
| **完整率** | 实际采样点 ÷ 应有采样点 | 采集器掉线或进程重启会造成缺口 |
| 样本量 | 单进程实例的采样数 | 多实例比较时需可比 |
| 实际采样窗口 | `[起始时间, 结束时间]` | 与计划窗口对比，确认没跑偏 |
| **稳态占比** | 稳态时段样本 ÷ 总样本 | **均值会被窗口构成污染**（见 `methodology-pitfalls.md` 第 9 条） |

## 快速判定卡（贴给业务方看的版本）

| 维度 | 指标 | 达标线 |
|---|---|---|
| 快不快 | 平均响应时间 / P95 | **核心操作 ≤200ms**；页面加载 ≤3s；只读查询 ≤10ms |
| 稳不稳 | 错误率 | ≤0.2% |
| 扛不扛 | TPS 曲线 | 目标并发下保持平稳，不出现拐点 |
| 累不累 | CPU | 达标 **≤70%**（70% 好 / 85% 坏 / 90%+ 很差）；警戒 75%~80%（表 1） |
| 吃不吃内存 | 内存（**private_Dirty 口径**） | 系统 **≤70%**、无页交换；JVM 堆 **≤70%**；不持续增长 |
| 磁盘忙不忙 | `%util` / `%iowait` | `%util` **≤80%**（<30% 好）；`%iowait` **≤20%-30%**（>40% 可能成瓶颈） |
| 网卡满没满 | 带宽占用 | **≤30%** 且无丢包/延迟/阻塞；千兆 ≈119 MB/s |
| 排队长不长 | Load Average | ≤核数×0.7 |
