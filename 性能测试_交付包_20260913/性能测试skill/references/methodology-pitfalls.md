# 口径与方法学陷阱（十八条）

> **这是本技能最值钱的一份文档。** 全部条目都来自目标机 `10.18.15.103:/Volume1/public/` 上
> 真实跑出来的 12 份报告的**踩坑记录**——其中两条是报告初版结论被推翻后留下的纠错痕迹。
> **动手做性能测试之前先读一遍**，能省掉一整轮返工。

---

## A. 内存口径（1~8）

### 1. PSS 优先于 RSS
RSS 把多进程共享的库页在**每个进程各算一份**，重复计入。PSS 按共享进程数**比例分摊**，
多进程/多线程应用求和才不虚高。
→ **跨进程求和一律用 PSS。**

### 2. `private_Dirty` 才是真实匿名内存
它是进程私有的、不可回收的脏页，与 `RssAnon` 基本相等（空载基线里两者数值完全一致）。
RSS 里混着共享库与页缓存。
→ **判内存压力看 `private_Dirty`。**

### 3. `RssFile` 是页缓存，可回收
mmap 读入的文件页计入 `RssFile`，内核随时可丢弃后重读。
→ qBittorrent 的 5.9 GB RSS 里 **5778 MB（97.6%）** 是这种，真实匿名仅 140 MB。

### 4. 页缓存放大 RSS，据此判 OOM 是错的
libtorrent 等 mmap 大文件的服务，RSS 可虚高到整机 67%，而真实匿名只有一小部分。
→ 实测报告据此撤回了「限制写缓存 512MB~1GB」的建议。**别重犯。**

### 5. Linux 无逐进程网络计数，网络是整机口径
`/proc/<pid>/net/dev` 属于**整个网络命名空间**，与整机数值相同。
→ 每个进程 CSV 里的网络列取自同一份数据、**数值完全相同**，**不可归因给单个应用**。
→ 报告里必须显式声明，否则读者会把整机流量算到被测应用头上。

### 6. 网络峰值要贴线速判断
千兆网 ≈ **119 MB/s**。实测发送峰值 119.19 MB/s 即「贴住线速上限」。
→ 此时瓶颈是**网卡**，不是 CPU / 内存 / 磁盘。别去优化错的对象。

### 7. 页缓存不会进入 swap
→ 「A 应用的残留写缓存污染了 B 应用窗口的 swap 统计」这种因果**不成立**。
→ 实测报告初版栽在这里，该结论已撤回。

### 8. swap 换出 ≠ 内存压力
Jellyfin 的 155 MB swap 配 PSS 仅 30 MB、CPU 0.01%、磁盘近零，说明这些页**长期未被访问**，
是「深度空闲」的结果。代价只是**首次请求有一次换入延迟**。
→ 报告要写出这个推论，别让读者当成故障。

## B. 统计与对齐（9~15）

### 9. 均值会被窗口构成污染（**最容易骗人的一条**）
> 实测案例：Jellyfin 5 分钟窗口里空载段占 6.6%，30 分钟窗口只占 1.9%，
> 于是算出「+7.2% 长时退化」的假结论。改用「只看 ffmpeg 并发数 ≥3 的**稳态时段**」重算，
> 实际是 278.51% vs 283.72%，**仅 +1.9%**，推翻了「长时退化」。

→ **比较不同时长的均值前，必须先对齐负载占比**，或直接改用**稳态时段口径**。
→ 报告里同时给出「全程均值」与「稳态均值」，并注明稳态占比。

### 10. 短窗口与长窗口不可互相替代
5 分钟捕捉「**峰值型**」负载的真实上限；30 分钟才暴露「**慢变量**」（内存持续增长）。
→ 两个时长都要跑，别用一个代替另一个。

### 11. 不同采样周期不要按精确时间戳 JOIN
1 秒的系统监控对 5 秒的应用探测，精确 join 只匹配上约 10% 的点，
算出「均值 1.83 路 / 占比 9.8%」的假值；改**最近邻对齐（容差 4 秒）**后得真实值 **13 路 / 53%**。
→ 多进程汇总**按采样周期向下对齐**，否则产生**幻影行**。

### 12. 峰值必须带发生时刻
> 实测：写盘尖峰 543 MB/s 只标数值时看着像持续压力；标上发生时刻 `09-09 12:00:24` 后，
> 才归因到「转码轮次切换的收尾落盘」，是一次性动作。

→ 所有峰值列都带 `peak_time`。

### 13. 重复测试前必须清缓存 + 保证请求唯一
Jellyfin 会**缓存转码产物**，相同请求直接命中缓存、根本不启动 ffmpeg。
→ 必须清转码目录，且每路请求参数唯一（唯一 `PlaySessionId`），否则测出「CPU 接近 0」的假象。

### 14. 磁盘读峰值会因缓存预热而虚降
> 实测：Emby 第二次读同一批素材，读峰值从 184 MB/s 降到 35.7 MB/s。
> 这是 **page cache 命中**，**不是性能提升**。

→ 对比两次运行时先确认缓存状态一致。

### 15. 并发台数不是有效容量指标
4 路全转码占 2.8 核，13 路混合只占 0.9 核。差异在**素材能否硬件解码**
（DivX3 无硬解必须软解；1080p H.264 走核显）。
→ 报告里要写清负载的**编码格式与解码路径**，否则数字不可比。

## C. 监控对象与判定（16~18）

### 16. 必须按进程树统计（父 + 全部子孙）
> 反例一：vpnmon 只跟踪**常驻父进程**，整轮测试 RSS 合计只在 29.51~35.05 MB 波动，
> 而 cgroup 实为 81 MB——**漏掉了 77% 的开销**（内存长在 fork 出的 `pppd` 上）。
> 反例二：Emby/Jellyfin 的转码负载跑在 **ffmpeg 子进程**里，只盯主进程会得到「CPU 接近 0」的假象。
> 反例三：`pptpd` 父进程全程恒为 **2.51 MB RSS / 0.41 MB PSS，从不变化**——它只负责 listen 和 fork。

→ **进程树规模本身就是一个独立指标**（实测：转码服务峰值 5 个进程 = 服务进程 + 4×ffmpeg；
qBittorrent 的 13 路并发全在单进程内完成，进程树恒为 1）。
→ 新增子进程要能**自动纳入监控**（实测脚本是 ≤5 秒），目标进程退出**自动结档**。

### 17. 判定阈值有两套，别混
| 场景 | 判定口径 |
|---|---|
| 通用「使用 / 空闲」 | `CPU > 2%` **或** `磁盘读写合计 > 0.5 MB/s` **或** `网络收发合计 > 0.5 MB/s` |
| 传输类应用 | 进程**网络收发合计 > 0.5 MB/s** = 使用 |

### 18. cgroup 口径含内核内存，逐进程 RSS 看不到
cgroup 的 `memory.current` 含 socket 缓冲区与 slab。
→ fork-per-connection 应用（pptpd 这类）**优先用 cgroup** 而非单 PID 求和。
→ 实测：PPT 满载 64 进程按 PSS 拆解 = `pppd×30` 37.32 MB + `pptpctrl×30` 4.32 MB +
父进程 0.41 MB + 内核 slab/页表，**单会话开销 77% 在 `pppd`**（每个 1.24 MB）。

## D. 写报告时的红线

| 红线 | 理由 |
|---|---|
| **采不到的指标不许填 0** | 0 会被读成「实测值是 0」。采不到就标 `❌ 未采集` 或 `⚠️ 口径降级`，并写清原因 |
| **必须输出「采集覆盖度与未测项」** | 借鉴 `Photos 安全问题修复验证报告` 的做法：逐条列 ✅已采 / ⚠️降级 / ❌未采 + 统计 |
| **默认阈值必须回显来源** | 「阈值来源：默认参考值（业界参考，**非业务验收标准**）」，并支持 `--thresholds` 覆盖 |
| **结论被推翻时留下纠错记录** | 实测报告里 qBittorrent 的 OOM 误判、写缓存建议撤回都留了痕迹。**保留纠错记录本身就是报告质量的一部分** |
| **负载真实性必须验证** | 证明负载真的压上了：ffmpeg 并发路数 / TCP 连接数 / 累计传输字节。否则「CPU 接近 0」可能只是负载没跑起来 |

### 19. 应用的「后台任务」可能跑在**独立服务**里，不在应用的进程树内

> **实测（2026-09-13，MultimediaServer 3.2.106）**：采集器按 `--app MultimediaServe` 盯住应用进程树，
> 但用户触发「媒体索引」后，真正干活的是 TOS 的独立服务 **`mediaindex`**
> （`/usr/sbin/mediaindex -f /etc/media.conf -P /run/mediaindex/mediaindex.pid -S`），
> 它 **PPID=1**，与应用进程树完全无关。只盯应用 → **索引这段负载全程漏采**。

**→ 对策**：测「应用」之前，先确认它的重活到底跑在哪个进程里。查法：

```bash
# 1) 触发任务前，记录基线进程清单
ps -eo pid,comm --no-headers | sort -u > /tmp/before.txt
# 2) 触发任务后，diff 出新增进程
ps -eo pid,comm --no-headers | sort -u > /tmp/after.txt
comm -13 /tmp/before.txt /tmp/after.txt
# 3) 也看服务层：任务常由 systemd 拉起
systemctl list-units --type=service --state=running --no-pager | grep -i <应用名或功能>
```

**已知的这类「旁路进程」**（TOS 上）：
| 应用/功能 | 真正干活的进程 | 是否在应用进程树内 |
|---|---|---|
| MultimediaServer 媒体索引 | `mediaindex`（独立服务） | ❌ 不在 |
| 媒体库/数据库 | `mediadb` | ❌ 不在 |
| 缩略图生成 | `thumbnaild` | ❌ 不在 |
| 转码 | `ffmpeg` | ✅ 在（应用 fork 的子进程） |

**→ 采集时用正则把兄弟服务一起纳入**，例如 `--app "MultimediaServer|mediaindex|mediadb"`。
宁可多盯几个，也别漏掉真正吃资源的那一个。

### 20. 状态侦测脚本自身容易「瞎」：数据源会换、判定字段要对准方向

做「负载开始/结束自动打点」的侦测脚本时，两个坑实测都踩到了（2026-09-13 MultimediaServer 测试）：

| 坑 | 现象 | 对策 |
|---|---|---|
| **盯着已停更的数据源** | 中途换了采集器（修复 bug 后重启），文件名从 `P3_*.csv` 变成 `P4_*.csv`，侦测仍在 `tail -1` 旧文件 → **55 分钟只打印了一条状态**，全程等于没监控 | 侦测要按**最新 mtime** 选文件，或直接问采集器当前在写哪个；换采集器时**同步重启侦测** |
| **判定字段方向搞反** | 推流是**发送(tx)**，判定条件里却只检查了**接收(rx)** → 打满千兆（tx 119 MB/s）也不触发 | 判定条件必须覆盖**双向**：`tx` 和 `rx` 都看，别只写一边 |
| **阈值定得太高** | 按「CPU≥15%」判活跃，而推流 CPU 只有 0.02% → 永远判 IDLE | 阈值要**按被测场景的量级**定：推流看带宽/进程树规模，转码才看 CPU |

**→ 通用做法**：侦测脚本里把判定条件写成「**任一维度越界**」，维度包含 `CPU / 磁盘读 / 磁盘写 / 网络发 / 网络收 / 进程树规模`，
并在启动时**先打印一次它正在读哪个文件**，便于核对。

**兜底**：连续采集 + 事后按时间戳切分，**永远比实时侦测可靠**。
本案例最终就是靠 `--from/--to` 切分连续 CSV 出报告的，侦测只当辅助。
