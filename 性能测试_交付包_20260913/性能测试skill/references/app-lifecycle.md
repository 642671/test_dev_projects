# 应用六阶段生命周期手册

> **为什么按生命周期切**：同一个应用，「装着没跑」「跑着没任务」「跑着有任务」三种状态的资源画像
> **完全不同**，混在一起采只会得到一份说不清的数字。
> 本文件把应用从「还没装」到「卸掉之后」切成 **P0~P5 六个阶段**，每阶段定死**采集口径**与**通过判据**，
> 由 `scripts/perf_lifecycle.py` 编排（人工触发关键动作，脚本只管监控与打点）。

---

## 一、六阶段总表

| 阶段 | 名称 | 做什么 | 谁来触发 | 采集口径 | 产出 |
|---|---|---|---|---|---|
| **P0** | `pre_install` | 未安装态基线：断言应用**确实没装**、记**整机基线**（默认 5 分钟）、记**已装应用清单**（防串味）、记设备规格 | 脚本自动 | 整机 | `P0_host.csv` |
| **P1** | `install` | 安装过程：全程 **1s 采样**，记录**耗时**、CPU/磁盘**峰值**、**应用进程出现时刻** | **人工触发安装** | 整机（持续采到进程出现 + 收尾 60s） | `P1_install_host.csv` |
| **P2** | `idle` | 安装后**空载默认占用**：静置 2 分钟（让首次初始化扫描收敛）后采 5 分钟 | 脚本自动 | **进程树** | `P2_<app>.csv` |
| **P3** | `load` | **负载态**：人工发起任务，采 10 分钟 | **人工发起任务** | **进程树** | `P3_<app>.csv` |
| **P4** | `leak` | 停任务 → 采**回落曲线** → **5 轮 churn** → 判泄漏 | 脚本自动 + 人工建拆 | 进程树 + cgroup | `P4_churn.json` |
| **P5** | `post_uninstall` | 卸载后**残留**检查（**默认不跑**）：人工卸载后复查进程残留 | **人工卸载** | 整机 + 进程 | `P5_post_uninstall_host.csv` |

> **P2 与 P3 的差值是本技能最核心的一个数**：「放大倍数 = 负载期均值 ÷ 空载期均值」，CPU 与内存各一份。
> 没有 P2 就没有分母，放大倍数就出不来。

## 二、每阶段的判据表

| 阶段 | 通过判据 | 常见误判 |
|---|---|---|
| **P0** | 应用进程**确实不存在**；已装应用清单已留档 | 忘了记清单 → 后续窗口里混进别的应用的负载，无法归因 |
| **P1** | 安装**成功结束**且能定位到**进程出现时刻**；耗时/峰值有 `peak_time` | 把**解包/编译**的一次性 CPU 峰值当成常驻开销 |
| **P2** | **内存不随窗口增长**；得到一份干净的空载基线 | **把首次初始化扫描的一次性动作当成稳态占用**（Emby 首次启动含媒体库扫描，数值偏保守） |
| **P3** | 负载**确实压上了**（有并发/连接数/传输量佐证）；与 P2 算出放大倍数 | 负载没跑起来 → 测出「CPU 接近 0」的假象，见 `methodology-pitfalls.md` 第 13 条 |
| **P4** | **多轮拆除后水位不单调上升**；空闲期能回落 | 把**空闲期不归零**当成泄漏（属正常设计，见下） |
| **P5** | 卸载后**无残留进程 / 无残留目录与配置** | 只看进程不看文件 → 漏掉残留数据目录 |

## 三、为什么安装 / 卸载必须人工触发

| 原因 | 说明 |
|---|---|
| **不同应用安装方式不一** | 应用中心的、命令行的、上传包的，路径与交互都不同，脚本代劳等于把不确定性写进代码 |
| **卸载可能丢配置 / 丢数据** | 卸载是不可逆动作，脚本误触发的代价远大于省下的那一次点击 |
| **需要人来判断「装完了没」** | 安装成功的判据是**人能确认应用可用**，不是进程出现就完事 |

→ **脚本只做两件事：监控 + 打点**。每到闸门停下来等人，人做完动作再继续。
→ 非交互场景（CI / 批量）用 `--wait-file` 或 `--yes` 放行闸门，见第五节。

## 四、泄漏检测的两种判据

### 弱判据（常规巡检，看趋势）

| 观察 | 判定 |
|---|---|
| 窗口内内存**单调增长** | **疑泄漏** |
| 峰值 / 均值波动小 | 无泄漏 |
| 空闲期能否**回落** | 能回落 = 无残留；不能回落 = 有残留 |

对应脚本 `perf_analyze.py` 的 `growth()`，结论分四档：
`疑泄漏` / `有抬升但非单调，建议延长窗口复测` / `无增长` / `样本不足`。

### 强判据（churn 专项）

每轮：**建立 N → 保持 15s → 全拆 → 静置 20s**，共 **5 轮**；
每轮记录**三个水位**——**建立后 / 保持期 / 拆除后**，判定看**拆除后水位是否单调上升**。

> **实测范例（PPT 服务端）**：5 轮拆除后水位
> **32.32 / 32.45 / 30.96 / 31.05 / 31.19 MB**，
> 末轮比首轮**反而略降 -1.12 MB（噪声级）→ 判定无泄漏**。

> ⚠️ **空闲期内存不归零属正常设计**：实测 Duple Backup 任务停止后仍保留 **62~335 MB** 常驻缓冲。
> 判据不是「是否归零」，而是「**是否有单调爬升**」——无爬升即判无泄漏。

## 五、长稳测试

| 项 | 做法 |
|---|---|
| 时长 | 标准压力下持续 **8h**（8 小时系统）/ **24h**（24 小时系统） |
| 看什么 | TPS 曲线平稳度、错误率、内存是否持续增长 |
| 时长的选择 | 5 分钟抓**峰值型**负载的真实上限；长窗口才暴露**慢变量**（内存持续增长）。**两者不可互相替代** |

## 六、怎么跑（可直接复制）

```bash
# 1) 完整六阶段——最常用。P0~P4 自动串起来，闸门处等人操作
python scripts/perf_lifecycle.py --app Emby --phases P0,P1,P2,P3,P4 --out-dir ./perf-out

# 2) 只补采空载基线（应用已装好，不重跑安装过程）
python scripts/perf_lifecycle.py --app Emby --phases P2 --p2-min 5 --out-dir ./perf-out

# 3) 泄漏专项：加大 churn 轮数、拉长保持期
python scripts/perf_lifecycle.py --app Emby --phases P4 --rounds 8 --hold-s 60 --rest-s 30 \
    --out-dir ./perf-out

# 4) 远程采集（凭据走环境变量 TOS_HOST / TOS_USER / TOS_PASS / TOS_PORT，不写进命令）
python scripts/perf_lifecycle.py --app Emby --phases P0,P1,P2,P3,P4 --remote --out-dir ./perf-out

# 5) 非交互（CI）：每到闸门等文件出现，出现即继续并自动删除该文件
python scripts/perf_lifecycle.py --app Emby --phases P0,P1 --wait-file /tmp/gate.ok --out-dir ./perf-out

# 6) 只采集不出报告
python scripts/perf_lifecycle.py --app Emby --phases P2 --no-report --out-dir ./perf-out
```

> `--wait-file` 用于**非交互场景**：脚本在每个闸门处轮询该文件，文件一出现就放行并自动删除，
> 适合由外部编排系统在「安装完成」后 `touch` 一下来推进流程。
> 纯本地交互调试用默认行为即可（回车放行）；`--yes` 则是一次性全部放行，**慎用**——会跳过人确认安装/卸载。
