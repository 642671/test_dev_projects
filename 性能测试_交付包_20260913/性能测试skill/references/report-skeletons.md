# 报告骨架（三种体裁）

> **为什么分三种体裁**：同一批采集数据，**对比轴不同**就是三份不同的报告。
> 拿「应用占用多少」的骨架去写「负载带来多少开销」，读者会读到一堆对不上号的表。
> 本文件给出三种体裁的**章节骨架**与**必带收尾章**，与 `scripts/perf_report.py` 的
> `--kind monitor|perf|summary` 一一对应。

---

## 一、三种体裁的分工

| 体裁 | 对比轴 | 监控层级 | 统计量 | 回答的问题 |
|---|---|---|---|---|
| **monitor** | 同一应用**使用期 vs 空闲期** | **进程树级**，PSS 为中心 | 峰值 / 均值（+P95） | 「这个应用占多少」 |
| **perf** | 同一进程**空闲 vs 负载**（2~3 场景） | **系统级 + 进程级并列** | 峰值 / 均值 / P95 / P99 | 「负载带来多少开销、瓶颈在哪一维」 |
| **summary** | **多应用横向** | 系统 + 进程 | 峰值 / 均值 / 稳态均值 / P95 / P99 | 「跨服务对比、方法学是否成立」 |

三种体裁的 `h1` 标题由 `KIND_TITLE` 决定：
`应用资源监控报告` / `性能测试报告` / `性能测试汇总报告`。

---

## 二、monitor（应用资源监控报告）

```
# <应用名> · 应用资源监控报告
> **元信息**：设备 · CPU 口径 · 采样间隔 · 方法 · 环境
## 总结
    一句话结论
    核心数字表（CPU / 内存 PSS / private_Dirty / 进程树规模 / 磁盘）
    N 条要点（bullet）
    建议
## 一、监控概况
    采集窗口 · 样本数 · 坏行剔除 · 完整率
    **进程构成明细**（父 + 全部子孙，各自 PSS / private_Dirty）
## 二、使用期 vs 空闲期
    两段窗口的指标对照表 + 判定口径
## 三、汇总曲线
    内存 / CPU / 磁盘 趋势折线（内联 SVG）
## 四、结论
    > blockquote：原始 CSV 落点（哪几个文件、各自是什么）
```

| 关键点 | 说明 |
|---|---|
| 进程构成明细**必给** | 只给合计会掩盖「开销长在子进程上」（实测 vpnmon 漏掉 77%） |
| 使用/空闲判定口径要写在正文 | `CPU>2%` 或 `磁盘读写合计>0.5` 或 `网络收发合计>0.5 MB/s` |
| 结论章要给**原始 CSV 落点** | 读者要能自己回去核数 |

## 三、perf（性能测试报告）

```
# <应用名> · 性能测试报告
> **元信息**：设备 · **CPU 口径：单核口径（100% = 1 个核；4 核满 = 400%）** · 采样间隔 · 方法
## 一、监控概况
    场景清单 · 样本数 · 坏行剔除 · 实际窗口 · 负载真实性证据
## 二、指标统计表
    列序固定：**均值 | 峰值 | P95 | P99**（单位与阈值同列）
## 三、分组趋势折线图
    CPU / 内存 / 磁盘 / 网络，按场景分组
## 四、结论与优化建议
    瓶颈定位（结论句式见 analysis-playbook.md）
```

| 关键点 | 说明 |
|---|---|
| **CPU 口径必须在 meta 里声明** | 单核口径写不清，400% 会被读成「超标 4 倍」 |
| 统计列序固定为 **均值 / 峰值 / P95 / P99** | 三种体裁里只有 perf 强制四列，别偷懒省 P99 |
| 峰值**必须带发生时刻** | 不带时刻的峰值会被误读成持续压力（见 `methodology-pitfalls.md` 第 12 条） |
| 至少 2~3 个场景 | 单场景出不来「放大倍数」 |

## 四、summary（性能测试汇总报告）

```
# <汇总主题>
## （副标题）
## 一、测试矩阵与运行条件
    **可比性前提 3 条**（同设备 / 同采样间隔 / 同负载口径）
## 二~五、各服务对照
    每个服务一节：使用期 vs 空闲期、放大倍数、进程构成
## 六~七、客户端并发测试
    **负载真实性验证**
    **测试方法学陷阱**
## 八、横向对比
    统一到同一内存口径（建议 private_Dirty）的跨服务表
## 九、综合结论与建议
## 十、分项报告
    链到各服务的 monitor / perf 报告
```

| 关键点 | 说明 |
|---|---|
| **可比性前提必须显式列出** | 设备不同、采样间隔不同、负载口径不同，横向对比直接失效 |
| 横向对比**统一内存口径** | 不能一个用 RSS 一个用 PSS（见 `memory-accounting.md`） |
| 客户端并发测试要写**负载真实性验证** | 证明负载真压上了：并发路数 / TCP 连接数 / 累计传输字节 |
| 分项报告**一步可达** | 别写成 A 报告链 B、B 再链 C |

## 五、三种体裁都必带的收尾章

### 1. 采集覆盖度与未测项

逐条列，**三态而非两态**：

| 标记 | 含义 | 写法 |
|---|---|---|
| ✅ | 已采 | 正常出数 |
| ⚠️ | **口径降级** | 说清降级成什么口径、为什么 |
| ❌ | **未采集** | 说清原因 + 是否可补采 |

末尾给**统计**（如「共 12 项：✅9 / ⚠️2 / ❌1」）。

> **红线**：**采不到 ≠ 达标**。**绝不拿 0 冒充实测值**——0 会被读成「实测值为 0」。
> 采不到就标 `❌ 未采集` 或 `⚠️ 口径降级`。

### 2. 口径声明

| 声明项 | 内容 |
|---|---|
| **网络** | 整机口径，**不可归因给单个应用**（Linux 无逐进程网络计数） |
| **RSS** | 含页缓存（`RssFile`），**判压力请用 `private_Dirty`** |
| **CPU** | 单核口径：100% = 1 个核，4 核跑满 = 400% |
| **阈值来源** | 默认参考值（业界参考，**非业务验收标准**），支持 `--thresholds` 覆盖 |

### 3. 已撤回的结论（summary 体裁）

保留纠错记录本身就是**报告质量的一部分**——实测报告里 qBittorrent 的 OOM 误判、
Jellyfin 的 swap 误判、写缓存建议的撤回都留了痕迹。
**删掉纠错记录 = 下一个读者会把已经想清楚的问题重新推翻一遍。**

## 六、本技能实际生成的章节

`scripts/perf_report.py` 生成的是上面骨架的**可执行精简版**：
自动算统计量、自动判阈值、内置**统计卡**（通过/待确认/不通过/未采集计数）、
**KPI 卡**（取前 4 条有值的指标）与**内联 SVG 趋势图**，输出自包含 HTML + Markdown 两份。

**Markdown 实际输出**（章节随数据存在与否**条件出现**）：

| # | 章节 |
|---|---|
| 一 | 结论概览（总判定 + 通过/待确认/不通过/未采集计数 + 未通过项点名） |
| 二 | 监控概况（场景数 · 样本数 · 坏行剔除 · 采集窗口 · 进程组窗口） |
| 三 | 指标统计（N 个场景，均值列 + 阈值 + 判定） |
| 四 | 峰值与发生时刻 |
| 五 | 使用期间 vs 空闲期间（有使用/空闲拆分时） |
| 六 | 空载 → 负载 放大倍数（有 P2/P3 两场景时） |
| 七 | 内存回落与泄漏判定（有 churn / 增长检验时） |
| 八 | 采集覆盖度与未测项 |
| 九 | 口径声明 |
| 十 | 已撤回的结论（有纠错记录时） |
| — | 瓶颈分析与建议 |

**HTML 实际输出**：把「结论概览」渲染成**统计卡**（替代 Markdown 的表格），
并在「指标统计」前多一节**趋势图**，其余章节对应关系同上：

`一、指标统计` → `二、趋势图` → `三、峰值与发生时刻` → `四、使用期间 vs 空闲期间` →
`五、空载 → 负载 放大倍数` → `六、内存回落与泄漏判定` → `七、采集覆盖度与未测项` →
`八、口径声明` → `九、已撤回的结论`。

### 常用命令

```bash
# monitor：单应用 使用期 vs 空闲期
python scripts/perf_report.py --kind monitor -i WebServer_stats.json --md r.md --html r.html

# perf：空闲 + 负载两个场景，标签自定义
python scripts/perf_report.py --kind perf -i idle.json -i load.json --labels 空闲,4路转码 \
    --md r.md --html r.html

# summary：多应用横向
python scripts/perf_report.py --kind summary -i emby.json -i jellyfin.json -i qb.json \
    --labels Emby,Jellyfin,qBittorrent --md r.md --html r.html

# 直接吃压测工具产物（不用先转 stats.json）
python scripts/perf_report.py --kind perf --from-k6 k6_summary.json --html r.html
python scripts/perf_report.py --kind perf --from-jmeter result.jtl --html r.html

# 自定义阈值 + 不通过即非零退出（可挂 CI）
python scripts/perf_report.py --kind perf -i load.json --thresholds my.json \
    --fail-on FAIL --html r.html
```

## 七、源材料的两份完整报告示例（**版式权威参照**）

> 摘自两份性能测试入门材料。下面两份是**源材料里的真实报告样例**，
> 我们自己的 `perf_report.py` 输出与之对齐（见第六节）。

### 7.1 接口性能测试报告（JMeter 压测 / 已压完的场景）

```
# 接口性能测试报告
/api/v1/users/login，3000 并发用户压力测试结果分析

## 测试基本信息
测试接口    /api/v1/users/login      并发用户数  3000
测试时长    30 分钟                   测试时间    2026-01-11 14:30:00
测试工具    JMeter 5.6                测试环境    生产环境

## 核心指标（4 个大卡）
总请求数            5,847,291 requests
平均响应时间        156 milliseconds
成功率              99.87 %
吞吐量              3,248 requests/sec

## 响应时间分布（折线）
横轴：响应时间区间  0-50ms / 50-100 / 100-150 / 150-200 / 200-300 / 300-500 / 500-1000 / >1000ms
纵轴：请求分布(%)
趋势：请求占比在 50~100ms 区间达到峰值，之后随响应时间变长逐步下降。

## 吞吐量趋势（柱状）
横轴：测试时间段  0-5min / 5-10 / 10-15 / 15-20 / 20-25 / 25-30min
纵轴：吞吐量(req/s)
趋势：全时段稳定维持在 3000 req/s 以上，波动很小。

## 详细性能指标（6 个小卡）
最小响应时间 45ms    最大响应时间 2,340ms
90% 响应时间 210ms   95% 响应时间 380ms
99% 响应时间 680ms   错误率 0.13%

## 测试结论
✅ 测试通过
系统在 3000 并发用户下表现稳定，平均响应时间 156ms 满足性能要求（< 200ms），
成功率 99.87% 达到预期标准（> 99.5%），吞吐量 3248 req/s 符合设计指标。
建议继续监控系统资源使用情况，并考虑进行更高并发量的压力测试。
```

**要点**：结论段**逐条对照了目标值**（156<200 ✓、99.87%>99.5% ✓），不是只给一句「通过」。

### 7.2 云容器性能监控（实时监控面板）

```
云容器性能监控 —— 实时监控容器 CPU、内存、网络等关键指标

## 容器基本信息
容器名称 web-api-service   容器 ID a3f5e9c8d2b1   镜像 nginxxlatest
运行状态 运行中             启动时间 2026-01-11 08:30:00   运行时长 6 小时 45 分钟

## 资源指标卡片（4 个，每个带一句状态判语）
CPU 使用率    64.1%       「CPU 使用率正常，负载稳定」
内存使用率    82.3%       「内存使用率较高，建议关注」   ← 超 70% 阈值，判语变了
网络吞吐      1,247 Mbps  「网络传输正常」
磁盘 IO       156 MB/s    「磁盘读写正常」

## 资源使用趋势（折线）
1. CPU & 内存使用率趋势：蓝线=CPU(%)，绿线=内存(%) —— 运行区间稳定，内存持续高位
2. 网络吞吐量趋势：深色=网络输入(Mbps)，浅色=网络输出(Mbps) —— 吞吐稳定

## 实时性能指标（4 个小卡）
请求处理 3,847 req/s   响应时间 45ms（平均）   连接数 1,234   成功率 99.96%

## 系统状态概览
图例：CPU(0-100%) / 内存(0-100%) / 网络吞吐(0-2000Mbps) / 磁盘IO(0-400MB/s)
✅ 系统状态正常
容器运行状态良好，CPU、磁盘 IO 处于正常范围，网络吞吐稳定，内存使用率达到 82.3%，
建议关注内存使用情况，必要时考虑扩容。所有服务正常运行，请求响应时间在正常范围内。
Last updated: 2026/1/11 19:34:01 | Auto refresh every 30 seconds
```

**要点（值得我们照抄的两条）**：

1. **每张资源卡都带一句「状态判语」**，且判语随阈值变化
   （64.1% →「正常」；82.3% →「较高，建议关注」）—— 读者不用自己对照阈值
2. **「系统状态概览」是逐项判语 + 一句总结**，末尾还给数据更新时刻与刷新周期（**数据可追溯**）
