# 瓶颈定位手册

> **本文件解决一个问题**：数据采完、指标算完，然后呢？
> 从「响应时间变长」这类**症状**出发，一步步收敛到**瓶颈到底在哪一维**，
> 最后落成一句能直接写进报告的结论。
> 全部路径来自目标机 12 份实测报告的定位过程，不是教科书推演。

---

## 一、分析四步法

| 步 | 做什么 | 看什么 | 产出 |
|---|---|---|---|
| 1 | **对照阈值** | 逐项比 `metrics.md` 的参考阈值 | 达标 / 不达标 / 未采集 三态 |
| 2 | **观察趋势与拐点** | 曲线形状，不只看均值 | 「响应时间-并发」「吞吐量-并发」曲线上的拐点 |
| 3 | **关联分析定位根因** | 同一时间线对齐压测数据与资源监控 | 瓶颈落到 CPU / 内存 / 磁盘 / 网络 / 应用逻辑 |
| 4 | **关注稳定性** | TPS 平稳度、错误率、内存单调性 | 长稳结论 |

> 第 1 步只能得出「不达标」，**第 2、3 步才回答「为什么」**——报告里最值钱的是后两步。
> 只做第 1 步的报告，读者拿不到任何可执行的优化方向。

## 一·五、源材料的瓶颈分析流程图（**带具体阈值，照这个走**）

> 摘自两份性能测试入门材料。**入口是「先看响应时间是否超标」，再用吞吐量分大类，最后匹配资源阈值。**
> 与下面第二节的「线索 A / 线索 B」是同一套逻辑，这里给出流程与数值。

```
开始分析测试结果
      │
      ▼
判断：响应时间是否超过阈值？
      │
      ├─ 否 ──► 响应时间达标 ──► 结合其他指标评估是否通过测试
      │
      └─ 是 ──► 判断：对应时间的系统吞吐量如何？
                    │
                    ├─ 分支 A：TPS / QPS 显著下降
                    │        │
                    │        ▼
                    │   资源利用率分析 ──► 判断：哪个资源达到瓶颈？
                    │        │
                    │        ├─ CPU 使用率 > 75~80%        ──► CPU 瓶颈：计算能力不足
                    │        ├─ 内存使用率异常高或持续增长   ──► 内存瓶颈：可能存在泄漏
                    │        ├─ 磁盘 I/O 繁忙率 > 70%       ──► 磁盘瓶颈：读写速度慢
                    │        └─ 网络吞吐量接近带宽上限       ──► 网络瓶颈：带宽不足
                    │        │
                    │        └──► 制定优化方案 ──► 结合其他指标评估是否通过测试
                    │
                    └─ 分支 B：TPS / QPS 保持高位
                             │
                             └──► 可能为应用逻辑或数据库瓶颈
                                  ──► 制定优化方案 ──► 结合其他指标评估是否通过测试
```

### 这张图给出的四个资源阈值（**记下来，比笼统的「看资源」有用**）

| 资源 | 判定瓶颈的阈值 |
|---|---|
| **CPU** | 使用率 **> 75~80%** → 计算能力不足 |
| **内存** | 使用率**异常高或持续增长** → 可能存在泄漏 |
| **磁盘 I/O** | **繁忙率 > 70%** → 读写速度慢 |
| **网络** | 吞吐量**接近带宽上限** → 带宽不足 |

> ⚠️ **两套阈值不要混**：本表是**瓶颈判定**（>70% 就该怀疑磁盘）；
> `references/metrics.md` 里的 `%util ≤80%` 是**达标线**（超过才算不合格）。
> **70% 是预警线，80% 是不合格线** —— 报告里说「逼近瓶颈」用 70%，说「不达标」用 80%。

## 二、瓶颈决策树

从**症状**出发，先分两条线索，再各自收敛到具体维度。

### 线索 A：响应时间变长 + TPS/QPS 上不去甚至下降

→ 这是**资源饱和**的典型特征。**立即看服务端资源监控图**，按下面顺序排：

```
响应时间↑ 且 吞吐量↓
        │
        ├─ CPU 持续 >80% 且 %iowait 很低
        │     └→ 瓶颈 = CPU 计算能力不足
        │        对策：代码优化（算法/锁/序列化）或 加 CPU
        │
        ├─ 内存持续增长且不释放
        │     └→ 瓶颈 = 内存泄漏
        │        对策：查代码（对象生命周期 / 连接未释放 / 缓存无上限）
        │
        ├─ 磁盘 I/O 等待时间长（%iowait 高、await 高、写队列积压）
        │     └→ 瓶颈 = 数据库或文件读写
        │        对策：优化查询 / 加索引 / 换更快存储 / 减少落盘
        │
        └─ 网络贴住线速（千兆 ≈ 119 MB/s）
              └→ 瓶颈 = 网卡
                 对策：升级网卡 / 多网卡分流 / 减少传输量
```

| 资源特征 | 判定瓶颈 | 下一步动作 |
|---|---|---|
| CPU >80%，`%iowait` 低 | **CPU 计算能力不足** | 拆 `%us` / `%sy`：用户态高→应用计算密集；系统态高→上下文切换过多 |
| 内存只增不减、无回落 | **内存泄漏** | 看 `private_Dirty` 单调性，见 `memory-accounting.md` |
| `%iowait` 高 / `%util` 高 / `await` 高 | **磁盘 I/O** | 区分是数据库查询慢还是落盘量大 |
| 网络贴线速（119 MB/s 级） | **网卡** | 此时优化 CPU 是白费力气 |

> 四条可能同时出现（如磁盘慢导致 CPU 大量等待），要按**时间线先后**定主因，别急着下单条结论。

### 线索 B：响应时间变长，但 TPS/QPS 平稳、资源利用率也不高

→ 这是**最容易被写成「无瓶颈」的一类，其实是错的**。
资源都不高却慢，说明时间耗在了**等**上面，瓶颈在应用自身之外的某一环：

| 怀疑对象 | 怎么确认 |
|---|---|
| **慢 SQL / 数据库查询效率** | 开慢查询日志；看单请求 SQL 条数与耗时 |
| **外部服务依赖**（第三方接口、认证、DNS） | 链路打点，看一次请求里各段耗时占比 |
| **锁竞争 / 线程池耗尽** | 看线程 dump、连接池活跃数、等待队列长度 |
| **同步阻塞调用** | 请求被串行化：并发上不去，资源也不高 |

> **判据**：资源利用率低 + 响应时间长 = **时间不在算上，在等上**。
> 这类问题加机器无效，必须先定位到具体是哪一段在等。

## 三、吞吐量与响应时间的权衡（拐点）

| 阶段 | 并发用户数 ↑ 时 | 说明 |
|---|---|---|
| 资源未饱和 | 吞吐量 **上升**，响应时间变化不大 | 系统还有余量，加并发是「免费的」 |
| 到达瓶颈 | 吞吐量 **趋于平缓甚至下降**，响应时间 **急剧上升** | **这个拐点就是系统的最佳并发点** |

**怎么找**：画两张曲线——

- 「响应时间 - 并发用户数」
- 「吞吐量 - 并发用户数」

拐点即两条曲线开始背离的位置。**报告里必须给出这个点**，否则读者不知道系统该按多少并发设计。

> ⚠️ 只在单一并发数上跑一次，是**找不到拐点**的。至少跑 3~4 个并发档位（阶梯压测）。

## 四、稳定性的三个观察点

| # | 看什么 | 判据 |
|---|---|---|
| 1 | **TPS 曲线平稳度** | 平稳、无大幅波动（波动大 = 存在周期性阻塞或资源争抢） |
| 2 | **错误率** | 在可控范围内（参考 ≤0.2%） |
| 3 | **内存使用率**（**特别是 `private_Dirty`**） | 无持续增长趋势；增长即疑泄漏 |

> 第 3 点务必用 `private_Dirty` 而非 RSS——RSS 会被页缓存撑大，拿 RSS 看趋势会得出
> 「内存缓慢增长」的假警报。详见 `memory-accounting.md`。

## 五、症状 → 怀疑对象 速查表

| 症状 | 首选怀疑 | 下一步查什么 |
|---|---|---|
| 响应慢 + CPU 高 | **计算瓶颈** | 拆 `%us` / `%sy`；定位热点函数、GC 频率 |
| 响应慢 + CPU 低 + `%iowait` 高 | **磁盘 I/O** | `iostat -x` 的 `%util` / `await`；慢查询日志 |
| 响应慢 + 资源都不高 | **应用逻辑 / 慢 SQL / 外部依赖** | 链路打点；SQL 条数；第三方接口耗时 |
| 内存只增不减、无回落 | **内存泄漏** | `private_Dirty` 单调性 + churn 复测（见 `app-lifecycle.md`） |
| swap 增长但 PSS 很小 | **深度空闲**（**不是压力**） | 看 CPU/磁盘是否近零；写出「首次请求有换入延迟」的推论 |
| RSS 巨大但 `RssFile` 占比高 | **页缓存**（**不是压力**） | 算 `RssFile ÷ RSS`；改用 `private_Dirty` 判压力 |
| 网络贴住线速 | **网卡** | 对比带宽上限；确认是整机口径（不可归因单应用） |
| 错误率非零 | **先分三类** | 超时 / 连接拒绝 / 5xx 代码异常——三者根因完全不同 |

> 表中后四条都是**「看着像问题、其实不是」**的经典误判：写报告时要么给出辩解，要么别写。
> 实测报告里 qBittorrent 的 OOM 误判、Jellyfin 的 swap 误判都出在这一栏。

## 六、结论话术模板

直接套用，把 `<>` 换成实测数字。

### 达标类

- 「在 **N** 并发下，CPU 均值 **X%**、P95 响应时间 **Y ms**、错误率 **Z%**，各项均满足阈值，**判定通过**。」
- 「监控窗口内进程 **P** 的 `private_Dirty` 全程恒定于 **X MB**，峰值/均值波动 < **N%**，**无泄漏迹象**。」

### 不达标类

- 「响应时间随并发上升至 **N** 后急剧抬升，同时 CPU 达到 **X%**（超过 70% 阈值），
  **瓶颈定位在 CPU 计算能力**，该并发即**最佳并发点**。」
- 「并发升至 **N** 后吞吐量趋平而响应时间翻倍，**系统已过拐点**；此时磁盘 `%iowait` 为 **X%**、
  `await` 为 **Y ms**，**瓶颈定位在磁盘 I/O**。」
- 「资源利用率均低于阈值（CPU **X%**、内存 **Y%**、`%iowait` **Z%**）而响应时间超标 **N** 倍，
  **瓶颈不在资源，而在应用逻辑或外部依赖**，建议按链路打点进一步定位。」

### 需复测类

- 「本次窗口 **N** 分钟内空载段占比 **X%**，均值已被窗口构成污染，
  **改按稳态时段口径重算后再下结论**。」
- 「指标 **M** 未采集（原因：…）。**未采集 ≠ 达标**，本次不对该项作判定，建议补采后复测。」

> 最后一类最容易被省略，但它决定了报告可不可信。见 `methodology-pitfalls.md` 的「写报告时的红线」。
