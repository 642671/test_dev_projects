# 统计 JSON 字段契约（`*_stats.json`）

> **谁产出它**：`scripts/perf_analyze.py`（CSV → 统计 JSON）。
> **谁消费它**：`scripts/perf_report.py`（→ `.md` + 自包含 `.html`）。
> **为什么要这份契约**：报告脚本是**纯标准库**、只认字段名不认来源。只要 JSON 长成下面这样，
> 不管是脚本算出来的、还是**手工写的**，都能出报告 —— 这条是「手写 results.json」那一节的前提。

---

## 二、逐字段说明

### 2.1 顶层

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `app` | str | 否 | 应用名。报告标题与 `label` 的兜底来源 |
| `tag` | str | 否 | 标签（默认采集当天 `YYYYMMDD`，生命周期里是阶段名 `P0`~`P5`） |
| `generated` | str | 否 | 生成时刻 `YYYY-MM-DD HH:MM:SS` |
| `quality` | obj | 否 | 采集质量，见 2.2 |
| `procs` | obj | **是** | 进程组字典，**键是进程组名**，值见 2.3。没有它报告就是空的 |
| `thresholds` | obj | 否 | 覆盖默认阈值（同 `--thresholds` 文件），键见 `perf_report.py` 的 `DEFAULT_THRESHOLDS` |
| `coverage` | list | 否 | 采集覆盖度，每项 `{"item","status","reason"}`，`status` ∈ `OK` / `DEGRADED` / `NA` |
| `analysis` | obj | 否 | 人工分析，`{"bottleneck","evidence":[],"suggestions":[],"withdrawn":[]}` |
| `leak` | obj | 否 | 泄漏判定（有则优先于从 `growth` 推） |
| `amplification` | list | 否 | 放大倍数；不给则由报告脚本按前两个场景自动算 |

### 2.2 `quality` —— 采集质量

| 字段 | 类型 | 说明 |
|---|---|---|
| `files` | int | 参与的 CSV 文件数 |
| `bad_rows` | int | **被剔除的坏行数**（时间列解析失败、或数值列粘连的行）。>0 时报告要提一句 |
| `samples` | int | 有效样本总数（各进程组之和） |
| `notes` | str | 口径备注，报告「口径声明」会带上 |

### 2.3 `procs.<进程组名>` —— 每个进程组的统计

进程组名由采集侧决定：单进程是进程名（`mediaindex`），多实例是 `<名>#1`/`<名>#2`，
合计是 `<名>(合计)`。**报告优先取「合计」那条**（名字里含「合计」），否则取第一条。

| 字段 | 类型 | 说明 |
|---|---|---|
| `segments` | list | 数据来源明细，每项 `{"file","n","window":[起,止]}`。可追溯「这个数是哪几个 CSV 来的」 |
| `samples` | int | 该进程组的有效样本数 |
| `window` | [str,str] | 实际采集窗口 `["2026-09-13 10:00:00","2026-09-13 10:04:59"]` |
| `series` | obj | 抽稀后的时间序列，供报告画内联 SVG，见 2.4 |
| `usage` / `idle` | obj | 使用期 / 空闲期拆分，见 2.5 |
| `peak_time` | obj | 各指标的**峰值发生时刻**，键与指标同名。**峰值必须带时刻** |
| `growth` | obj | 内存增长判据，见 2.6 |
| `cpu` / `pss` / `rss` / `pvt` / `anon` / `file` / `swap` / `disk_r` / `disk_w` / `tx` / `rx` / `tree` | obj | 各指标的 `{peak, avg, p95, p99}`，见 2.7 |
| `tx_total_MB` / `rx_total_MB` | float | 网络累计量（均值 × 样本数 × 采样间隔 积分得到） |

### 2.4 `series` —— 时间序列

| 键 | 说明 |
|---|---|
| `t` | 时间戳数组，**只保留 `HH:MM:SS`**（省体积）；与各指标数组**按下标一一对应** |
| `cpu` / `pss` / `rss` / `pvt` / `anon` / `file` / `swap` / `disk_r` / `disk_w` / `tx` / `rx` / `tree` | 数值数组，长度与 `t` 相同 |

⚠️ **数组里的 `null` 是「这一秒没采到」，不是 0。** 报告画图时会**断线分段**，
不会把缺口连成 0 —— 否则曲线周期性掉 0 会得出完全相反的结论。

### 2.5 `usage` / `idle` —— 使用期 vs 空闲期

判定口径（写死在 `perf_analyze.py`，报告里会回显）：
**CPU > 2% 或 磁盘读写合计 > 0.5 MB/s 或 网络收发合计 > 0.5 MB/s = 使用**。

| 字段 | 说明 |
|---|---|
| `seconds` | 该状态的**样本数**（1 秒采样时等于秒数） |
| `ratio_pct` | 占比 % |
| `cpu_avg` | 该状态下的 CPU 均值（**单核口径**） |
| `pss_avg` / `pvt_avg` | 该状态下的 PSS / private_Dirty 均值（MB） |
| `disk_w_avg` | 该状态下的磁盘写均值（MB/s） |

### 2.6 `growth` —— 内存是否随窗口增长（泄漏判据）

| 字段 | 说明 |
|---|---|
| `first_mb` / `last_mb` | **首段 / 末段各 1/4 样本**的均值（不是首尾单点 —— 单点噪声极大：GC、一次性缓冲） |
| `delta_mb` | `last_mb - first_mb` |
| `monotonic` | 单调度：相邻递增的占比（0~1，>0.6 才算「一路在涨」） |
| `verdict` | `无增长` / `有抬升但非单调，建议延长窗口复测` / `疑泄漏` / `样本不足`（<8 个样本时） |

判据：**`delta` 超过 `max(2.0 MB, first×5%)` 且 `monotonic > 0.6` 才判「疑泄漏」**。
空闲期内存不归零属正常设计，只要**无单调爬升**即可判无泄漏。

### 2.7 指标统计块 `{peak, avg, p95, p99}`

| 字段 | 说明 |
|---|---|
| `peak` | 最大值。**报告里一定会和 `peak_time` 一起出现** |
| `avg` | 算术均值 |
| `p95` / `p99` | 分位数，**线性插值**（与既有报告口径一致） |

## 三、手工写 results.json（没有 stats.json 也能出报告）

**可以不给 `procs`，直接手写一份带 `metrics` 块的最小 JSON** ——
形状是 `metrics[指标名][场景名] = {avg, peak, p95, p99}`，
`perf_report.py` **两种形状都吃**（见 `normalize()`）。

```json
{
  "kind": "perf",
  "meta": {
    "title": "MultimediaServer · 空载 vs 负载",
    "device": "TOS 6 · 10.18.15.179 · 4 核",
    "cpu_scope": "单核口径（100% = 1 个核；4 核跑满 = 400%）",
    "interval_s": 1
  },
  "metrics": {
    "cpu":  { "空闲": { "avg": 0.4 }, "负载": { "avg": 297.75 } },
    "pss":  { "空闲": { "avg": 23.5 }, "负载": { "avg": 97.4 } },
    "pvt":  { "空闲": { "avg": 8.72 }, "负载": { "avg": 41.2 } },
    "disk_w": { "空闲": { "avg": 0.01 }, "负载": { "avg": 12.6 } }
  },
  "coverage": [
    { "item": "Full GC 次数", "status": "NA", "reason": "本机 JRE 未开 GC 日志，无该指标" }
  ]
}
```

要点：

- **场景名（`空闲` / `负载`）就是报告的列名**，两个场景自动出「放大倍数」章节
- `kind` 可省：给两个场景时默认按 `perf`，一个场景按 `monitor`；也可用 `--kind` 强制
- 想按项目验收标准判定，加 `--thresholds my.json` 覆盖默认阈值
- 想进 CI，加 `--fail-on FAIL`（总判定不通过则退出码 1）

## 四、缺字段怎么办

**所有字段都是可选的。** 报告脚本用 `dig()` 按 `a.b.c` 安全取值，
任一层缺失都返回 `None`，**不会崩、也不会填 0**：

| 情况 | 报告里的表现 |
|---|---|
| 整块指标缺（如没有 `swap`） | 该行显示「未采集」，判定 **`NA`** |
| `series` 缺或点数 < 2 | 趋势图位置显示「（采样点不足 2 个，无法绘制趋势）」，其余章节照常 |
| `growth` 缺 | 「内存回落与泄漏判定」章节整节不出现 |
| `usage` / `idle` 缺 | 「使用期间 vs 空闲期间」整节不出现 |
| `peak_time` 缺 | 峰值照常显示，时刻列显示 `—` |
| `quality` 缺 | 概况表相应行为 `—` |

**红线两条：**

1. **缺指标判 `NA`，绝不升级成 `FAIL`。** 采不到 Full GC ≠ Full GC 超标 ——
   误判会让团队去修一个不存在的故障。
2. **采不到不许填 0。** 0 会被读成「实测值为 0」。缺的指标一律进报告的
   「采集覆盖度与未测项」章节，并写清原因。

## 五、单位约定

| 维度 | 单位 | 口径 |
|---|---|---|
| CPU | `%` | **单核口径**：100% = 1 个核，4 核跑满 = 400%。跨报告比较前必须确认这一条 |
| 内存（pss / rss / pvt / anon / file / swap） | `MB` | 判压力用 `pvt`(private_Dirty) 或 `pss`，**不要用 `rss`**（含可回收的页缓存） |
| 磁盘 / 网络（disk_r / disk_w / tx / rx） | `MB/s` | 速率 |
| 网络（tx / rx） | —— | **整机口径**，Linux 没有逐进程网络计数，**不可归因给单个应用** |
| `tree` | `个` | 进程树**进程个数**（父 + 全部子孙），不是内存 |
| `tx_total_MB` / `rx_total_MB` | `MB` | 窗口内累计传输量 |
| 累计量 / 响应的百分位 | —— | `p95` / `p99` 为**线性插值**分位数 |

> 阈值（`cpu_pct` 70、`p95_rt_ms` 500 等）都是**业界参考值，不是业务验收标准**，
> 报告里会显式回显这一点。完整口径与阈值见 `references/metrics.md`。
