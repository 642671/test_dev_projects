# 生命周期

> **为什么按生命周期切**：同一个应用，「装着没跑」「跑着没任务」「跑着有任务」三种状态的资源画像
> **完全不同**，混在一起采只会得到一份说不清的数字。
> 本技能把它切成 **P0~P5 六个阶段**，每阶段定死采集口径与通过判据，由
> `scripts/perf_lifecycle.py` 编排。

---

## 一、六阶段总表

| 阶段 | 名称 | 做什么 | 谁触发 | 采集口径 | 产出 |
|---|---|---|---|---|---|
| **P0** | `pre_install` | 未安装态基线：断言应用**确实没装**、记**整机基线**（默认 5 min）、记**已装应用清单**、记设备规格 | 脚本自动 | 整机 | `P0_host.csv` |
| **P1** | `install` | 安装过程：全程 **1s 采样**，记耗时、CPU/磁盘峰值、**进程出现时刻** | **人工触发安装** | 整机（持续采到进程出现 + 收尾 60s） | `P1_install_host.csv` |
| **P2** | `idle` | 安装后**空载默认占用**：静置 2 min（让首次初始化扫描收敛）后采 5 min | 脚本自动 | **进程树** | `P2_<app>.csv` |
| **P3** | `load` | **负载态**：人工发起任务，采 10 min | **人工发起任务** | **进程树** | `P3_<app>.csv` |
| **P4** | `leak` | 停任务 → 采**回落曲线** → **churn** → 判泄漏 | 脚本 + 人工建拆 | 进程树 + cgroup | `P4_churn.json` |
| **P5** | `post_uninstall` | 卸载后**残留**检查（**默认不跑**） | **人工卸载** | 整机 + 进程 | `P5_post_uninstall_host.csv` |

> **P2 与 P3 的差值是本技能最核心的一个数**：「放大倍数 = 负载期均值 ÷ 空载期均值」，CPU 与内存各一份。
> **没有 P2 就没有分母，放大倍数就出不来**——别只跑 P3。

---

## 二、每阶段的通过判据与常见误判

| 阶段 | 通过判据 | 常见误判 |
|---|---|---|
| **P0** | 应用进程**确实不存在**；已装应用清单已留档 | 忘了记清单 → 后续窗口混进别的应用的负载，无法归因 |
| **P1** | 安装**成功结束**且能定位到**进程出现时刻**；耗时/峰值带 `peak_time` | 把**解包/编译**的一次性 CPU 峰值当成常驻开销 |
| **P2** | **内存不随窗口增长**；得到一份干净的空载基线 | 把**首次初始化扫描**的一次性动作当成稳态占用（Emby 首次启动含媒体库扫描，数值偏保守） |
| **P3** | 负载**确实压上了**（有并发/连接数/传输量佐证）；与 P2 算出放大倍数 | 负载没跑起来 → 测出「CPU 接近 0」的假象 |
| **P4** | **多轮拆除后水位不单调上升**；空闲期能回落 | 把**空闲期不归零**当成泄漏（属正常设计） |
| **P5** | 卸载后**无残留进程 / 无残留目录与配置** | 只看进程不看文件 → 漏掉残留数据目录 |

> ⚠️ P2 的「静置 2 分钟」不是可选项：安装完的头两分钟应用在**建索引 / 初始化库 / 首次扫描**，
> 这期间采到的数字不叫「空载默认占用」。

## 三、为什么安装 / 卸载必须人工触发

| 原因 | 说明 |
|---|---|
| **不同应用安装方式不一** | 应用中心的、命令行的、上传包的，路径与交互都不同，脚本代劳等于把不确定性写进代码 |
| **卸载可能丢配置 / 丢数据** | 卸载是不可逆动作，脚本误触发的代价远大于省下的那一次点击 |
| **需要人判断「装完了没」** | 安装成功的判据是**人能确认应用可用**，不是进程出现就完事 |

> ⚠️ **脚本只做两件事：监控 + 打点。** 每到闸门停下来等人，人做完动作再继续。
> 本技能所有采集都是**只读**的，脚本不会替你去装、去卸、去改任何配置。

## 四、`perf_lifecycle.py` 用法（可直接复制）

```bash
# 1) 完整六阶段（最常用）：P0~P4 串起来，闸门处等人操作
python scripts/perf_lifecycle.py --app Emby --phases P0,P1,P2,P3,P4 --out-dir ./perf-out

# 2) 只补采空载基线（应用已装好，不重跑安装过程）—— 数据可拼接
python scripts/perf_lifecycle.py --app Emby --phases P2 --settle-min 5 --out-dir ./perf-out

# 3) 泄漏专项：加大 churn 轮数、拉长保持期
python scripts/perf_lifecycle.py --app Emby --phases P4 --rounds 8 --hold-s 60 --rest-s 30 \
    --out-dir ./perf-out

# 4) 远程采集（凭据走 TOS_HOST / TOS_USER / TOS_PASS / TOS_PORT，不写进命令）
TOS_HOST=<被测机IP> TOS_USER=<用户> TOS_PASS=<口令> TOS_PORT=9222 \
  python scripts/perf_lifecycle.py --app Emby --phases P0,P1,P2,P3,P4 --remote --out-dir ./perf-out

# 5) 非交互（CI）：每到闸门等文件出现，出现即继续并自动删除
python scripts/perf_lifecycle.py --app Emby --phases P0,P1 --wait-file /tmp/gate.ok --out-dir ./perf-out

# 6) 只采集不出报告
python scripts/perf_lifecycle.py --app Emby --phases P2 --no-report --out-dir ./perf-out
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--app` | 必填 | 应用名 / 进程正则，用于进程树匹配 |
| `--phases` | `P0,P1,P2,P3,P4` | **可单跑任一阶段**，数据与既有产物可拼接 |
| `--out-dir` | `perf-lifecycle` | 产物目录 |
| `--remote` | 关 | 经 SSH 到被测机采集 |
| `--wait-file <路径>` | — | **非交互闸门**：轮询该文件，出现即放行并自动删除 |
| `--yes` | 关 | 闸门全部直接放行，**慎用**——会跳过人确认安装/卸载 |
| `--settle-min` | `2` | P2 前**静置分钟数**（等首次初始化扫描收敛） |
| `--p0-min` / `--p1-max-min` / `--p1-settle` | 5 / 20 / 60 | P0 基线分钟数 / P1 最长分钟数 / P1 收尾秒数 |
| `--p2-min` / `--p3-min` / `--p5-min` | 5 / 10 / 3 | 各阶段采集分钟数 |
| `--cool-min` / `--rounds` / `--hold-s` / `--rest-s` | 3 / 5 / 15 / 20 | P4 回落分钟数 / churn 轮数与节奏 |
| `--no-report` | 关 | 只采集，不出报告 |

> ⚠️ `--wait-file` 是给**非交互场景**（外部编排系统在「安装完成」后 `touch` 一下推进流程）用的。
> 纯本地交互调试用默认行为即可（回车放行）。

## 五、P0 要记什么

| # | 记什么 | 为什么 |
|---|---|---|
| 1 | **断言应用确实没装** | 这是「安装带来多少开销」的**零基准**；装过了就没法再回到 P0 |
| 2 | **整机基线**（默认 5 min） | 没有整机基线，后面无法判断「是应用占的，还是系统本来就占的」 |
| 3 | **已装应用清单** | **防串味**：后续窗口里混进别的应用的负载，就没法归因了 |
| 4 | **设备规格** | 核数（CPU 单核口径换算要用）、内存、磁盘类型、网卡速率 |
| 5 | 采集时的系统时间与时区 | 多机数据对齐、峰值时刻标注要用 |

> ⚠️ P0 是**一次性机会**——应用装上之后再补采就不是 P0 了。
> 所以 `--phases` 里千万别把 P0 漏掉，也别为了省 5 分钟跳过它。

## 六、P1 怎么捕获安装过程

```
人工开始安装
      │
      ▼
┌─────────────────────────────────────────────┐
│  整机口径 1s 采样（长窗口，上限 --p1-max-min）  │
│  每轮检查：目标进程出现了吗？                   │
│      否 → 继续采                              │
│      是 → 记录【进程出现时刻】打点              │
│           再收尾 --p1-settle 秒（默认 60s）     │
│           然后自动停采                          │
└─────────────────────────────────────────────┘
      │
      ▼
  P1_install_host.csv + 进程出现时刻
```

| 要产出 | 怎么用 |
|---|---|
| **安装耗时** | 从开始到进程出现的时长，报给业务方 |
| **CPU / 磁盘峰值 + `peak_time`** | ⚠️ **必须带发生时刻**，否则会把**解包/编译**的一次性峰值误读成常驻开销 |
| **进程出现时刻** | P2 静置窗口的起算点 |
| 进程树规模变化 | 安装过程中 fork 出的辅助进程也要记录 |

> ⚠️ P1 采的是**整机口径**（`--scope host`）——安装阶段应用进程还没起来，进程树口径采不到东西。

## 七、P4 判据去哪看

P4 的泄漏判定（churn 轮次设计、拆除后水位单调性、四条反误判、长稳）**不在本文件**，
详见 `<泄漏检测>/SKILL.md`。

本文件只管把 P4 的**数据采回来**：回落曲线（`P4_cooldown_<app>.csv`）与 churn 打点
（`P4_churn.json`，含 `rounds` / `baseline_mb` / `drift_mb` / `verdict`）。
