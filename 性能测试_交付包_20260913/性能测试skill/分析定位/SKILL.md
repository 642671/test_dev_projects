# 分析定位

> 数据采完、指标算完，然后呢？本文件解决**从「响应时间变长」这类症状收敛到瓶颈在哪一维**，
> 最后落成一句能直接写进报告的结论。完整决策树见 `references/analysis-playbook.md`。

---

## 一、分析四步法

| 步 | 做什么 | 看什么 | 产出 |
|---|---|---|---|
| 1 | **对照阈值** | 逐项比 `references/metrics.md` 的参考阈值 | 达标 / 不达标 / 未采集 三态 |
| 2 | **观察趋势与拐点** | 曲线形状，不只看均值 | 「响应时间-并发」「吞吐量-并发」的拐点 |
| 3 | **关联分析定位根因** | 同一时间线对齐压测数据与资源监控 | 瓶颈落到 CPU / 内存 / 磁盘 / 网络 / 应用逻辑 |
| 4 | **关注稳定性** | TPS 平稳度、错误率、内存单调性 | 长稳结论 |

> ⚠️ 第 1 步只能得出「不达标」，**第 2、3 步才回答「为什么」**——报告里最值钱的是后两步。
> 只做第 1 步的报告，读者拿不到任何可执行的优化方向。

## 二、瓶颈决策树

从**症状**出发，先分两条线索，再各自收敛到具体维度。

### 线索 A：响应时间变长 **且** TPS/QPS 上不去甚至下降

→ 这是**资源饱和**的典型特征。**立即看服务端资源监控图**，按下面顺序排：

```
响应时间↑ 且 吞吐量↓
        │
        ├─ CPU 持续 >80% 且 %iowait 很低
        │     └→ 瓶颈 = CPU 计算能力不足
        │        对策：代码优化（算法 / 锁 / 序列化）或加 CPU
        │
        ├─ 内存持续增长且不释放
        │     └→ 瓶颈 = 内存泄漏
        │        对策：查代码（对象生命周期 / 连接未释放 / 缓存无上限）
        │
        ├─ 磁盘 I/O 等待时间长（%iowait 高、await 高、写队列积压）
        │     └→ 瓶颈 = 数据库或文件读写
        │        对策：优化查询 / 加索引 / 换更快存储 / 减少落盘
        │
        └─ 网络贴住线速（千兆 ≈ 119 MB/s）
              └→ 瓶颈 = 网卡
                 对策：升级网卡 / 多网卡分流 / 减少传输量
```

| 资源特征 | 判定瓶颈 | 下一步动作 |
|---|---|---|
| CPU >80%，`%iowait` 低 | **CPU 计算能力不足** | 拆 `%us` / `%sy`：用户态高→应用计算密集；系统态高→上下文切换过多 |
| 内存只增不减、无回落 | **内存泄漏** | 看 `private_Dirty` 单调性，见 `<泄漏检测>/SKILL.md` |
| `%iowait` 高 / `%util` 高 / `await` 高 | **磁盘 I/O** | 区分是数据库查询慢还是落盘量大 |
| 网络贴线速（119 MB/s 级） | **网卡** | 此时优化 CPU 是白费力气 |

> ⚠️ 四条可能**同时出现**（如磁盘慢导致 CPU 大量等待），要按**时间线先后**定主因，
> 别急着下单条结论。

### 线索 B：响应时间变长，**但 TPS 平稳、资源利用率也不高**

→ 这是**最容易被写成「无瓶颈」的一类，其实是错的**。资源都不高却慢，
说明时间耗在了**等**上面，瓶颈在应用自身之外的某一环：

| 怀疑对象 | 怎么确认 |
|---|---|
| **慢 SQL / 数据库查询效率** | 开慢查询日志；看单请求 SQL 条数与耗时 |
| **外部服务依赖**（第三方接口、认证、DNS） | 链路打点，看一次请求里各段耗时占比 |
| **锁竞争 / 线程池耗尽** | 看线程 dump、连接池活跃数、等待队列长度 |
| **同步阻塞调用** | 请求被串行化：并发上不去，资源也不高 |

> **判据**：资源利用率低 + 响应时间长 = **时间不在算上，在等上**。
> ⚠️ 这类问题**加机器无效**，必须先定位到具体是哪一段在等。

## 三、拐点：吞吐量与响应时间的权衡

| 阶段 | 并发用户数 ↑ 时 | 说明 |
|---|---|---|
| 资源未饱和 | 吞吐量 **上升**，响应时间变化不大 | 系统还有余量，加并发是「免费的」 |
| 到达瓶颈 | 吞吐量 **趋平甚至下降**，响应时间 **急剧上升** | **这个拐点就是系统的最佳并发点** |

**怎么找**：画两张曲线——「响应时间 - 并发用户数」与「吞吐量 - 并发用户数」。
拐点即两条曲线**开始背离**的位置。

```bash
# 阶梯压测：3~4 个并发档位，每档出 stats.json，再横向到一张汇总报告
python scripts/perf_report.py --kind summary \
  -i s10.json -i s50.json -i s100.json -i s200.json \
  --labels 并发10,并发50,并发100,并发200 --md 阶梯.md --html 阶梯.html
```

> ⚠️ **只在单一并发数上跑一次，是找不到拐点的。** 至少跑 **3~4 个并发档位**。
> ⚠️ 报告里**必须给出这个点**，否则读者不知道系统该按多少并发设计。

## 四、放大倍数：怎么算、怎么解释

```
放大倍数 = 负载期均值 ÷ 空载期均值      ← CPU 与内存各一份
```

| 项 | 说明 |
|---|---|
| **分母从哪来** | P2 空载基线（见 `<生命周期>/SKILL.md`）——**没有 P2 就没有放大倍数** |
| 怎么算 | 两次采集产物各自跑 `perf_analyze.py` 出 `stats.json`，相应字段相除 |
| 怎么解释 | N 倍 = 负载把该应用的开销抬到了空载的 N 倍；**倍数本身没有绝对好坏**，要看业务能不能接受 |
| 内存口径 | 一律用 **`private_Dirty`**，不要用 RSS（页缓存会污染） |

> ⚠️ **窗口不同、素材不同时不宜作精确比较。** 实测教训：4 路全转码占 2.8 核，
> 13 路混合只占 0.9 核——差异在**素材能否硬件解码**。
> 报告里必须写清负载的**编码格式与解码路径**，并注明两次窗口的构成是否一致。

## 五、症状 → 怀疑 → 下一步 速查表

| 症状 | 首选怀疑 | 下一步查什么 |
|---|---|---|
| 响应慢 + CPU 高 | **计算瓶颈** | 拆 `%us` / `%sy`；定位热点函数、GC 频率 |
| 响应慢 + CPU 低 + `%iowait` 高 | **磁盘 I/O** | `iostat -x` 的 `%util` / `await`；慢查询日志 |
| 响应慢 + 资源都不高 | **应用逻辑 / 慢 SQL / 外部依赖** | 链路打点；SQL 条数；第三方接口耗时 |
| 内存只增不减、无回落 | **内存泄漏** | `private_Dirty` 单调性 + churn 复测 |
| swap 增长但 PSS 很小 | **深度空闲（不是压力）** | 看 CPU / 磁盘是否近零；写出「首次请求有换入延迟」的推论 |
| RSS 巨大但 `RssFile` 占比高 | **页缓存（不是压力）** | 算 `RssFile ÷ RSS`；改用 `private_Dirty` 判压力 |
| 网络贴住线速 | **网卡** | 对比带宽上限；确认是**整机口径**（不可归因单应用） |
| 错误率非零 | **先分三类** | 超时 / 连接拒绝 / 5xx——三者根因完全不同 |
| TPS 平稳但响应时间翻倍 | **已过拐点前兆** | 看并发是否已接近拐点；查队列 / 锁等待 |

> ⚠️ 表中「不是压力」的那两条是**经典误判**：写报告时要么给出辩解，要么别写。
> 实测报告里某做种应用的 OOM 误判、某媒体服务的 swap 误判都出在这一栏。

## 六、结论话术模板（`<>` 换成实测数字）

**达标类**

- 「在 **N** 并发下，CPU 均值 **X%**、P95 响应时间 **Y ms**、错误率 **Z%**，各项均满足阈值，**判定通过**。」
- 「监控窗口内进程 **P** 的 `private_Dirty` 全程恒定于 **X MB**，峰值/均值波动 < **N%**，**无泄漏迹象**。」

**不达标类**

- 「响应时间随并发上升至 **N** 后急剧抬升，同时 CPU 达到 **X%**（超过 70% 阈值），
  **瓶颈定位在 CPU 计算能力**，该并发即**最佳并发点**。」
- 「并发升至 **N** 后吞吐量趋平而响应时间翻倍，**系统已过拐点**；此时磁盘 `%iowait` 为 **X%**、
  `await` 为 **Y ms**，**瓶颈定位在磁盘 I/O**。」
- 「资源利用率均低于阈值（CPU **X%**、内存 **Y%**、`%iowait` **Z%**）而响应时间超标 **N** 倍，
  **瓶颈不在资源，而在应用逻辑或外部依赖**，建议按链路打点进一步定位。」

**需复测类**

- 「本次窗口 **N** 分钟内空载段占比 **X%**，均值已被窗口构成污染，
  **改按稳态时段口径重算后再下结论**。」
- 「指标 **M** 未采集（原因：…）。**未采集 ≠ 达标**，本次不对该项作判定，建议补采后复测。」

> ⚠️ 最后一类**最容易被省略，但它决定了报告可不可信**。
