## 二、核心结论

| 问题 | 答案 |
|---|---|
| 装了这个应用，NAS 多占多少？ | **PSS 31.5 MB / private_Dirty 8.4 MB**（RSS 48 MB 里 40 MB 是可回收页缓存） |
| 推流吃性能吗？ | **几乎不吃**。单路 1080p → CPU **0.02%**；打满千兆 → CPU **仅 4%** |
| 瓶颈在哪？ | **千兆网卡线速**。实测发送峰值 **118.95 MB/s ≈ 951.6 Mbps**，贴住线速 |
| 能扛多少路？ | 按码率算：1080p ≈1.5 MB/s，千兆理论上限 **≈79 路**，建议留 30% 余量 → **≤55 路** |
| 有内存泄漏吗？ | **无**。**47.9 分钟**长窗口 private_Dirty 未升反降（−2.25 MB），单调度 0.018 |
| 索引重建重不重？ | **轻**。`mediaindex` 扫描 61 个视频期间 CPU 0~2% |

## 五、必须知道的口径与坑（本案例实测）

1. **网络是整机口径** —— Linux 没有逐进程网络计数，CSV 里的网络列取自整机数据，**不可归因单应用**。
2. **判内存压力用 `private_Dirty`，不要用 RSS** —— RSS 48 MB 里 40 MB（83%）是可回收的页缓存。
3. **`mediaindex` 不在应用进程树内** —— 索引与媒体库跑在独立 systemd 服务里。只盯 `MultimediaServer` 会漏采。采集要用 `--app "MultimediaServer|mediaindex|mediadb"`。
4. **MiniDLNA 每连接 fork 一个进程** —— 并发 8 路时进程树从 4 涨到 11，属正常，不是泄漏。
5. **启动应用会重启 `mediaindex`** —— PID 变更、内存基线重置。
6. **小文件全速拉取会让客户端「合计速度」虚高** —— 那是各路平均速度相加；**并发吞吐必须以服务端实测为准**。
7. **该设备是共用设备** —— 测试期间存在他人操作的可能（SSH 日志见 `10.18.15.203` 等）。

## 六、采集器已知问题（已修，但本案例早期数据受影响）

`perf_collect.py` 的 `--app` 是正则，而采集器自己的命令行里就含这个正则
（`python3 perf_collect.py --app MultimediaServer`），**会匹配到自身**，把采集器的
CPU/内存算进被测进程树 —— 实测凭空多出 1 个进程、约 12 MB PSS。

**已在 `perf_collect.py` 修复**（`_is_self_or_helper()` 排除自身），并写入
`references/methodology-pitfalls.md` 第 19 条。

受影响的数据：`P2_MultimediaServer.csv`、`P3_load_continuous.csv`、`P3b_mediaindex.csv`（均为 v1 采集）。
**`P4_app_fixed.csv` 起为修复版，口径干净**，报告主结论基于它。
