八、口径声明

  • 网络列为整机口径：Linux 没有逐进程网络字节计数（/proc/<pid>/net/dev 属于整个网络命名空间），因此该列取自整机数据，不可归因给单个应用/功能。
  • 内存判压力请用 private_Dirty 或 PSS，不要用 RSS：RSS 含 RssFile（mmap 文件页缓存，内核可随时回收），会被严重放大。
  • CPU 为单核口径：100% = 1 个核，4 核跑满 = 400%。
  • 评审红线（硬性）：单个进程的内存峰值超过 1 GB —— 超过即需团队讨论评估，不是「达标 / 不达标」的二元判定。判定口径用 private_Dirty（真实匿名内存），不用 RSS（RSS 含可回收的 mmap 页缓存，会把页缓存误判成占用）。
  • 其余阈值为业界参考值（CPU ≤70%、%util ≤80%、错误率 ≤0.2% 等），非业务验收标准，需各项目组结合自身业务具体讨论定夺。本报告判定用达标线口径；源材料另有警戒值口径（CPU 75%~80%、磁盘繁忙率 <70%），两者含义不同，勿混用。
  • 跨应用对比的适用边界：不同应用若采样窗口不同、素材不同，均值不可直接精确比较。

九、已撤回的结论

保留纠错记录是报告质量的一部分。
  • **「按带宽可支撑 79 路」的推算已撤回。** 该结论基于「千兆 119 MB/s ÷ 单路 1.5 MB/s」，但实测证明应用的并发上限（约 50 路）先于带宽成为约束 —— 80 路时带宽只用了 64% 就已服务不过来。**容量应以实测的 ~50 路为准。**
  • 多路加压首次用 urllib 实现时曾出现「连接建立但数据不流」的卡死，一度怀疑是 MiniDLNA 并发上限；改用 curl 对照后确认那次是**采集脚本自身的 read 阻塞**问题。该怀疑已撤回 —— 但后续更严谨的测试确实**证实了存在并发上限**，只是原因不同。
  • 全速压测的客户端「合计 555 MB/s」曾看着像 4.4 Gbps，但那是各路平均速度相加、且小文件瞬间读完导致的虚高；以服务端实测为准应为 118.95 MB/s（千兆线速）。该口径已更正。

瓶颈分析与建议

瓶颈定位：**MiniDLNA 的并发服务上限（约 50 路）**，而非带宽 —— 80 路同时拉流时，前 50 路满速、第 51 路起逐级衰减、第 67 路起完全拿不到数据，而此时发送仅 79.83 MB/s（638.7 Mbps），**只占千兆带宽的 64%**
  • **并发上限实测**：80 路同时启动，前 50 路各 1.46 MB/s 满速，第 51-53 路衰减（1.09/1.18/1.29），第 54-66 路近乎无服务（0.01~0.44），第 67-80 路为 0.00；成功 67/80，合计 79.83 MB/s
  • **服务端进程树佐证**：并发 48 路时进程树 51（3 基础 + 48 流），并发 64/80 路时进程树**仍卡在 52**，说明应用不再为新连接 fork 服务进程
  • **限速并发完美线性**：16/32/48 路 → 24.9/51.7/78.0 MB/s（每路 1.56 MB/s），全程零错误；到 48 路后不再增长
  • **带宽不是瓶颈**：全速模式（少量连接高速读）可达 119.74 MB/s = 957.9 Mbps，**打满千兆**，证明链路本身有余量；瓶颈在应用的并发处理
  • **CPU 全程不是瓶颈**：并发 48 路时应用 CPU 均值 0.09%、峰值 5.00%；整机 CPU 均值 2.77%、峰值 12.47%
  • **内存无压力**：private_Dirty 均值 6.32 MB、峰值 9.32 MB；47.9 分钟长稳无单调爬升
  1. 容量规划按 **并发连接数** 算，不要按带宽算：实测约 **50 路** 1080p 并发播放是上限，建议留 30% 余量 → **≤35 路**
  2. **加 CPU / 内存 / 网卡都无用** —— 瓶颈在 MiniDLNA 的连接处理上限。要提并发需从应用侧改（如调整 minidlna 的 max_connections 并验证其 fork 模型能否承受）
  3. **链路饱和时真实播放器会卡顿**：全速压测期间，持续播放的 Windows Media Player 出现缓冲停住（发送归零），随后才恢复 —— 说明带宽被占满时在线播放会受影响
  4. 监控该应用时用 --app MultimediaServer|mediaindex|mediadb：索引与媒体库跑在独立服务里，不在应用进程树内
